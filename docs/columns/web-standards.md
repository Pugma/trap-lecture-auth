# コラム：Web 標準の形成

::: tip このページの目標

仕様の公開元・文書の状態・更新関係を確認し、標準の存在や接続に成功したことだけで安全性や適合性を判断しない理由を説明できるようになる

:::

::: info このページの要点

- **標準化**：通信と情報の解釈を共有するため、レビューや合意、実装間の相互運用を通じて約束を整える
- **文書の種類**：RFC はすべてが標準ではなく、公開元・版・文書の状態を確認して読む
- **実装と更新**：接続の成功だけで適合を判断せず、別実装や試験で確かめ、後続の安全性の知見も追う
- **学ぶ順序**：仕様の公開順ではなく解決したい問題から読み進め、判断の根拠は該当する仕様へ戻って確認する

:::

ブラウザが別の会社のサーバーへ接続できるのは、実装の内部が同じだからではありません  
相手へ送る情報と、受け取った情報の解釈について共通の約束があるからです  
認証連携でも、署名が正しいだけでは足りず、誰が誰に対して何を主張しているかを同じ意味で読める必要があります

標準化は、その約束を複数の参加者で検討する作業です  
W3C の説明では、広いレビュー、合意、実装と相互運用の確認が重視されます  
セキュリティ、プライバシー、アクセシビリティなど、ある実装の成功だけでは見えない問題も検討対象です [W3C Web Standards](https://www.w3.org/standards/)

## 標準文書の種類と状態

「RFC に書いてある」という説明を見たら、番号だけでなく文書の状態も確かめます  
[RFC](../reference/glossary.md#rfc) は文書シリーズの名前であり、すべてが Internet Standard ではありません  
Standards Track のほか、Best Current Practice、Informational などがあります  
[Internet-Draft](../reference/glossary.md#internet-draft) は作業中の文書であり、公開済みの RFC とは区別します  
[IETF RFCs](https://www.ietf.org/process/rfcs/)

OIDC Core は OpenID Foundation の仕様、WebAuthn は W3C の仕様です  
どちらも RFC 番号がないことを理由に非標準とは扱いません  
文書を読む際には、次の項目を確認します [OIDC Core の冒頭](https://openid.net/specs/openid-connect-core-1_0.html)、[WebAuthn の文書状態](https://www.w3.org/TR/webauthn-3/#sotd)

- 公開元
- 参照する版
- 文書が自分で示す状態

例えばライブラリの説明に「仕様対応」と書かれていても、その言葉だけでは対象を特定できません  
基本仕様のどのフローか、追加の拡張を含むか、どの版を基準にするかで、相手に期待できる振る舞いは変わります  
教材では「OAuth 対応」という名前だけで済ませず、Authorization Code Flow と PKCE S256 のように、使う契約を具体化します  
これは規格の名称を細かく暗記するためではなく、実装間で前提を揃えるためです

文書の状態と機能の用途も別の軸です  
Standards Track の文書であることから、すべてのサービスがその機能を実装すべきだとは決まりません  
まず自分が扱う課題にその仕様が適用されるかを判断し、そのうえで対象となる要件を読みます [IETF：RFCs](https://www.ietf.org/process/rfcs/)

## 相互運用と仕様適合の確認

約束が詳細でも、実装がその条件を取り違えることはあります  
逆に、自分たちの二つのプログラムが同じ取り違えをしていると、接続には成功してしまいます  
そこで別実装との接続や外部の適合試験が役立ちます  
本書ではこの問題を[OP の要件と相互接続](../chapter-3/oidc-provider.md#op)で扱います

教材の二つのアプリが、どちらも同じ誤った文字列を期待していたら、開発中の画面は正常に動くかもしれません  
しかし別の実装が仕様どおりの値を送ると接続できなくなります  
このとき直すべきなのは、別実装に独自の例外を追加させることとは限らず、自分たちの契約の読み違いかもしれません  
相互運用の確認は、実装が成功したように見える範囲の外から、その前提を調べる機会になります

一方、別実装と一回ログインできたことだけでは、不正な応答を拒否できるか、利用していないオプションを正しく処理できるかは分かりません  
接続試験で観測した範囲と、仕様の要求範囲を並べ、確認できなかった部分を残します  
標準が共通の条件を示し、試験が実際の振る舞いを確かめるという役割の違いを保ちます

また、公開済みの RFC 本文だけを読めば、以後の安全性の検討まで分かるわけではありません  
OAuth Security BCP は実践から得た知見を反映して元の仕様群を更新しています  
読者は文書の更新関係を追い、古い選択肢が現在も推奨されるかを確かめる必要があります [RFC 9700 の冒頭・§1](https://www.rfc-editor.org/rfc/rfc9700.html#section-1)

## 仕様の構成と学習順序

仕様書は相互運用の条件を厳密に伝えるために分かれています  
初めて読む人にとっては、同じ機能に複数の文書が関係し、必要な前提が離れた場所にあるように見えます

そこで本書では、メッセージを読む権限を渡す、戻ってきた応答を開始した処理に結び付ける、認証結果を検証する、という問題の順に読んでいきます  
この順序は教材の説明上の選択であり、標準化の歴史を再現した年表ではありません

読んだ後は仕様へ戻り、「誰に対する、どの条件での要求か」を自分で確かめることが目標です  
具体的な読み方は[RFC・仕様書の読解](../reference/reading-specifications.md)を参照してください
