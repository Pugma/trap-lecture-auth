# コラム：OIDC RP の実装

::: tip このページの目標

OP が発行した認証結果を受け取る RP 側で、検証・要求との対応・利用者の対応付け・セッションとログアウトをどこで判断するかを説明できるようになる

:::

::: info このページの要点

- **ログイン判定**：外部の認証結果の検証、内部ユーザーへの対応付け、利用可否、セッション確立、リソースへの認可を別々に判断する
- **検証処理**：受信したトークンをライブラリで検証し、検証で得た Claims だけを使う
- **要求との対応**：nonce などを開始したログイン処理ごとに保存し、対応しない応答を正常扱いしない
- **アカウントの対応付け**：`iss` と `sub` の組で外部アカウントを識別し、表示用の属性やメールアドレスで自動統合しない
- **セッションとログアウト**：RP のセッション、OP の認証状態、トークンは別々に終了する

:::

第3章の本編は、OP を作る提供側の視点で、RP が検証する条件を OP が満たす契約として扱いました  
このコラムはその裏側として、RP を作る側が受け取った結果をどう処理するかをまとめます  
[OIDC の目的とフロー](../chapter-3/oidc.md)、[ID Token の発行と検証](../chapter-3/id-token.md)、[OP の設計と相互接続](../chapter-3/oidc-provider.md)、[認証方式の比較と運用](../chapter-3/federation.md)の各節を補います  
以下は教材の設計例であり、RP の参照実装や接続試験の結果ではありません

## RP のログイン判定 {#rp-login-decision}

チャットビューアーが外部認証を受け入れる場合を、アプリ側の判断として分解します

1. 外部サービスへの要求と応答を検証する
2. 検証した外部アカウントを、アプリ内の利用者へ対応付ける
3. その利用者がアプリを利用できる状態か確認する
4. アプリ自身のログインセッションを確立する
5. 各操作で対象のリソースへの権限を確認する

例えば認証に成功した利用者でも、ビューアー側で利用停止になっているなら、三番目の判断で止まります  
外部 OP が認証したという主張と、このアプリがその利用者を受け入れることは別だからです  
外部アカウントに新しい表示名が付いたことを理由に、利用停止の内部アカウントを別人として作り直す設計も、対応付けの意味を崩します

この分解は、エラーをどこで扱うかにも役立ちます  
外部サービスの応答を検証できない場合は、その入力を信頼できません  
アプリ内のアカウントが利用停止なら、認証結果が正しくてもアプリの利用条件に基づいてログインを拒否します  
画面上の案内を必要以上に細かくする必要はありませんが、実装と試験では失敗した判断を区別します

### 接続先の方式の確認 {#rp-connection-requirements}

「新しいから OIDC」「既存製品でよく見るから SAML」という選び方だけでは、実際に接続できるかを判断できません  
教材のチャットビューアーを組織の認証基盤へ接続する設計演習なら、最初に次を確認します

- 相手が提供する方式とフロー、事前登録できる設定
- アプリ内の利用者と対応付ける識別子、およびその変更・再割当ての条件
- 再認証やログアウトについて、利用者へ提供したい振る舞い
- 運用中に設定や鍵を変更する手順と、障害時に調査できる記録

例えば、相手の IdP が SAML の特定 Profile だけを提供しているなら、アプリ側の好みで OIDC の endpoint を仮定することはできません  
逆に両方式が使えても、ログインに必要な属性や識別子の契約が揃うかを確かめる必要があります  
ログイン画面が表示されたことより、そのアカウントを翌日も同じ内部ユーザーへ対応付けられることが重要です

ここまでの比較は選定の問いを整理するもので、独自の変換器を作ることを勧めるものではありません  
方式を変換する仲介サービスを置く場合には、元の認証結果を検証し、新しい受信者向けに結果を発行する責任が増えます  
元の署名付き文書の値をコピーするだけでは、別方式の契約を満たしたことにはなりません  
方式ごとの比較は本編の[SAML Web Browser SSO との比較](../chapter-3/federation.md#comparison-saml-web-browser-sso-との比較)にあります

## ID Token の検証処理 {#rp-id-token-validation}

本編の[Claims の検証条件](../chapter-3/id-token.md#id-token-validation)は、RP が ID Token を受け入れる観点を示しました  
ここでは、その検証をアプリへ組み込むときに取り違えやすい点を扱います  
JWT の検証処理を自作する手順ではなく、OIDC を扱うライブラリの設定と検証範囲を確認するための観点です

### デコードと検証の違い {#rp-decode-vs-verify}

compact JWS を三つに分けてデコードすると JSON が読めますが、それは暗号を解いたという意味ではありません  
デコードしただけの内容は、まだ攻撃者から渡された未検証の入力です [RFC 7515 §3.1・§5.2](https://www.rfc-editor.org/rfc/rfc7515.html#section-3.1)  
ログイン判断には、受信したトークンの検証が成功した後の値だけを使います

#### JSON の表現と署名対象 {#rp-json-representation}

JWS の署名対象は、ヘッダーとペイロードを JSON として解釈した結果ではなく、定められた形式で連結したバイト列です  
JSON には空白や改行の入れ方、メンバーを並べる順序など、意味を保ったまま表現を変える余地があります  
受信した JSON を見やすく整形し直してから検証すると、発行者が署名したものとは異なる入力になります [RFC 7515 §3.1・§5.2](https://www.rfc-editor.org/rfc/rfc7515.html#section-3.1)

例えばデコードしたペイロードに改行を足して保存しても、表示用ファイルとしては同じ Claims を読めます  
しかし、そのファイルを改めて base64url 化した文字列へ元の署名を付け直せば、元の compact JWS と同じ検証結果になるとは限りません  
本編で表示用 JSON と[署名対象の文字列](../chapter-3/id-token.md#tokens-jws-の署名対象)を別々に示したのは、この違いを観察するためです

アプリケーションでは、ライブラリへ受信したトークンを渡して検証し、その検証で得た Claims を使います  
表示や保存のために加工した別のデータを、検証したデータと取り違えないことが重要です  
検証前と検証後に二回パースして別々の値を使う構成も、異なる解釈が入り込まないかを確認する対象になります

#### ヘッダーの検証 {#rp-header-validation}

署名方式や `kid` を読むために、検証前にヘッダーをパースすることはあります  
この段階で得た値は、検証処理の候補を選ぶための入力であり、信頼済みの設定ではありません  
例えばヘッダーに `alg=RS256` とあれば、RP の許可した方式の中で RS256 を扱えるかを調べるのであって、RP の許可一覧へ RS256 を追加するのではありません

同じように、`kid` は信頼する鍵の集合の中から候補を選ぶ手掛かりです  
攻撃者が同じ `kid` を付けた鍵を作っても、それだけで OP の鍵にはなりません  
文字列の一致で選んだ候補を使って、署名検証が成功するところまで確かめます  
入力と設定の役割を分けることが、アルゴリズムの混同を防ぐ前提です [RFC 8725 §3.1](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.1)

### 復号と発行者の確認 {#rp-decrypt-then-verify}

公開鍵で受信者宛てに暗号化する方式では、その公開鍵を知る人が暗号文を作れる構成があります  
したがって、受信者が自分の秘密鍵で復号できたことだけから、「信頼する OP が作った」とは判断できません  
内容を誰が読めるかという条件と、誰が発行したかという条件は分けて成立させます

ID Token を署名と暗号化の両方で保護する場合、OIDC は署名してから暗号化する順序を定めています  
受信側は外側を復号した後、内側の署名付き ID Token を検証し、さらに Claims を照合します [OIDC Core §2・§16.14](https://openid.net/specs/openid-connect-core-1_0.html#IDToken)、[RFC 7519 §11.2](https://www.rfc-editor.org/rfc/rfc7519.html#section-11.2)

ここで、外側の復号が成功したから内側の署名を省く、署名が成功したから `aud` を省く、という短縮はできません  
それぞれが異なる問いに答える処理だからです  
内側に想定していない形式や用途の値が入っていた場合も、そのまま汎用の JSON として受け入れるのではなく、要求した ID Token の契約へ照らします

## 要求との対応 {#rp-request-binding}

本編の[nonce による認証結果の照合](../chapter-3/id-token.md#oidc-nonce)では、OP が要求の nonce を ID Token に入れる契約を扱いました  
RP 側では、その値を開始したログイン処理と結び付けて保存し、照合します

### nonce の保存と使用済みの管理 {#rp-nonce-storage}

教材では RP が毎回 `nonce` を生成し、進行中のログイン要求とともに保存します  
応答の検証後はその要求の記録を使用済みにし、再利用を防ぎます  
Code Flow のあらゆる利用で nonce が無条件の MUST であるという説明ではなく、教材として要求との対応を明確にする選択です  
`state` と PKCE も維持し、それぞれの対応先を一つの「ランダム文字列」にまとめません

### 並行するログイン要求 {#rp-concurrent-logins}

同じ利用者がタブ A とタブ B でログインを開始し、B の応答が先に戻ったとします  
二つのログインを区別せず、ブラウザごとに「最後に作った nonce」一件だけを保存すると、A の正当な応答を照合できなくなる可能性があります  
だからといって nonce が一致しない場合だけ照合を省くと、本来拒否すべき応答も受け入れてしまいます

処理の開始時に nonce などをどう保存するかは RP の設計ですが、それぞれの応答がどの開始処理に対応するかを保てる必要があります  
片方の完了によってもう片方を終了させる設計を採るなら、その扱いも明示します  
同時に二つのログインが成功する必要があるかという製品上の選択と、対応しない値を正常扱いしないという検証条件を分けます

また、OP が同じ利用者を返したことだけで、この照合を省略できるとは限りません  
自分のアカウントについての正しい結果であっても、意図しないタイミングでセッションを確立する操作を受け入れることになるからです  
どの人物かだけでなく、どの処理に対する結果かもログインの契約に含まれます

### 拒否時の状態 {#rp-rejection-state}

正常系も、検証が終わる前に RP セッションを作っていないかを確認します  
画面にエラーが出たとしても、先にログイン Cookie を発行していれば拒否の契約は満たせていません  
試験対象は戻り値だけでなく状態の変化です  
拒否する条件の一覧は本編の[ID Token の拒否試験](../chapter-3/id-token.md#tokens-id-token-の拒否試験)にあります

## 属性と利用者の対応付け {#rp-account-mapping}

本編の[利用者の識別](../chapter-3/id-token.md#oidc-利用者の識別)では、OP が安定した `sub` と正しい `aud` を発行する契約を扱いました  
RP 側では、どの属性を求め、受け取った値を内部ユーザーのどの情報へ反映するかを決めます

### 共有する属性の選択 {#rp-attribute-selection}

ID Token に多くの属性を詰めるほど、RP のコードが簡単になるとは限りません  
属性を持つ場所が増えれば、更新の反映、保存期間、ログへの露出も増えます  
チャットビューアーが利用者を識別するだけなら、メール、所属、プロフィール全文が必要かを先に考えます

例えばアイコンと表示名は画面表示のために取得しても、アプリ内の所有者 ID は `iss` と `sub` の対応から決める構成にできます  
そうすれば表示用の属性が取得できなかったことと、認証結果を検証できなかったことを分けられます  
逆に、特定の属性を利用資格の判断へ使うなら、その属性の発行元、更新条件、欠落時の動作まで契約に含める必要があります  
要求する属性と、受け取った属性に基づいてアプリが許可する操作は別に設計します [OIDC Core §5.4](https://openid.net/specs/openid-connect-core-1_0.html#ScopeClaims)

これらは GitHub や traQ の実環境を追加で検証した結果ではなく、各方式を読むための設計上の問いです  
提供元の具体的な保証は、そのサービスの文書と採用した構成へ戻って確認します

### UserInfo の属性の反映 {#rp-userinfo-attributes}

例えばログイン後に利用者が表示名を変更したとします  
発行済み ID Token に入っていた表示名と、後から UserInfo で取得した表示名が違っていても、それだけで別人とは判断しません  
識別子の照合と、表示用の属性の更新を区別するためです  
一方、`sub` が違うなら、古いプロフィールだろうと推測して使い続けず、その応答を利用しません [OIDC Core §5.3.2](https://openid.net/specs/openid-connect-core-1_0.html#UserInfoResponse)

RP 側では、UserInfo から得た情報をどこへ反映するかを分けます

- 表示名や画像など、表示用として更新する情報
- 内部アカウントとの対応に使う識別子
- アプリの利用条件として別途評価する属性

表示名を更新する処理と内部アカウントを選ぶ処理が同じフィールドへ依存していると、プロフィール変更がアカウントの切替になってしまいます  
属性を一つのユーザーオブジェクトへまとめて扱う場合でも、どの値がどの判断の根拠かは失わないようにします

### 属性の欠落時の処理 {#rp-missing-attributes}

RP は実際に返された情報を確かめ、任意の属性が返されない場合と、識別に必要な情報の欠落を分けて扱います [OIDC Core §5.3.2・§5.4](https://openid.net/specs/openid-connect-core-1_0.html#ScopeClaims)  
例えばチャットビューアーが画像を取得できない場合、既定のアイコンで表示できる設計が考えられます  
それに対して、UserInfo に必須の `sub` がない場合は、表示の代替を用意する話ではありません  
誰の属性かを確認できない応答として扱う必要があります

また、情報が返らなかった理由を、必ず利用者の拒否と断定することもできません  
OP が保持していない、要求に含まれていない、開示されなかったなどの違いを、欠落だけから完全に識別できるとは限らないためです  
RP の動作は、推測した理由ではなく、実際に得られた保証とアプリの必要条件に基づいて決めます

### 外部アカウントと内部ユーザーの対応 {#rp-external-account}

教材で内部ユーザー `alice` に外部アカウントを結び付ける場合も、メールの文字列が一致しただけで自動統合する設計は採りません  
アカウント統合には、現在のアカウントを操作できることの確認など、別の判断が必要です  
ログインを導入することとアカウント回復・統合を安全に完成させることを分けます

例えばチャットビューアーが、内部ユーザー `viewer-42` に対して、発行元 `https://id.example` と `sub=user-17` の組を登録しているとします  
次のログインで表示名やメールアドレスが変わっても、この組が同じなら同じ外部アカウントとして照合できます  
逆に、同じメールアドレスでも `sub=user-89` なら、別の外部アカウントを既存の内部ユーザーへ結び付けようとしている状態です

| 受け取った情報の変化 | RP が考えるべき処理 |
| --- | --- |
| `iss` と `sub` は同じで表示名だけが変化 | 同じ外部アカウントの属性更新として扱う |
| `iss` は同じで `sub` が変化 | 新しい外部アカウントとして扱い、既存ユーザーへの統合は別途判断する |
| `sub` は同じで `iss` が変化 | 発行元が異なるため、同一人物という推測だけで統合しない |

この表は、仕様が定める識別子の安定性をアプリの設計へ適用した例です [OIDC Core §5.7](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability)  
内部ユーザーの ID と外部アカウントの組を分けて保存すれば、表示用属性の更新が、そのまま所有するデータの移転にならずに済みます  
外部アカウントの追加・解除は単なるプロフィール編集ではなく、その内部ユーザーへログインできる経路の変更です

### メールアドレスの確認とアカウント統合 {#rp-email-account-linking}

本編の[メールアドレスの確認](../chapter-3/id-token.md#oidc-メール確認とアカウント統合)で扱ったとおり、[`email_verified=true`](../reference/glossary.md#email-verified) は、OP がそのメールアドレスの制御を確認したという主張です  
そのアドレスを永遠に同じ人物が使うことや、別の OP の同名アカウントと同一であることまでは保証しません [OIDC Core §5.1・§5.7](https://openid.net/specs/openid-connect-core-1_0.html#StandardClaims)

例えば退職した人のアドレスが別の人へ再割当てされ、後任が新しい外部アカウントでログインした場合を考えます  
メールだけで照合すると、そのアドレスでメールを受信できる後任に、前任のチャットビューアー内の設定や保存データまで渡すことになります  
メールアドレスの確認は成功していても、以前と同じ利用者のアカウントであることは確認できていません

教材の設計では、新しい外部アカウントを既存ユーザーへ追加する操作を、ログインの自動処理から分けます  
現在の内部アカウントを操作できることと、追加する外部アカウントの認証結果の両方を確かめ、どのアカウントへ結び付ける操作なのかを保持します  
これは OIDC がアカウント統合の画面や回復手順を定めているという意味ではなく、RP に残る判断です

## RP のセッションとログアウト {#rp-session}

### 認証連携と Cookie セッション {#rp-cookie-session}

Cookie [セッション](../reference/glossary.md#session)は、ブラウザの次の要求をアプリ内の状態へ結び付ける仕組みです  
OIDC による認証連携を採用しても、OP の認証状態や RP のログイン状態を保持するために使います  
Cookie と OIDC は、同じ位置の代替案として比較するものではありません

RP が ID Token を検証してから自身のセッションを作ると、以後の通常画面では RP セッションを利用できます  
ここではセッション固定化への対策、Cookie の属性、有効期限、CSRF 対策などを別途扱います  
外部認証を導入したことによって、アプリ自身のセッション管理の責任がなくなるわけではありません  
[OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

### ログアウトと残存する状態 {#rp-logout-state}

教材のチャットビューアーで、RP のセッションだけを終了した場合を考えます  
次の要求でビューアーがログインを要求しても、OP に認証状態が残っていれば、再び連携した際にパスワード入力などを省略できる場合があります  
これは RP のログアウトが失敗した証拠ではなく、終了させた状態の範囲が違うことを示します

| 終了させる対象 | 教材で確かめる結果 | 別に判断する対象 |
| --- | --- | --- |
| RP のセッション | そのセッションで画面を利用できなくなる | OP の認証状態、API 用トークン |
| OP のセッション | その認証状態を新しい連携に再利用できなくなる | すでに成立した各 RP のセッション |
| トークンを更新する権限 | その権限で新しい Access Token を得られなくなる | 発行済み Access Token の残る有効期間 |

教材の設計レビューでは、「この端末の画面利用を止めたい」「紛失した端末にある権限を止めたい」「すべての連携先から利用を終えたい」を別の要求として書き出します  
終了させる対象が異なるため、先に利用者へ約束する効果を決め、その範囲を満たす処理と確認項目を選びます  
OP から RP へ終了を伝える仕様は、本編の[RP 間のログアウト連携](../chapter-3/federation.md#comparison-rp-間のログアウト連携)で扱います

## 具体例：GitHub OAuth Apps によるログイン {#rp-github-oauth-apps}

OAuth を利用したサービス固有のログインも、必要な契約と検証を補えば構成できます  
具体例が **GitHub OAuth Apps の Web application flow** です  
このフローでは ID Token ではなく、GitHub 固有のユーザー情報 API と識別子の契約を使います  
以下は GitHub の公式手順を、本教材のサーバー側 Web アプリに対応付けたものです [GitHub Docs：Authorizing OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#web-application-flow)

1. **ログイン開始を記録する**  
   アプリが state と PKCE S256 の値を用意し、ブラウザセッションに関連付けて保存し、認可要求を送る  
   GitHub の文書でも両者は強く推奨されている
2. **自分の要求への応答を交換する**  
   callback の state が保存値と一致することを確認し、バックエンドが自分のアプリの資格情報と verifier を使ってコードを交換する  
   ブラウザから任意の Access Token を受け取って代用しない
3. **取得したトークンで利用者を確認する**  
   バックエンドから `GET https://api.github.com/user` を呼ぶ  
   認可途中でアカウントが切り替わる場合があるため、新しいトークンを得るたびに確認する
4. **安定した識別子で対応付ける**  
   応答の `id` を GitHub のアカウント識別子として保存し、検証した結果から自分のアプリのセッションを作る  
   変更や再利用があり得る `login` やメールを識別キーにしない

要求との結合は [Web application flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#web-application-flow)、識別子の選択は [GitHub の不変 ID に関する指針](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/best-practices-for-creating-an-oauth-app#use-the-durable-unique-id-to-store-the-user)に基づきます  
複数の提供元を使うアプリでは、教材の設計として「GitHub という提供元」とその `id` の組を内部アカウントに結び付けます

GitHub には、OAuth App が自分のアプリに対して発行されたトークンを確認する **Check a token** API もあります  
`POST /applications/{client_id}/token` を client ID と secret による Basic 認証で呼び、対象のトークンを確認します  
これはアプリとの対応を追加で確認する手段であり、通常の Web application flow に毎回必須の手順としては案内されていません [GitHub REST API：Check a token](https://docs.github.com/en/rest/apps/oauth-applications#check-a-token)

この API で確認できるアプリとの対応と、現在のブラウザが開始したログインとの対応は別です  
token check や `/user` の成功だけで、state などの照合を省くことはできません  
これは、それぞれが確認する対象を分けたときの設計上の帰結です

この例の安全性は、GitHub の個別の契約とアプリ側の検証を組み合わせて成立させます  
OIDC は、そうした認証結果の伝達・検証を提供元を越えて共通化します  
「OIDC でなければログインは実現できない」という意味でも、「OAuth を使えばログインの安全性まで自動的に揃う」という意味でもありません  
ここで示した説明順は、GitHub の方式から OIDC が歴史的に生まれたという主張ではありません  
各手順を OIDC の契約と対応付けた表は、本編の[独自方式と OIDC の対応](../chapter-3/federation.md#oidc-独自方式と-oidc-の対応)にあります

## 確認問題

**問い：UserInfo で取得したメールアドレスが既存ユーザーと一致したので、そのユーザーとしてログインさせてよいでしょうか**

::: details 解説
メールアドレスの一致だけでは、同じ外部アカウントであることも、既存ユーザー本人であることも確認できていません  
外部アカウントは `iss` と `sub` の組で照合し、既存ユーザーへの追加は、現在の内部アカウントを操作できることを確かめる別の操作として扱います
:::
