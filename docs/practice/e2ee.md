# パスキーによる E2EE

::: tip このページの目標

PRF の出力から鍵を導き、サーバーに暗号文だけを保存する流れを実行し、どの改変や差し替えが拒否されるかを結果に基づいて説明できるようになる

:::

::: info このページの要点

- **課題**：手元でコマンドを実行し、PRF のテストベクター、復号、改変時の拒否、鍵スロットの追加を確認する
- **題材**：WebAuthn の仕様にあるテストベクターで認証器の PRF を再現するため、ブラウザや認証器は不要である
- **範囲**：鍵の導出と暗号化だけを扱う。ログインの検証（challenge・origin・署名・UV）は行わない

:::

座学の[パスキーによる E2EE の設計](../chapter-ex2/e2ee.md)で扱った鍵の階層を、実際の値と検証結果で確かめます  
題材は、このリポジトリの `examples/e2ee/` にあるスクリプトと、WebAuthn の仕様から写したテストベクターです

## 準備 {#準備}

リポジトリのルートで実行します

```sh
mise install
mise exec -- node examples/e2ee/notes.mjs
```

Node.js の標準機能（Web Crypto API）だけを使うため、npm パッケージのインストールは不要です  
IV を毎回乱数で作るので、`Server stores:` に表示される値は実行するたびに変わります  
それ以外は、次のような結果になります

```text
PRF output matches WebAuthn test vector: true
Server stores: { ... }
Decrypt with passkey A: true
Unwrap with unregistered passkey rejected: true
Changed ciphertext rejected: true
Ciphertext moved to another note rejected: true
Decrypt with passkey B after adding a key slot: true
Key slot bound to another credential ID rejected: true
E2EE fixture checks passed: PRF test vector, key wrapping, decryption, tampering, and key slots.
```

最後の行に続けて、WebAuthn RP としての検証を行っていないことが表示されます

RP のコードがこの値を扱うことはなく、ここではテストベクターを再現するためだけに置いています

<<< @/../examples/e2ee/prf-test-vector.json

読むときは次の点を確認します

- 鍵暗号化鍵は `extractable` を `false` にして導いており、スクリプトの外へ取り出せない
- `wrapDataKey` の `additionalData` に資格情報の ID を含めているので、鍵スロットは特定のパスキーに結び付く

## サーバーに保存されるもの {#サーバーに保存されるもの}

`Server stores:` の表示が、サーバーのデータベースに保存される内容にあたります  
スクリプトは、この中にメモの平文と PRF の出力が含まれないことを確かめています

<<< @/../examples/e2ee/notes.mjs#server-view{js}

表示された値を見て、次の問いに答えてください

- `prfInput` はサーバーに保存してよい値でしょうか
- サーバーがこの内容だけからメモを読むには、何が足りないでしょうか

::: details 解説
`prfInput` は PRF への入力であり、秘密ではありません  
同じ入力を認証器に渡さないと同じ出力が得られないので、ログインのたびにサーバーからブラウザへ渡す必要があります  
メモを読むには、認証器の中にある PRF の関数が必要です。サーバーはそれを持たないので、鍵暗号化鍵もデータ鍵も導けません
:::

## 正常系と拒否条件 {#正常系と拒否条件}

| 確認 | 期待する結果 | その結果が示す範囲 |
| --- | --- | --- |
| パスキー A で鍵スロットを開き、メモを復号する | 成功 | 同じ資格情報と同じ入力から、同じ鍵を導き直せる |
| 登録していないパスキーで鍵スロットを開く | 失敗 | 別の資格情報の PRF 出力からは、データ鍵を取り出せない |
| 暗号文の1ビットを変えて復号する | 失敗 | 読めない相手による改変も検知できる |
| メモの暗号文を別の ID のメモとして復号する | 失敗 | 暗号文を別のメモへ差し替えても受け入れない |
| パスキー B の鍵スロットを追加して復号する | 成功 | データを暗号化し直さずに、パスキーを増やせる |
| B の鍵スロットを A の資格情報 ID で開く | 失敗 | 鍵スロットを別のパスキーのものとして流用できない |

パスキー B を追加する処理では、先にパスキー A でデータ鍵を開いています

<<< @/../examples/e2ee/notes.mjs#add-passkey{js}

データ鍵を知っているのは、既に登録されたパスキーで開いた端末だけです  
サーバーはデータ鍵を知らないので、この処理をサーバーだけで行うことはできません

## 完了条件 {#完了条件}

手元でコマンドを実行し、すべての確認とスクリプト全体の成功を確かめてください  
そのうえで、次の三点を、確認した処理を指して説明できれば、この課題は完了です

- PRF の出力をサーバーへ送ってはいけない理由
- データ鍵をパスキーで直接暗号化せず、鍵スロットに分ける理由
- 暗号化に `additionalData` を付けることで、防げるようになった操作

発展課題として、パスキー B の鍵スロットを削除したあと、B で取り出されたかもしれないデータ鍵を使えなくする処理を書いてみてください

::: details 発展課題の解説
新しいデータ鍵を作り、既存のメモをすべて復号して新しいデータ鍵で暗号化し直します  
そのあと、残ったパスキー A の鍵スロットを新しいデータ鍵で作り直します  
鍵スロットを削除するだけでは、古いデータ鍵を知っている相手は、保存済みの暗号文を読めます
:::

::: details このスクリプトで確かめていないこと
ログインの検証（challenge・origin・RP ID・署名・UV）は行っていません  
ブラウザと認証器が `prf` 拡張に対応しているかも、このスクリプトでは確かめられません  
実際のサービスでは、[パスキーの実装](./passkeys.md)で扱う WebAuthn RP の検証と組み合わせ、対応するブラウザと認証器で試験する必要があります
:::
