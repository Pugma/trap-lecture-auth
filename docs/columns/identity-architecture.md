# コラム：IdP とユーザー管理の分離

::: tip このページの目標

IdP とユーザー管理を分離したときのデータと認証の責任を整理し、利用停止や通信障害がどこへ影響するかを説明できるようになる

:::

::: info このページの要点

- **責任と配置**：IdP・ユーザー管理・業務 API の責任は、同じプロセスでも別サービスでも区別する
- **データの所有者**：ユーザー情報、認証資格情報、セッション、権限について正本と更新主体を決める
- **通信の契約**：ユーザー情報の参照と認証結果の取得を分け、通信相手・要求との対応・失敗時の扱いを定める
- **状態の反映**：ユーザーの利用停止は、発行済みトークンや RP のセッションへ自動的には伝わらない

:::

本編では、OP がユーザーを認証し、認証結果に基づいて ID Token を発行する流れを扱いました  
その説明では、ユーザーの情報や認証結果を OP が取得できることを前提にしています  
ここでは、ユーザー管理と IdP を別サービスへ分けた場合に、その前提をどう成立させるか考えます  
以下は教材上の設計例であり、traQ の実際の配置や、稼働確認済みの参照実装ではありません

## 責任と配置

ここでいう **ユーザー管理サービス**は、ユーザーの作成・更新・停止やプロフィールの正本を管理するものです  
**IdP（Identity Provider）** は利用者の認証結果を他のサービスへ伝える役割で、本教材の OIDC では OP に対応します  
資格情報の検証までユーザー管理へ含めるかは設計上の選択であり、ユーザー情報を返せることだけでは認証したことになりません

| 配置 | 簡単になること | 分けて考える責任 |
| --- | --- | --- |
| 同じプロセス・同じ DB | 関数呼出しで情報を取得し、一つの DB のトランザクションで関連する更新をまとめやすい | 誰がユーザー情報、認証結果、トークンを更新できるか |
| 別プロセス・共有 DB | 既存のテーブルを参照できる | スキーマ変更と DB 権限に依存が残り、サービスを独立に変更できるとは限らない |
| 別サービス・別 DB | 所有するデータや公開する機能をサービスごとに限定できる | API・同期・障害時の動作と、情報が反映されるまでの遅延 |

マイクロサービスとして分けるときに変わるのは、主に内部の情報取得と状態管理です  
RP が信頼する issuer と OIDC の契約を維持すれば、RP にユーザー DB の分割方法を知らせる必要はありません  
OIDC は OP が利用者を認証する責任を定めますが、その内部で使う具体的な認証方法は規定していません [OIDC Core §3.1.2.3](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequestAuthentication)

## IdP とリソースサーバーの配置

IdP は認証結果とトークンを発行し、リソースサーバーは API への要求を認可します  
同じ利用者を扱っても責任は異なるため、同居させる場合にも、どの処理がトークンを発行し、どの処理が API 要求を受け入れるかを区別します

| 配置 | 利点 | 注意点 |
| --- | --- | --- |
| 同じプロセス・同じ DB | 関数呼出しと一つの DB トランザクションで、トークン発行・失効・API の確認を結び付けやすい。開発・運用の構成が小さい | 変更・障害・権限が一つのサービスへ集まる。API の増加に合わせて認証機能まで同時に配備・拡張しやすく、分離が必要になったときの境界が見えにくい |
| 別プロセス・共有 DB | デプロイ、負荷、障害をプロセス単位では分けられる。既存のデータを使いながら API と IdP の責任を分け始められる | DB のスキーマ、権限、移行順序に強く結び付く。リソースサーバーがトークンや認証用の表を直接読めると、プロセス境界を越えた内部実装への依存が残る。DB 障害と権限の影響範囲も共有する |
| 別プロセス・別 DB | データの所有者と DB 権限を分け、各サービスを独立に変更・拡張しやすい。リソースサーバーが認証用データへ直接アクセスしない境界を作れる | API 契約、サービス間認証、タイムアウト、再試行、監視、状態反映の遅れを設計する。単一トランザクションでまとめられない更新が増える |

どの配置でも、リソースサーバーが「この Access Token でこの操作を許可できるか」を判断する契約は必要です  
同じプロセスなら内部関数や保存層で確認でき、別 DB なら署名付きトークンを検証する、または IdP / Authorization Server へトークンの有効性を照会する、といった境界に応じた方式を選びます  
この選択は opaque token と JWT、失効の反映時間、鍵の配布とローテーションを一緒に決める論点です  
内部の直接 DB 参照を外部の Introspection エンドポイントと呼ばないことにも注意します [RFC 7662 §2](https://www.rfc-editor.org/rfc/rfc7662.html#section-2)

この表は「別 DB が常に優れる」という結論ではありません  
小さなサービスで一貫した更新を優先するのか、独立した変更・権限・障害範囲を優先するのかによって、受け入れる複雑さが変わります

## データの所有者

例えば、ユーザー管理にプロフィールと利用停止状態を置き、IdP に認証資格情報とログイン状態を置く構成を考えます

| 所有するサービス | 正本として管理する情報の例 |
| --- | --- |
| ユーザー管理 | 変更しない内部ユーザー ID、表示名、所属、利用停止状態 |
| IdP / OP | パスワード検証用の情報や WebAuthn 資格情報、認証セッション、認証時刻、同意、コード・トークン、署名鍵 |
| 業務 API | メッセージ、チャンネルの参加者、対象ごとの操作権限 |
| RP | 外部の `iss`・`sub` と内部アカウントの対応、RP 自身のセッション |

これは一つの分担例です  
IdP が持つプロフィールのコピーと、ユーザー管理の正本を区別し、同じ属性を両方から自由に更新する状態を避けます  
別 DB の同じ番号やメールアドレスを同一人物の根拠にせず、どの内部 ID をどの IdP の利用者へ対応付けたかを管理します  
RP へ公開する `sub` には OIDC の安定性・再割当て禁止の要件があり、内部 DB を移しただけで別人へ再利用してよいわけではありません [OIDC Core §2・§5.7](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability)

## 分離後のログイン

上の分担例で、チャットビューアーがログインを始めた場合を追います

1. RP がブラウザを OP の認証要求へ送る
2. OP が自分の認証処理で利用者を確認し、対応する内部ユーザー ID を得る
3. OP が認証されたサービス間通信でユーザー管理へ問い合わせ、利用停止状態とトークンの発行に必要な属性を取得する
4. OP が要求された条件と利用者の同意を確認し、認証時刻とともに自分のセッションを管理する
5. OP が認可コードを発行し、RP のコード交換に対して ID Token などを返す

RP はユーザー管理へパスワードを送らず、業務 API もユーザー DB を読むだけでログインを成立させません  
ユーザー管理から「この ID のレコードがある」と返ることと、手順2で利用者が認証されたことは別の事実です

プロフィールを読み取る API と、認証を担当する API は、返す結果の意味が違います  
既存の認証機能をユーザー管理側に残す設計なら、手順2の認証も委譲しますが、次のような契約が必要です

- **結果の意味**：認証された内部ユーザー ID、実際の認証時刻、必要な検証条件を返す
- **要求との対応**：結果を、その認証を開始した処理へ結び付け、別の要求の成功結果を使い回せないようにする
- **呼出し元の権限**：呼出し元を確認し、許可したサービスだけが認証処理や結果を利用できるようにする
- **失敗の区別**：資格情報の不一致と、認証サービスのタイムアウトを区別する

この API の形式は OIDC が自動的に定めるものではありません  
サービス間の認証に mTLS 等を使う話と、エンドユーザーを認証する話も別であり、詳しくは[マシンアカウントのコラム](../columns/machine-authentication.md)で扱います  
別サービスがすでに IdP なら、自分の OP がその IdP に対して RP として動く構成も考えられます  
その場合は上流の認証結果を検証し、自分の利用者へ対応付けてから、自分の issuer で下流向けの結果を発行します

## 参照と同期

ユーザー管理から情報を得る方式にも選択があります

| 方式 | 特徴 | 決めること |
| --- | --- | --- |
| 必要なときに API で参照 | その時点の情報を確認しやすいが、通信先の障害や遅延の影響を受ける | タイムアウト、取得できない場合の拒否、許容するキャッシュ期間 |
| 更新通知でコピーを同期 | ログイン時に正本へ問い合わせずに処理できるが、古い状態が残り得る | 通知の欠落・重複・順序逆転への対応、照合と再同期 |

ユーザー情報の作成・更新・削除をサービス間で扱う標準の一例に [SCIM（System for Cross-domain Identity Management）](../reference/glossary.md#scim) があります  
これはユーザーやグループを管理するためのプロトコルで、ログイン時の認証結果を RP へ伝える OIDC とは用途が異なります  
SCIM を導入すれば任意の変更が即時に全サービスへ届く、という意味でもありません [RFC 7644 §1・§3](https://www.rfc-editor.org/rfc/rfc7644.html#section-1)

別 DB へ分けた後は、ユーザー管理での更新と OP でのトークン発行を、通常の単一 DB トランザクションとしてまとめられません  
例えば利用停止の直前に確認が成功していた場合、直後の発行や既存セッションをどう扱うかを決めます  
単に内部関数を HTTP API に置き換えるだけでは、この時間差の問題は解決しません

## 利用停止と障害

ユーザー管理で A さんを停止しても、他の状態まで自動的に消えるわけではありません

- **OP**：停止を認識して新しい認証・発行・更新を止め、必要なセッションや許可を失効させる
- **業務 API**：発行済み Access Token を、どの時点から拒否するか決める
- **RP**：すでに作成したログインセッションを、いつ終了するか決める

署名と期限だけで Access Token を検証する API には、後から DB に書いた停止状態が届きません  
短いトークン寿命、失効情報の配信、トークンの有効性を照会する Introspection など、必要な反映時間に合う方式を選びます  
Introspection を使っても、AS 自身がユーザーの利用停止を反映していることが前提であり、照会結果のキャッシュにも遅延が残ります [RFC 7662 §4](https://www.rfc-editor.org/rfc/rfc7662.html#section-4)

教材の分離例では、必須とした利用停止状態の確認に失敗したら、新しいログインやトークン発行を成功扱いにしない方針を採ります  
一方で、任意の表示名だけ取得できない場合まで同じ停止条件にするかは別の選択です  
どの情報が認証・認可に必須かを決めれば、障害時の動作を整理できます

**確認問題：** ユーザー管理で利用停止にした直後、RP が以前作ったセッションで操作できました  
OIDC の署名検証を強化すれば、この問題を解決できるでしょうか

::: details 解説
署名は、発行後に変わった利用停止状態を通知する仕組みではありません  
ユーザー管理から OP への反映、発行済みトークンを API が拒否する条件、RP セッションの終了という経路を分けて確認します  
ログイン時に正しく検証したことと、後の権限変更を反映できることは別です
:::
