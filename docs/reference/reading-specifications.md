# 付録：RFC・仕様書の読解

::: tip このページの目標

通信や検証についての疑問から仕様の該当節へ進み、要件の対象・適用条件・実装上の選択を読み分けられるようになる

:::

::: info このページの要点

- **仕様群と契約**：OAuth/OIDC の文書構成と、入力・成立条件・結果・失敗時の動作を含む要件を確認する
- **該当節の探し方**：疑問を特定の主体と処理へ絞り、関連する仕様の参照先まで読む
- **要件の読み方**：MUST などの要件語を、対象・条件・動作・失敗時の処理と組み合わせて解釈する
- **文書の状態**：RFC 番号だけで判断せず、文書の位置付け・更新関係・Errata を確認する
- **実装への対応**：根拠の節と教材の選択、対応する試験、その実施状態を分けて記録する

:::

仕様書を最初のページから最後まで読んでからでなければ実装できない、ということはありません  
まず一つの疑問を持ち、該当する契約へたどり着き、その前提と周辺の条件を広げて読む方法があります  
本編の通信を踏まえ、このページでは「PKCE の `code_verifier` が違っていたら、何を返すべきか」を例にします

## 仕様と実装の責任 {#specifications}

本編で扱う通信や検証を、仕様の文書と要件へ対応付けます

### RFC と関連仕様の構成 {#specifications-rfc-と関連仕様の構成}

OAuth の仕様は一冊で完結せず、基本の枠組み、トークンの利用、追加の防御などに分かれています  
本書は次の仕様を組み合わせて扱います

| 文書 | 定める内容 |
| --- | --- |
| [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749.html) | OAuth 2.0 の役割、登録、認可の取得、トークンの更新 |
| [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html) | Bearer Token の提示とエラー応答 |
| [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636.html) | PKCE による認可要求とコード交換の結合 |
| [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html) | OAuth の安全性に関する要件・推奨と脅威への対策 |
| [OIDC Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html) | OAuth 2.0 上で認証結果を伝える手順と検証 |

[RFC](../reference/glossary.md#rfc) は文書シリーズであり、すべてが同じ意味での標準ではありません  
例えば RFC 6749 は [Standards Track](../reference/glossary.md#standards-track)、RFC 9700 は [Best Current Practice](../reference/glossary.md#bcp) です  
OIDC は RFC ではなく OpenID Foundation の仕様です  
文書の種類、更新関係、規範用語の読み方は、このページの後半で確認します

#### 仕様ごとの役割 {#specifications-仕様ごとの役割}

「認可コードを取得して交換する」という流れだけでは、Client と API の連携は完結しません  
交換して得たトークンをどの HTTP ヘッダーへ載せるかは Bearer の仕様、前半の要求と後半の交換をどう結ぶかは PKCE、安全性のため避けるべき古い構成は Security BCP から確認します  
基本仕様の成功例を一つ実装しただけでは、採用する構成に関係する条件をすべて読んだことにはなりません

例えば RFC 6749 には Password Grant の手順がありますが、RFC 9700 はその利用を禁止しています  
古い文書に通信形式が記載されていることは、現在それを選ぶ根拠にはなりません [RFC 6749 §4.3](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.3)、[RFC 9700 §2.4](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.4)  
仕様を読む際には、目的の節に加えて、その機能に対する更新や現在の安全性の要件も確認します

一方、OIDC を使わない OAuth で API を利用する権限を委譲する際に、ID Token の発行を必須条件として持ち込むのも誤りです  
追加仕様は、採用した機能に対応する契約を加えます  
すべての関連仕様を無差別に要求するのではなく、利用する機能、その主体、要求パラメータによって適用範囲を決めます  
本書では認可の通信を先に完成させ、その上に認証結果の連携を追加することで、この境界を追います

### インターフェースとしての要件 {#specifications-インターフェースとしての要件}

仕様は、実装間で共有するインターフェースとして読めます  
ただし、入力と戻り値の形式だけでなく、受け入れてよい条件と失敗時の振る舞いも含みます

- **入力**：要求を送る主体、パラメータ、資格情報
- **成立条件**：宛先、期限、要求との対応など
- **出力**：成功時に返す値と、その用途
- **失敗時の動作**：拒否条件、エラー形式、応答先

例えば認可コードは、トークンと交換するための一回限りの値です  
仕様は再利用の拒否を要求しますが、保存するデータベースの種類を指定してはいません  
内部の構成を選べることと、外部から観測される振る舞いが任意であることは異なります [RFC 6749 §4.1.2](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1.2)

OAuth と OIDC は、仕様で定めた範囲でプロトコルを拡張する余地も用意しています  
拡張する際には、対象に応じた命名・登録の規則や、拡張を理解しない相手の扱いに従います  
内部実装を選ぶ自由に加え、共通の要件を守りながら機能を追加するための規則も、仕様の一部です [RFC 6749 §8](https://www.rfc-editor.org/rfc/rfc6749.html#section-8)、[OIDC Core §2](https://openid.net/specs/openid-connect-core-1_0.html#IDToken)・[§5.1.2](https://openid.net/specs/openid-connect-core-1_0.html#AdditionalClaims)

この区別はライブラリの利用にも当てはまります  
ライブラリの既定値が仕様上の必須値とは限らず、ライブラリを呼ぶアプリケーションにも保証すべき条件が残ります  
本書では、仕様の要件、実装上の推奨、ライブラリの挙動、教材として選ぶ構成を区別し、各処理の説明に対応付けます  
実装はその理解を確かめる手段であり、IdP 全体の自作を本文の修了条件にはしません


### 認可要求を受け付ける条件 {#specifications-認可要求の受入条件}

後の章で扱う認可要求を、ここでは「外部アプリが許可を求め、結果の戻り先を指定する要求」として見ます  
成功時の応答だけを決めても、どこへ何を返してよいかという契約は完成しません

| 状況 | 確かめること | 応答の考え方 |
| --- | --- | --- |
| 要求と戻り先が正しく、利用者が許可した | 誰の、どのアプリへの許可か | 検証した戻り先へ成功の結果を返す |
| 戻り先は正しいが、利用者が拒否した | 拒否をアプリへ伝えてよい相手か | 検証した戻り先へ拒否の結果を返す |
| 戻り先が登録内容と一致しない | 応答先そのものが信頼できない | その戻り先へ自動的に転送しない |

OAuth は、不正な戻り先へ自動転送してはならないことと、利用者の拒否を `access_denied` で伝えることを定めています [RFC 6749 §4.1.2.1](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1.2.1)  
この例のポイントは、同じ「失敗」でも、応答先を信頼できるかによって処理が変わることです  
成功時と同じ転送関数を、すべてのエラーから呼ぶ設計では、この違いを表せません

仕様を実装へ移すときは、「戻り値に error があるか」だけでなく、「そのエラーを誰に返してよいか」まで読み取ります  
この読み方を、コード交換、トークン検証、認証結果の受入れにも適用します

#### 要件と実装上の選択 {#specifications-要件と実装上の選択}

本書の説明には、拘束する相手が異なる条件が含まれます

- **仕様の要件**：認可コードの再利用を拒否するなど、対応を名乗る実装が守る条件
- **ライブラリの責任**：ある条件を検証する処理が実装されていても、必要な設定とデータが渡されることが前提
- **教材の選択**：単一 issuer、事前登録したサーバー側 Client など、仕組みを追いやすくするために絞る構成

例えば、教材が利用者二人で動けば十分なのは、認可の違いを比較するためです  
仕様が利用者数を二人に限定しているわけではありません  
逆に、「教材では二回交換しない」という前提を置いても、一回限りのコードを再利用できる実装でよいことにはなりません [RFC 6749 §4.1.2](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1.2)

#### 要件の適用条件 {#specifications-要件の適用条件}

仕様の一文は、要求の強さだけでなく、誰にどの条件で適用されるかまで含めて読みます  
例えば confidential Client と public Client は秘密の保持能力が異なり、同じ認証方法を一律に要求することはできません  
本教材のサーバー側 Client が秘密で認証することから、すべての OAuth Client に秘密の配布が必要だと一般化しないようにします [RFC 6749 §2.1・§2.3](https://www.rfc-editor.org/rfc/rfc6749.html#section-2.1)

また、パラメータを送るかどうかが任意であることと、送られた後の処理が任意であることは違います  
後で扱う OIDC の `max_age` は任意の要求パラメータですが、指定された場合には認証の経過時間に関する処理が必要です  
「任意なので無視できる」と読むと、Client が要求した条件を満たしていない認証結果を返してしまいます [OIDC Core §3.1.2.1](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest)

次のように対象と条件を短く書き出すと、実装へ割り当てやすくなります

| 観点 | 読み取る内容 |
| --- | --- |
| 誰の義務か | Client が送る条件か、AS が拒否する条件か |
| いつ適用されるか | すべての要求か、あるパラメータを受けた場合か |
| 何を保証するか | 値の一致、宛先の検証、再利用の拒否など |
| 何を選べるか | 保存方式、画面構成、教材で扱う Client の種類など |

実装する際には、必要な検証の存在だけでなく、検証に使う情報の出所も確認します  
ライブラリが Client の登録情報と callback を比較しても、アプリが要求に含まれる未検証の値を登録情報として渡していれば、期待した保証にはなりません  
関数の呼び出しが成功したという事実は、その入力を信頼してよかったことまで証明しません

試験にも同じ区別が当てはまります  
正常な入力で成功する試験は通信の接続を確認しますが、条件を一つずつ変えて拒否されることを確かめなければ、要求を受け付ける条件の実装は確認できません  
逆に、すべてを拒否する実装でも異常系だけは通るため、成功と失敗の両方を同じ契約へ対応付けます  
その対応があれば、内部構造を変更した後も、守るべき外部の振る舞いを確認できます

**確認問題：** 利用者が許可を拒否した場合と、戻り先が不正な場合を、同じ転送処理で扱ってよいでしょうか

::: details 解説
拒否という結果だけでは、転送してよいかは決まりません  
戻り先を検証できている場合にはアプリへ拒否を伝えられますが、不正な戻り先への自動転送は避けなければなりません  
入力の形式、要求を受け付ける条件、失敗時の動作をまとめて契約として読む必要があります
:::

## 処理と該当節の特定

「OAuth のエラー」だけでは、認可エンドポイントのブラウザ応答なのか、トークンエンドポイントのサーバー間応答なのかが分かりません  
今回の問いは、認可コードを交換する要求で、先に保存された challenge と verifier の対応を検証する場面です  
登場する値と処理を絞れたら、RFC 7636 の目次から §4.6 のサーバー側の検証へ進めます

その節は、交換要求の `code_verifier` を元の方式で変換し、保存された challenge と比較すること、不一致なら `invalid_grant` を返すことを定めています  
エラー応答の詳細については RFC 6749 §5.2 を参照しています  
したがって PKCE の RFC 一冊だけで読み終えず、参照先にある HTTP 応答と JSON の条件へ進みます [RFC 7636 §4.6](https://www.rfc-editor.org/rfc/rfc7636.html#section-4.6)、[RFC 6749 §5.2](https://www.rfc-editor.org/rfc/rfc6749.html#section-5.2)

この順番なら「認証で失敗したから何となく 401」という連想を避けられます  
認可要求で未検証の redirect URI へエラーを返すか、トークン要求で JSON を返すかも、同じ名前のエラーだけからは決まりません  
仕様書では、処理を受け付ける主体と通信の経路を先に確かめます

検索結果の短い抜粋から読み始めた場合も、見つかった一文だけを実装要件にしません  
その文がどの見出しに属し、直前にどんな条件が置かれているかを確認します  
PKCE の例なら、challenge を保存する場面と verifier を比較する場面は別の節です  
検証処理だけ読んで保存側の対応を見落とすと、何と比較すればよいかが実装に残りません  
RFC 7636 §4.4 は認可要求を受けた側の処理、§4.6 はコード交換時の検証を扱います [RFC 7636 §4.4](https://www.rfc-editor.org/rfc/rfc7636.html#section-4.4)

読む途中で分からない語が増えたら、本文の定義へ戻ります  
例えば client はブラウザそのものを指すのか、ブラウザを使って認可を受けるアプリを指すのかで、秘密を置く場所の判断も変わります  
図の矢印を追う際にも、仕様で定義された主体名と自分の構成を一度対応付けると、通信経路を読み違えにくくなります

## 要件の構成

見つけた文をそのままテスト名にする前に、対象、条件、動作、失敗時を整理します  
今回の例は次のように分けられます

- 対象：認可サーバー
- 条件：PKCE の検証を行うコード交換
- 動作：保存済みの方式で verifier を変換して比較する
- 失敗時：対応するエラーを返す

この整理は教材で使う読解方法であり、新しい規範を追加するものではありません

さらに、仕様が観測可能な結果を定めているのか、内部の実装方法まで指定しているのかを区別します  
例えば、ある値の一致を確認する要件から、必ず特定の DB 製品を使うという結論は出ません  
一方で保存方法を選べることから、一致を確認する要件まで省略できるわけでもありません  
設計レビューでは「この保存方式を選んだ」と「この検証は要求される」を別の文にすると、変更してよい部分が明確になります

試験に落とす際には、次のように観測する結果も具体化します

| 要件から導く疑問 | 教材で確認する結果 |
| --- | --- |
| verifier が対応しているか | 正しい値ならコード交換が成立する |
| 不一致を拒否するか | エラーを返し、Access Token を発行しない |
| 別の検証で先に落ちていないか | 同じ前提の正常な要求を用意し、verifier だけを変更する |

表の最後の行は、プロトコルに新しい要件を加えるものではなく、試験結果を解釈するための条件です

試験では、コードが未使用で有効であり、クライアント認証、redirect URI、期限などの前提条件を満たすことも確認します  
すべて同時に壊した要求からエラーを得ても、verifier の検証が働いた証拠にはなりません  
本教材では、正常なコード交換を基準として verifier だけを変更し、トークンが発行されないことも確認する試験を設計します

同じ読み方で「PKCE S256 を採る」という教材上の選択を分けられます  
ある構成で必要な方式を固定したことを、過去と現在の全クライアントに対する一律の仕様要件へ書き換えてはいけません  
安全性の要件は、基本仕様に加えて OAuth Security BCP の該当条件も読みます [RFC 9700 §2.1.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1.1)

## 要件語と適用条件

MUST、SHOULD、MAY は、仕様の要求を読み分ける手掛かりです  
SHOULD を「気分で省略できる」、MAY を「実装しなくても受信した値を無条件に無視できる」と読み替えないようにします  
RFC 2119 の定義と RFC 8174 による補足を確認し、文書がそれらを採用しているか、規範的な大文字の用法かを見ます [RFC 8174 §2](https://www.rfc-editor.org/rfc/rfc8174.html#section-2)

とくに主語を落とさないことが重要です  
クライアントが行う検証を OP の機能一覧へ移したり、Authorization Server の条件を Resource Server のものとして記録したりすると、ライブラリを選んでも必要な検証を誰も担当しないままになります  
OPTIONAL なパラメータでも、受信した場合の処理が別途要求されることがあります  
OIDC の `max_age` では、指定された最大経過時間を認証時刻と比べる条件へ進んで読みます [OIDC Core §3.1.2.1](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest)

SHOULD の例外を採る場合も、理由が「実装が少し長くなるから」だけでは、影響を評価した説明になりません  
RFC 2119 では、特定の状況で異なる選択をする理由があり得る一方、影響を理解し、慎重に判断することを求めています [RFC 2119 §3](https://www.rfc-editor.org/rfc/rfc2119.html#section-3)

SHOULD を読むときは、適用される状況、推奨どおりにした場合の効果、例外にした場合の影響、代替策を対応付けます  
「MUST ではないから不要」とだけ読むと、どの前提が変われば推奨を満たす必要が生じるのかが分かりません

## 文書の状態と更新関係

RFC は公開文書のシリーズで、すべてが Internet Standard ではありません  
Standards Track、Best Current Practice、Informational などの位置付けを確認します  
Internet-Draft は作業中の文書であり、RFC と同じ公開状態とは扱いません  
OIDC は OpenID Foundation、WebAuthn は W3C の文書体系で作られており、RFC 番号がないことは根拠が弱いことを意味しません  
[IETF：RFCs](https://www.ietf.org/process/rfcs/)

更新関係も確認します  
Updates は既存文書への追加や変更の関係、Obsoletes は置換関係を調べる入口になります  
本文が公開当時のまま残っていることと、現在それだけを実装指針にしてよいことは別です  
たとえば古い本文にフローの説明があるからといって、安全性に関する後続文書を読まず、現在の教材の実装対象へ戻してはいけません [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)

Errata は誤りの報告や扱いを調べる場所ですが、報告があるだけで本文を好きに書き換えてよいわけではありません  
状態、内容、関連する議論を確認し、教材では何を根拠に解釈したかを記録します  
最新の作業版を見た場合も、公開済みの仕様と同じものとして URL を混ぜないようにします  
[IETF：RFCs の Errata の説明](https://www.ietf.org/process/rfcs/)

## IANA registry と値の定義

パラメータ名、トークンの種類、エラーなどの登録値を調べるときには、IANA registry も使えます  
たとえば OAuth Parameters の表には、各登録項目と根拠となる文書への参照があります  
しかし一覧表から名前を見つけただけでは、使う条件や検証手順は分かりません  
対応する仕様の節まで戻る必要があります  
[IANA：OAuth Parameters](https://www.iana.org/assignments/oauth-parameters/)

教材固有の scope を決めることと、標準 Claims や認証方式の値を勝手に発明することも分けます  
標準値に見える名前を付けたからといって、他の実装と同じ意味を共有できるわけではありません  
名前、意味、誰が解釈するかを揃えるところまでが契約です

仕様に拡張できる場所がある場合は、その入口の規則も読みます  
たとえば値を増やせることと、既存の値の意味を独自に変えることは違います  
名前を登録する手順があるなら、その手順と、値の意味を定義する文書を確認します  
一方、サービス内で使う scope のように、そのサービスの契約として意味を共有する部分もあります  
何でも IANA に登録する、何でも好きな文字列を使う、というどちらか一方の規則にはまとめません [RFC 6749 §8](https://www.rfc-editor.org/rfc/rfc6749.html#section-8)

## 仕様・設計・試験の記録

後で同じ判断を見直せるよう、本教材では次の項目を一緒に記録します

- 根拠となる文書と節
- 要求の対象となる主体と条件
- 教材の選択
- 対応する確認と、その実施状態

仕様を読んで妥当と考えた状態と、実装のテストが通った状態を分ければ、API の版が変わった際にどこを再確認すべきかも分かります

たとえば verifier の例なら、根拠は RFC 7636 §4.6、教材の方式は S256、試験は正しいコードに対する verifier の差し替え、実施状態は参照実装ができるまで未実施です  
設計の筋が通ったことを、コードが実行済みである証拠にはしません  
この区別を最後まで維持することが、仕様を実装へつなぐ読み方です

未確認の部分がある場合も、空欄にするより「仕様の解釈は確認したが、固定したライブラリ版での挙動は未確認」と残すほうが次の作業を選べます  
ライブラリが返すエラーを読めただけなら、アプリケーションが正しい HTTP 応答へ変換するところは別の確認です  
根拠、設計、コード、実行結果を一段ずつ対応付けることで、問題が見つかった際にどの段階へ戻るべきかを判断できます

:::
