## パスキーの仕組みと認証の設計 {#passkeys}


第3章で扱った OIDC の認証連携を踏まえ、OP が利用者を認証する入口としてパスキーを考えます  
この章はコードなしで読める読み物です  
パスキーは、あるサービスのログイン方法として抽象的に扱います  
以下は問題を理解するための説明順であり、技術の発明や普及を年代順に再現したものではありません

### パスワードの課題 {#passkeys-パスワードの課題}

あるサービスの利用者が短いパスワードを選べば、攻撃者は推測を試みられます  
十分に長くても、別サービスと使い回していれば、そちらで流出した情報が入口になります  
さらに、利用者が本物そっくりの画面へ入力すれば、パスワードの長さとは別の理由で秘密が渡ります  
「複雑にしてください」という指示だけでは、それぞれの失敗を解消できません

追加のワンタイムコードを求める設計では、盗まれたパスワードだけで入れる経路を減らせます  
しかし偽サイトが入力されたコードも直ちに本物へ中継する場合、コードが短時間で変わることだけでは十分ではありません  
ここで欲しい性質は、秘密を覚えやすくすることではなく、認証の証拠を本来の利用先へ結び付けることです  
NIST はこの性質を[フィッシング耐性](../reference/glossary.md#phishing-resistance)として扱い、手入力 OTP と区別しています [NIST SP 800-63B-4 §3.2.5](https://pages.nist.gov/800-63-4/sp800-63b.html#phishres)

これらの違いを、利用者の努力だけで解決できる範囲と照らし合わせます  
パスワードを長くすることは推測への対策になりますが、入力先へそのまま渡る性質は変わりません  
短時間で変わるコードも、攻撃者が時間内に転送できるなら転送先との対応は保証しません  
そこで認証方式を比較するときは、秘密の長さや画面の操作数だけでなく、得られた証拠を別の相手が再利用できるかを問います

例えば本物のサービスから届く確認コードを偽サイトへ入力した利用者に、さらに長いコードを求めても、転送の構造は残ります  
ここで変えたいのは、人間が毎回正しい相手を見抜くことへの依存です  
利用先を技術的な検証へ組み込むことで、利用者が似た画面を見た場合にも、同じ証拠を本物へ流用できないようにします

### 認証の対象と保証範囲 {#definitions-認証の対象と保証範囲}

例えば要求にユーザー名 `alice` が含まれていても、分かるのは送信者がその名前を指定したことだけです  
パスワードの検証に成功して初めて、サーバーはそのアカウントに登録された秘密を知る者からの要求として扱えます  
ただし、共有されたパスワードや盗まれた秘密でも同じ検証は成立し得ます  
「認証に成功した」という結果は、採用した証拠と検証方法の前提の下で解釈する必要があります

公開鍵による認証でも、鍵を使った計算が正しいことだけで、人間の氏名や所属が分かるわけではありません  
どのアカウントにその鍵を登録したかという結び付きがあって、初めて認証結果をアカウントへ対応付けられます  
登録時に別人のアカウントへ鍵を追加できるなら、その後の暗号学的な検証が正しくても、意図したアカウントの保護にはなりません

ここで区別するのは、主張する名前、証拠を検証する手続き、証拠とアカウントの対応です  
名前を自由に書けること自体が問題なのではなく、確認していない名前を検証済みの主体として後続処理へ渡すことが問題になります

身元確認は、オンラインの主体を現実の人物へ結び付けるための別の過程です  
NIST はこれを identity proofing として認証とは別に扱い、証拠の真正性や、提示者と証拠の対応などを区別しています [NIST SP 800-63A-4 §2](https://pages.nist.gov/800-63-4/sp800-63a.html#sec2)  
教材で「A としてログインした」と書く場合、A という内部アカウントについての結果を指します  
その利用者の実名が確認された、現在も特定の組織に所属する、といった追加の主張までは含めません


### 公開鍵による認証 {#passkeys-公開鍵による認証}

公開鍵による認証では、サービスが検証に使う[公開鍵](../reference/glossary.md#public-key)と、認証する側が使う[秘密鍵](../reference/glossary.md#private-key)を分けます  
登録後のログインでは、毎回の challenge を含む応答を作り、サービスが検証します  
過去の応答を取り出すだけでは、新しい要求に対する証明にはなりません  
WebAuthn はこの登録と認証の手順を定め、資格情報を RP ID と結び付けます [WebAuthn Level 3 §7](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-rp-operations)

署名の役割を、教材用のログイン要求で追ってみます  
サーバーが今回の要求用に challenge を発行し、認証器は秘密鍵を使って応答へ署名します  
サーバーは登録済みの公開鍵でその署名を検証します  
公開鍵を知っているだけでは、新しい要求を通す署名を作れないことが、この方法の基礎です

ただし、正しい署名があることと、今回のログインを受け入れてよいことは同じではありません  
WebAuthn の認証応答では、challenge や origin を含む client data のハッシュと、RP ID のハッシュなどを含む authenticator data が署名の対象になります  
サーバーは署名だけでなく、それぞれが期待した要求・利用先に対応することも調べます [WebAuthn Level 3 §7.2](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-verifying-assertion)

例えば、昨日のログイン応答を再送された場合、署名自体は正しくても、今回発行した challenge とは一致しません  
同じ署名を何度も見せれば入れる方式ではなく、そのときの要求に対応する応答を作れることを確かめています  
登録時に公開鍵をどのユーザーへ結び付けたかも重要です  
攻撃者の公開鍵を利用者 A のものとして登録してしまえば、署名検証は攻撃者の操作を正しく受け入れてしまいます

この性質は、登録・認証・認可を分けると理解しやすくなります

| 段階 | 主な問い | その段階だけでは決まらないこと |
| --- | --- | --- |
| 登録 | このユーザーへ、この公開鍵を結び付けてよいか | 将来のすべての要求を許可してよいか |
| 認証 | 登録済みの鍵で、今回の要求に対応する証拠を作れたか | どのデータを閲覧・変更してよいか |
| 認可 | 認証した主体に、要求された操作を許してよいか | 以後のログインや別の操作も許してよいか |

鍵の暗号学的な性質が強くても、最初の結び付けを誤れば認証対象を取り違えます  
また、正しい鍵を使った認証が成功しても、管理者の権限が生じるわけではありません  
本編の「認証したことと許可したことを分ける」という原則は、ログイン方式をパスキーへ変えても同じです

あるサービスの偽サイトでは、パスワード入力欄の見た目を模倣することで、利用者から秘密を取得できる場合があります  
利用先に結び付いた資格情報では、見た目だけをコピーしても、本物用の認証をそのまま成立させられません  
この差は、利用者による URL の目視確認への依存を減らします  
ただし、ログイン後のセッションを盗まれる問題や、本物のサイト自身が侵害される問題は、別に残ります

利用先との結び付きは、画面に表示するサービス名だけで決まるものではありません  
例として、本物を https://auth.example、偽サイトを https://auth-example.invalid とします  
偽サイトが本物のロゴを表示し、本物から得た challenge を中継しても、ブラウザが扱う出所は偽サイトのままです  
WebAuthn ではブラウザが要求元と RP ID の関係を確かめ、サービス側も応答の origin と RP ID に対応する値を検証します  
この例のような無関係のドメインが、本物の RP ID を自由に名乗ることはできません [WebAuthn Level 3 §5.1.4.1](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-discover-from-external-source)

手入力のワンタイムコードでは、偽サイトへ入力された値を攻撃者が本物へ転送できることが問題でした  
WebAuthn は、使う資格情報と認証の証拠を利用先へ結び付けることで、そのまま転送する攻撃を抑えます  
NIST が説明する verifier name binding は、このように検証先の名前と認証の証拠を結び付ける性質です [NIST SP 800-63B-4 §3.2.5](https://pages.nist.gov/800-63-4/sp800-63b.html#phishres)

この説明は、正しいブラウザと認証器、適切な RP ID・origin の設定と検証を前提にしています  
本物のサイト上で不正なスクリプトが動く場合まで、偽ドメインとの区別で解決できるわけではありません

ログイン後に発行されたセッションの扱いも別に残ります  
パスキーで入った後の操作をセッション Cookie で受け付ける設計なら、通常の API 呼出しごとにパスキーの署名を検証しているとは限りません  
その Cookie が盗まれた場面では、入口の公開鍵認証を破らずに、既に認証された状態を使われる可能性があります  
したがって「秘密鍵を盗まれていない」という説明だけで、ログイン後の操作まで安全と結論付けないようにします

教材上の設計例として、閲覧中のセッションから資格情報の追加へ進むときに再認証を求める案を考えられます  
この場合、再認証の結果を重要操作へどう結び付け、どの程度の時間や回数まで有効とするかを決めます  
再認証用の画面を一度表示しただけでは、サーバーがその操作を保護したことにはなりません  
利用者、対象操作、検証した時刻の対応を、サーバー側で確認できることが必要です

[WebAuthn](../reference/glossary.md#webauthn) は Web アプリケーションから公開鍵資格情報を扱うための API と手順です  
[CTAP](../reference/glossary.md#ctap) はクライアントと認証器の間の通信を扱い、FIDO2 はこれらに関わる枠組みです  
[パスキー](../reference/glossary.md#passkey)は、この仕組みを使うパスワードに代わる資格情報として説明されます  
これらの名称は、API、通信、資格情報という異なる対象を指します [FIDO Alliance：Passkeys FAQ](https://fidoalliance.org/passkeys/)  
WebAuthn は W3C が、CTAP は FIDO Alliance が仕様を公開しており、FIDO Alliance はパスキーという呼び方と利用者・提供者向けの解説もまとめています  
仕様の細部は W3C や FIDO Alliance の仕様書に、利用者への説明の仕方や導入の進め方は FIDO Alliance の [Passkey Central](https://www.passkeycentral.org/ja/home/) に戻って確認できます

### 認証器の種類とパスキーの位置付け {#passkeys-認証器の種類}

パスキーは WebAuthn の使い方の一つです  
このページでは WebAuthn 全体を網羅せず、パスキーを理解するのに必要な周辺の知識だけを紹介します

WebAuthn は、資格情報を作って使う認証器を、端末との接続の仕方で二つに分けます  
端末に組み込まれた platform authenticator と、取り外して別の端末でも使える roaming authenticator です [WebAuthn Level 3 §6.2.1](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-authenticator-attachment-modality)  
スマートフォンやノート PC の画面ロック・生体認証と連動するものが前者、USB や NFC で接続するセキュリティキーが後者の代表例です

roaming authenticator とブラウザ・OS の間の通信を定めるのが CTAP です  
CTAP は通信路として USB、NFC、Bluetooth Low Energy を定めています [CTAP 2.2](https://fidoalliance.org/specs/fido-v2.2-ps-20250714/fido-client-to-authenticator-protocol-v2.2-ps-20250714.html)  
WebAuthn の通信路の種類には `hybrid` もあり、例えばデスクトップ PC でのログインにスマートフォンを認証器として使う経路を表します [WebAuthn Level 3 §5.8.4](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#enum-transport)

資格情報にも二つの種類があります  
サービスが資格情報の ID を先に指定して使うものと、サービスが ID を指定しなくても認証器側で候補を見つけられる discoverable credential です  
WebAuthn Level 3 は、パスキーを discoverable credential の別名として定義しています [WebAuthn Level 3 §4](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#passkey)  
パスワードでアカウントを特定した後に、追加の確認としてセキュリティキーを使う方式では、discoverable でない資格情報も使われます

#### セキュリティキーの例：YubiKey {#passkeys-yubikey}

よく知られたセキュリティキーの例が、Yubico の YubiKey です  
YubiKey 5 シリーズは FIDO2 / WebAuthn と FIDO U2F に対応し、機種に応じて USB や NFC で接続します [Yubico：FIDO2 / U2F](https://docs.yubico.com/hardware/yubikey/yk-tech-manual/yk5-apps-fido.html)

YubiKey に保存したパスキーは、そのキーの外へ複製できないデバイス固定型です [Yubico：Passkeys FAQ](https://docs.yubico.com/hardware/yubikey-guidance/best-practices/all-faq-passkeys.html)  
保存できる discoverable credential の数には上限があり、ファームウェア 5.7.4 以降で 100 件、それより前は 25 件です [Yubico：Firmware 5.7](https://docs.yubico.com/hardware/yubikey/yk-tech-manual/yk5-firmware-5.7.html)  
端末を替えても鍵が移らない代わりに、紛失時は[資格情報の同期と紛失時の回復](#passkeys-資格情報の同期と紛失時の回復)で扱う予備のキーのように、別の資格情報を登録しておく設計が必要になります  
製品の仕様は更新されるため、採用するときは製品の公式文書で確認します

#### この教材で扱わない WebAuthn の機能 {#passkeys-扱わない機能}

WebAuthn には、この教材で扱わない機能も多くあります  
例えば次のものです

- **attestation**：登録時に、認証器の種類や出所を RP が判断するための証明を受け取る [WebAuthn Level 3 §6.5](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-attestation)
- **拡張**：資格情報の性質を返す `credProps` や、資格情報から擬似乱数を得る `prf` などを追加する [WebAuthn Level 3 §9](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-extensions)
- **conditional mediation**：ユーザー名の入力欄の自動補完から、パスキーを選べるようにする [Credential Management Level 1](https://www.w3.org/TR/credential-management-1/#dom-credentialmediationrequirement-conditional)

登録・認証で何を検証するかが分かれば、これらも仕様の該当節から追えます  
使う場合は、それが何を追加で保証し、何を保証しないのかを同じ観点で確かめます

### 認証手段と認証要素 {#definitions-認証手段と認証要素}

[認証手段](../reference/glossary.md#authentication-method)は、パスワードやパスキーなどの具体的な方式を指します  
[認証要素](../reference/glossary.md#authentication-factor)は、知識・所持・生体など、認証に用いる証拠の性質による区分です  
[多要素認証](../reference/glossary.md#mfa)（MFA）は異なる種類の要素を組み合わせるものであり、入力画面や操作の回数による分類ではありません [NIST SP 800-63B-4 §2・§3](https://pages.nist.gov/800-63-4/sp800-63b.html#sec2)

複数の手段を選択可能にすることと、複数の要素を必須にすることも異なります  
同じ権限へ到達する認証経路が A OR B なら、A の強化だけでは B の条件は変わりません  
A AND B でも、同じ原因で両方が破られる可能性があります  
以下では、パスキーのユーザー検証と、回復経路を含む認証の条件へ対応付けます

### 認証器内のユーザー検証 {#passkeys-認証器内のユーザー検証}

パスキーの画面で PIN を入力したからといって、その PIN をサービスへ送って照合しているとは限りません  
認証器の利用をローカルに許可する検証と、サービス側で公開鍵で認証応答を検証する処理を分けて考えます  
サービスが通常の応答から受け取る [UV](../reference/glossary.md#uv) は、ユーザー検証が行われた結果であり、PIN と指紋を見分ける名前ではありません  
[UP](../reference/glossary.md#up) は利用者の関与を示す別のフラグです [WebAuthn Level 3 §6.1](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-authenticator-data)

理解の補助として「鍵の制御 AND（PIN OR 生体によるローカル検証）」と描けます  
これはあらゆる認証器の内部を保証する式ではなく、異なる役割を整理する概念モデルです  
画面操作が一回でも、検証する要素が一つとは限りません  
逆に操作を二回繰り返しただけでは、多要素になるとは限りません  
実際の保証水準は、認証器、鍵の扱い、登録や回復の条件まで含めて判断します  
[UV のコラム](../columns/user-verification.md)で、結果から言える範囲を詳しく扱います

ここでは「サービスのアカウント」と「認証器がローカルに確認する利用者」の範囲にも注意します  
認証器が PIN を確認できたという結果だけで、サービスに登録した氏名や所属まで証明されるわけではありません  
サービスは登録済み資格情報との対応からアカウントを決め、そのアカウントの属性を別に管理します  
公的な本人確認の結果を保持するサービスであっても、その属性を得た手続きと、その後のパスキーによるログインは異なる段階です

また、画面を操作した本人が操作の意味を十分理解したかは、UV の真偽だけからは分かりません  
例えば本人がだまされて重要操作を承認する問題は、誰かが本人に代わって鍵を使う問題とは違います  
認証結果を「この利用者は表示されたあらゆる条件へ同意した」という意味まで広げないようにします  
同意や重要操作の内容をどう確認するかは、認証結果を受け取るアプリケーションの設計です

### 資格情報の同期と紛失時の回復 {#passkeys-資格情報の同期と紛失時の回復}

安全なログイン手段でも、端末を失くすと永久に使えなくなるなら、利用者は別の手段を求めます  
パスキーには、複数端末で利用できるよう同期するものと、特定のデバイスに結び付いたものがあります  
同期は機種変更の負担を減らす一方、同期先へ入る条件も信頼の一部になります [FIDO Alliance：Passkeys FAQ](https://fidoalliance.org/passkeys/)

同期型とデバイス固定型の違いは、ログイン画面よりも、資格情報をどこで使い続けられるかに現れます  
同期型は対応する別端末へ資格情報を引き継げますが、デバイス固定型はその資格情報が特定のデバイスを離れない方式です [FIDO Alliance：Passkeys FAQ](https://fidoalliance.org/passkeys/)

教材の利用者 A が、スマートフォンと予備のセキュリティキーを使う場合を考えます

| 用意する経路 | スマートフォンを失くした後に必要なこと |
| --- | --- |
| 別端末でも利用できる同期型の資格情報 | 同期先を利用できることや、新しい端末を参加させる条件を確かめる |
| スマートフォンだけにあるデバイス固定型の資格情報 | その資格情報以外のログイン・回復経路を使う |
| あらかじめ別の資格情報を登録した予備のキー | 予備のキーでログインし、紛失した資格情報の扱いを見直す |

最後の例は、同じ鍵を二台にコピーする設計ではなく、一人のユーザーに別々の資格情報を登録する設計です  
「複数端末で入れる」という結果だけで、同期と複数登録を同じものとして扱わないようにします  
また、予備を同じ鞄に入れていれば一緒に失くすため、入口が二つあることだけで紛失への備えが十分とも言えません

利用者 A が同じサービスへ三つの資格情報を登録しているなら、紛失した一つを無効にし、残りで利用を続ける設計が考えられます  
一方、一つの資格情報を複数端末へ同期している場合、サービス側でその資格情報の受入れを止めると、同じ資格情報を使う別端末からのログインにも影響します  
「スマートフォンを削除する」という画面の表現だけでは、端末を除外したのか、資格情報を無効にしたのかが不明確です  
サービスが管理する対象と、同期サービスが管理する対象を分けて、利用者へ説明する必要があります

この判断では、サーバーが観測できる情報の限界も確認します  
WebAuthn は資格情報のバックアップ可否やバックアップ状態を表すフラグを定義していますが、それを全端末の一覧だとは扱いません [WebAuthn Level 3 §6.1.3](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-credential-backup)

教材の設計で「紛失した端末だけを止める」と要件に書くなら、どの識別情報とどの管理機能で実現するのかまで確認します  
未確認なら、資格情報単位の無効化で何が止まり、何が残るかを説明するほうが正確です

例えば Apple の iCloud キーチェーンは、パスキーを利用者の端末間で同期します  
その保護には、通信の両端で暗号化・復号し、仲介サーバーには内容を読ませない [E2EE（End-to-End Encryption、エンドツーエンド暗号化）](../reference/glossary.md#e2ee) が使われています  
Apple の説明では、同期データは Apple のサーバーを経由しますが、Apple 自身も内容を読めない設計です [Apple Platform Security：iCloud Keychain security overview](https://support.apple.com/guide/security/icloud-keychain-security-overview-sec1c89c6f3b/web)

ログイン先に秘密鍵を渡さず署名で証明する仕組みと、端末間でその資格情報を暗号化して同期する仕組みが組み合わされています  
E2EE で同期内容を保護していても、新しい端末の参加や紛失時の回復を誰に許すかは重要な条件として残ります

スマートフォン紛失時の復帰条件も、認証経路の一部として設計します  
予備の認証器、別端末の資格情報、運営者への回復申請は、同じ働きをするとは限りません  
回復申請をメール一本で終え、その直後に全権限を与えるなら、攻撃者もその経路を狙えます  
そこで本教材では、回復の実装を省略しても「回復経路は存在しないので安全」とは評価しません  
提供前に決めるべき運用として残します

回復は、普段のログインと同じ画面を別の名前で用意することではありません  
NIST は、必要な認証器の制御を失った状態からアカウントを回復する手続きを扱い、回復後の新しい認証器の登録や通知も含めています [NIST SP 800-63B-4：Account Recovery](https://pages.nist.gov/800-63-4/sp800-63b.html)

教材の利用者 A が予備のキーを使える場合と、使える資格情報をすべて失った場合を比べます  
前者では既存の認証経路で A を確認し、新しい資格情報を追加する設計を採れます  
後者では、その確認に使う根拠自体を再構成しなければなりません  
同じ「ログインできない」という相談でも、利用できる証拠が異なるため、一律の手順にまとめると確認の強さを見失います

運営者が手作業で回復を許す案でも、その判断が信頼の一部になります  
誰が申請を承認でき、どの根拠を確認し、既存の連絡先へ何を知らせるかを決めます  
これらは資格情報を暗号化して保存することでは代替できない判断です  
暗号による保護と、誰に新しい入口を渡すかという判断を分けておくと、実装を省略した部分も見失わずに済みます

紛失時には、ログインのしやすさに加えて次の条件を確認します

- 失くした資格情報を無効にできるか
- ほかのセッションも終了すべきか
- 利用者にどこまで通知するか

同期基盤や回復システムをこの教材で自作することはせず、選んだ製品や運用の条件を別に確認します

### 代替の認証手段と権限 {#passkeys-代替認証経路と到達可能な権限}

サービス全体で「パスワード OR パスキー」を許す場合、先ほどの認証器内部の AND とは階層が違います  
パスキーを追加しても、パスワードでログインして同じ権限を得る経路は残ります  
したがって「新しい入口が強いから、古い入口の問題もなくなった」とは説明できません

とはいえ移行中にパスワードを残すこと自体を、一律に失敗と判断する必要もありません  
たとえば教材上の設計演習として、古い経路では基本的な閲覧まで、資格情報の追加や重要な設定変更では改めて確認を求める案を比較できます  
実際に採るなら、どの権限まで到達できるかを画面単位ではなくサーバー側で定義します  
弱い入口でログインした直後に強い資格情報を登録できるなら、入口の制限を迂回する道になり得るためです

到達できる権限を具体化すると、回復も評価しやすくなります  
以下はサービスを設計するときの比較案です

- 閲覧だけを許す代替ログインでは、資格情報の追加や回復先の変更を別の確認に分ける
- 登録済みの予備のキーで確認できた場合は、紛失した資格情報の削除や新しい資格情報の登録へ進める案を検討する
- すべての資格情報を失った場合は、回復の根拠を確認し、重要操作への復帰条件を別に定める

ここで、閲覧用の経路からメールアドレスを変更でき、そのメールだけで回復できるとしたらどうでしょうか  
資格情報を追加する画面を直接開けなくても、回復先の変更を経由して新しい鍵を登録できる可能性があります  
確認すべきなのは一つの画面の強さではなく、操作を順につないだ先で得られる権限です  
通知や待機時間を追加する案も考えられますが、それだけで回復申請者を認証できるわけではありません  
誰の何を根拠に復帰を許すかを決めたうえで、検知や取消しの機会を補助として組み合わせます

AND の成功確率を単純に掛け算することもしません  
二つの条件が同じ端末の侵害で同時に破られる可能性があるためです  
経路の図は、検証すべき条件を探す道具として使います

### OIDC と内部認証の接続 {#passkeys-oidc-と内部認証の接続}

パスキーの公開鍵を登録し、認証応答を検証するサービスは、この場面では [WebAuthn RP](../reference/glossary.md#webauthn-rp) です  
検証に成功したサービスは、対応する利用者のログイン状態を確立します  
このサービスが OIDC の OP でもある場合は、パスキーによる認証を OP 内部の方法として使い、OIDC RP は引き続き ID Token の issuer、audience などを検証します [OIDC Core §1.2](https://openid.net/specs/openid-connect-core-1_0.html#Terminology)  
WebAuthn RP と OIDC RP は同じ RP という略称を使いますが、頼る証拠と相手が異なります

本編の契約を守ったまま OP の入口を変えると、利用者の認証と、その結果を別サービスへ伝える責任を分離できます

### 確認問題 {#passkeys-確認問題}

**問い：パスキーを登録した利用者について、パスワードでログインする経路でも資格情報の追加を無条件に許してよいでしょうか**

::: details 解説
入口だけで判断せず、追加後に到達できる権限を見ます  
攻撃者が弱い経路から自分の鍵を登録できるなら、その後はパスキーでログインする経路から入れます  
登録前の再確認や回復ポリシーまで含めて設計する必要があります
:::

**問い：一回の指紋操作でログインできたら、単要素認証でしょうか**

::: details 解説
操作回数からは決まりません  
何の制御を証明し、どこでユーザー検証を行い、その結果をどう検証したかを説明します  
UV だけから具体的な検証方法や特定の保証レベルへの適合までは断定しません
:::
