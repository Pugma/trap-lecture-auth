# 認証方式の比較と運用

::: tip このページの目標

認証連携の方式を、提供側が定める契約と信頼関係から比較し、OP が伝えるログアウトの範囲と運用上の責任を説明できるようになる

:::

::: info このページの要点

- **独自方式との対応**：サービス固有の方式を OIDC と対応付け、提供側が定める契約と保証範囲を確認する
- **方式の比較**：SAML・JPKI などとの目的や信頼関係の違いを整理する
- **ログアウト連携**：OP から RP へ終了を伝える経路と、終了させる状態の範囲を区別する
- **運用**：障害、記録など、プロトコル以外に残る提供側の設計を確認する

:::

OIDC の目的と検証を踏まえ、他の方式と運用上の判断を比較します

認証に関わる方式を比べるには、何を証明し、その結果を誰が使うのかを揃える必要があります  
方式の比較とともに、提供側がそれぞれの方式で守る範囲と、運用で引き受ける責任を確認します  
まずサービス固有の方式を OIDC と対応付け、次に SAML や JPKI など目的の異なる方式と比べます  
RP 側のログイン判定、セッション、GitHub OAuth Apps を使う具体例は、コラム「[OIDC RP の実装](../columns/rp-implementation.md)」で扱います

## サービス固有のログインと OIDC {#oauth-login}

OAuth を利用したサービス固有のログインも、必要な契約と検証を補えば構成できます  
例えば GitHub OAuth Apps の Web application flow は、ID Token ではなく、GitHub 固有のユーザー情報 API と識別子の契約を使います [GitHub Docs：Authorizing OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#web-application-flow)  
こうした方式では、提供側がユーザー情報 API の意味や安定したアカウント ID を独自に定め、RP はその契約を提供元ごとに調べて検証します  
OIDC は、そうした認証結果の伝達・検証を提供元を越えて共通化します  
RP 側から見た手順は、コラムの[GitHub OAuth Apps によるログイン](../columns/rp-implementation.md#rp-github-oauth-apps)で扱います

### 独自方式と OIDC の対応 {#oidc-独自方式と-oidc-の対応}

GitHub の例と OIDC は、返ってくるデータの形式こそ違いますが、RP 側が説明しなければならない判断には共通部分があります  
提供側は、RP がそれぞれの判断をできるだけの契約を定め、公開する必要があります  
独自方式を読むときも、まず「どの API を呼ぶか」からではなく、その API の成功で何が分かるかを考えます

| 判断したいこと | サービス固有の方式で提供側が定める契約 | OIDC で対応する箇所 |
| --- | --- | --- |
| 誰の情報か | ユーザー情報 API と安定したアカウント ID の意味 | `iss` と `sub`、必要なら UserInfo |
| 自分のアプリの処理か | 登録したアプリ、コード交換、取得したトークンの対応 | client の登録、コード交換、ID Token の `aud` |
| 開始したログインか | state、PKCE、ブラウザセッションと開始した要求の対応 | OAuth の保護に加え、送信した `nonce` の照合 |
| どの認証の結果か | サービスが返す認証情報とその保証範囲 | `auth_time`、`max_age`、`prompt` など |
| 何を許可してよいか | アプリ自身の利用条件とリソースへの権限 | 同じく RP・API の判断として残る |

この対応表は、独自 API の各値を OIDC の Claim と同じ意味に読み替えてよいという表ではありません  
例えばサービス独自の「最終アクセス時刻」を `auth_time` 相当と扱えるかは、その値の定義次第です  
名前や日時の形式が似ていても、どの出来事で更新されるかが異なれば同じ判断には使えません

#### 応答の信頼性と保証範囲 {#oidc-応答の信頼性と保証範囲}

仮に、あるサービスが自分の Access Token に対応する利用者の ID と表示名だけを返すとします  
RP が正しい接続先へ TLS で問い合わせてその応答を受け取れたなら、通信先から返された情報という根拠はあります  
しかし、その中にない「5分以内に再認証した」という事実を、応答の到着時刻から補うことはできません

この場合、RP が必要とするのが通常のアカウント識別だけなのか、重要操作に必要な認証の鮮度までなのかで、採用できる範囲が変わります  
契約が提供しない保証を必要とするなら、別の機能や手順を使うか、その操作を許可しないという判断が必要です  
不足している Claim を既定値で埋めてしまうと、データ形式はそろっても保証の内容はそろいません  
提供側から見ると、返さない保証を RP は補えないため、どの値がどの出来事で更新され、どの保証を提供しないかを契約として示す必要があります

OIDC が共通化する利点は、こうした意味を仕様の節へ戻って確認できることです  
ただし、OIDC の名前が付いていれば、あらゆる認証条件が常に要求・返却されるわけではありません  
どの条件を RP が要求し、OP が何を返し、RP がどこまで検証するかを選んで結び付けます [OIDC Core §2・§3.1.2.1](https://openid.net/specs/openid-connect-core-1_0.html#IDToken)

RP が検証した外部アカウントを内部ユーザーへ対応付け、自分のセッションを作るまでの判断は、コラムの[RP のログイン判定](../columns/rp-implementation.md#rp-login-decision)で扱います

## 認証連携方式の比較と運用 {#comparison}

### SAML Web Browser SSO との比較 {#comparison-saml-web-browser-sso-との比較}

[SAML](../reference/glossary.md#saml) の Web Browser SSO では、[Identity Provider](../reference/glossary.md#idp)（IdP）が利用者の認証について伝え、[Service Provider](../reference/glossary.md#sp)（SP）がそれを受け取ります  
[Assertion](../reference/glossary.md#assertion) が主張を運び、[Protocol](../reference/glossary.md#saml-components) が要求・応答を定め、Binding が HTTP などへの載せ方を定めます  
Profile は用途に応じてこれらを組み合わせます  
[OASIS SAML Technical Overview §4–5](https://docs.oasis-open.org/security/saml/Post2.0/sstc-saml-tech-overview-2.0.html)

OIDC の OP/RP と SAML の IdP/SP は、認証結果を伝える側と利用する側という観点で対応を考えられます  
ただし、パラメータや検証規則が一対一で置換できるわけではありません  
SAML は XML、OIDC の ID Token は JWT だからどちらかが安全、という結論も出せません  
宛先、発行者、時間条件、要求との結合、鍵の信頼を正しく扱う必要は共通します

| 観点 | OIDC の教材例 | SAML Web Browser SSO |
|---|---|---|
| 認証結果の提供側 / 利用側 | OP / RP | IdP / SP |
| 主張を運ぶもの | ID Token | Assertion |
| 認証連携の契約 | Core と関連仕様 | Core・Bindings・Profiles 等 |
| 公開情報の交換 | Provider Configuration / JWKS | Metadata による構成情報の交換 |
| 検証時の問い | この issuer が自分向けに発行した結果か | 信頼する IdP の結果で、対象 SP・条件に合うか |

SAML を新たに実装する場合には、この比較だけで要件を決めず、該当する Profile、Binding、Core の規範に戻ります  
本教材では SAML IdP を作りません  
比較の目的は、自分が既に学んだ検証の問いを、別方式を読む足場にすることです

例えば「署名が正しい Assertion を取得できた」という説明だけでは、どの SP に向けたものか、いつまで使えるか、どの要求に対応するかが分かりません  
OIDC で署名だけを見て ID Token を受け入れなかったのと同様に、受信した文書の正当性と、この場面で利用できることを分けて調べます  
具体的な拒否条件は選んだ SAML Profile に従います

#### SAML と OIDC のフローの対応 {#comparison-saml-と-oidc-のフローの対応}

SAML Web Browser SSO のうち、SP から開始して HTTP Redirect と HTTP POST を使う例を見ます  
利用者が SP の画面を開き、まだ SP のセッションがないところから始まります

1. SP が認証要求を用意し、ブラウザを IdP へ転送する
2. IdP が利用者の認証を行うか、条件に合う既存の認証状態を使う
3. IdP が SAML Response を用意し、ブラウザ経由の POST で SP の受信先へ送る
4. SP が応答と Assertion の条件を検証し、自分のセッションを確立する

これは SAML のすべての経路ではなく、一つの Binding の組合せです  
別の経路に Artifact を使う方式などがあるため、「SAML では必ず認証結果の全文を同じ方法で返す」と一般化しません [OASIS SAML Technical Overview §5.1.2–§5.1.3](https://docs.oasis-open.org/security/saml/Post2.0/sstc-saml-tech-overview-2.0.html)

OIDC の教材例では、ブラウザはコードを運び、RP のバックエンドがトークンを取得しました  
上の SAML の例では、認証結果を含む応答がブラウザを通ります  
通信経路が違っても、ブラウザから届いた値を無条件に信用せず、信頼する発行者、受信先、要求との対応、時間条件を検証するという問いは共通です  
実装の比較では、XML と JSON の見た目よりも、どの経路にどの証拠が現れ、誰が検証するかを図や通信記録から読み取ります

#### 方式の変換と接続先の確認 {#comparison-方式選定の接続条件}

方式を変換する仲介サービスを置く場合には、元の認証結果を検証し、新しい受信者向けに結果を発行する責任が増えます  
元の署名付き文書の値をコピーするだけでは、別方式の契約を満たしたことにはなりません  
RP が接続先の方式を選ぶときの確認事項は、コラムの[接続先の方式の確認](../columns/rp-implementation.md#rp-connection-requirements)で扱います

### 公的個人認証サービス（JPKI） {#comparison-公的個人認証サービス-jpki}

[公的個人認証サービス](../reference/glossary.md#jpki)（JPKI）は、電子証明書を利用してオンラインの申請やログインなどで本人確認を行う仕組みです  
ここでは、マイナンバーカードに搭載される二種類の電子証明書の用途を区別します  
[J-LIS：公的個人認証サービス](https://www.j-lis.go.jp/jpki/cms_18.html)

- **署名用電子証明書**：電子文書への署名に使い、本人が作成・送信した文書であることの確認に用います
- **利用者証明用電子証明書**：インターネットサイトなどへのログイン時に、利用者本人であることの確認に用います

「電子署名」と「ログイン」が同じカードを使っていても、証明する対象は異なります  
同様に JPKI、OAuth、OIDC、WebAuthn も、同じ位置の代替方式ではありません  
OAuth は API アクセスの委譲、OIDC は認証結果の連携、WebAuthn は Web アプリケーションでの公開鍵資格情報の登録・認証を扱います  
JPKI を比較するときには、これらに加えて、電子証明書の発行元と証明する対象を確認します

#### JPKI の発行と鍵管理

電子署名を検証できることだけでは、その鍵を誰へ結び付けてよいかは決まりません  
JPKI では、電子証明書の新規発行・更新や暗証番号の再設定をオンラインだけで完結させると、第三者が本人になりすまして電子申請できるおそれがあるため、市区町村の窓口で厳格な本人確認を行う仕組みにしています  
これは、証明書と利用者の対応付けを作り直す場面の信頼を、対面の本人確認で支える設計です [JPKI：電子証明書に関するご質問](https://www.jpki.go.jp/faq/digital_id.html)

秘密鍵と電子証明書は、耐タンパ性を持つマイナンバーカードの IC チップへ記録されます  
耐タンパ性は、カードを読み取っただけで秘密鍵を複製できないようにするための前提です  
したがって JPKI を理解するときは、公開鍵で署名を検証する計算だけでなく、鍵を格納する場所、鍵を使う操作の保護、証明書の発行・更新・失効という運用まで追う必要があります [JPKI：マイナンバーカードに関するご質問](https://www.jpki.go.jp/faq/iccard.html)

ここで対面の本人確認やカードの保護が必要なのは、WebAuthn、OAuth、OIDC のすべてに同じ手順を要求するためではありません  
各方式で、誰が鍵とアカウントの対応を登録し、資格情報をどう保護し、紛失・更新・失効をどう扱うかという問いを比較するための例です

本教材では JPKI の接続実装は扱いません  
利用場面や導入の全体像は、[デジタル庁の JPKI 紹介](https://www.digital.go.jp/policies/mynumber/private-business/jpki-introduction)を参照できます

### セッションと終了の範囲 {#comparison-認証連携と-cookie-セッション}

Cookie [セッション](../reference/glossary.md#session)は、ブラウザの次の要求をアプリ内の状態へ結び付ける仕組みです  
OIDC による認証連携を採用しても、OP の認証状態や RP のログイン状態を保持するために使います  
Cookie と OIDC は、同じ位置の代替案として比較するものではありません

終了処理も同様です  
RP のローカルログアウト、OP のセッション終了、Access Token の失効、Refresh Token の失効は、それぞれ対象が異なります  
本教材で説明したトークンを更新する権限の失効を、全アプリからの一斉ログアウトの完成と呼ばないようにします  
RP のセッション管理と、RP のセッションだけを終了したときに残る状態は、コラムの[RP のセッションとログアウト](../columns/rp-implementation.md#rp-session)で扱います

OIDC には、RP から OP へログアウトを求める RP-Initiated Logout という別仕様があります  
ログインに使う Core の実装だけで、すべての RP や API の終了まで完了するとは扱いません [OIDC RP-Initiated Logout 1.0 §2](https://openid.net/specs/openid-connect-rpinitiated-1_0.html#RPLogout)

#### RP 間のログアウト連携 {#comparison-rp-間のログアウト連携}

OP から RP へログアウトを伝える場合も、通知を誰が運ぶかによって必要な実装が変わります  
[Front-Channel Logout と Back-Channel Logout](../reference/glossary.md#logout-channels) は、どちらも RP に終了を伝えるための仕様ですが、前者はブラウザを介し、後者は OP から RP へ直接通信します [OIDC Front-Channel Logout §2](https://openid.net/specs/openid-connect-frontchannel-1_0.html#RPLogout)、[Back-Channel Logout §1](https://openid.net/specs/openid-connect-backchannel-1_0.html#Introduction)

バックエンドへ直接通知すれば、RP はその要求からブラウザの Cookie をそのまま読むことはできません  
そのため、通知された主体やセッションを、RP が保持している状態へ対応付けて終了する仕組みが必要です  
Back-Channel Logout では、OP が終了についての Claims を持つ署名付きの Logout Token を発行して送り、RP が所定の条件を検証します [Back-Channel Logout §2.4–§2.7](https://openid.net/specs/openid-connect-backchannel-1_0.html#LogoutToken)

同じ JWT でも、ID Token は認証結果、Logout Token は終了についての通知です  
どちらも署名が正しいから共通の処理へ流せる、とすると用途の違いを失います  
この例からも、形式だけでなく受け付ける場所と検証規則を用途ごとに決める必要が分かります

教材で終了通知を設計するとしたら、「通知を送った」「RP が受け取った」「対象のセッションを無効にした」を別の観測として記録します  
一つの RP へ届かないとき、他の RP で何が完了し何が残っているかも追える必要があります  
ここでは通知経路の設計を比較するだけで、これらのログアウト仕様を教材 OP/RP に実装済みとはしません

### 運用上の設計事項 {#comparison-運用上の設計事項}

本書では、認証連携の仕組みを状態と拒否条件へ対応付けて説明しました  
利用者二人、単一 issuer、事前登録 client という範囲は、その対応を追うための選択です  
実際の運用には、アカウント回復、鍵の更新と漏えい対応、監査記録、負荷制御、障害対応、バックアップ、依存関係の更新などの判断が残ります

この節ではこれらの実装を追加せず、運用前に判断する項目として整理します

- 署名鍵が使えなくなった場合、新しいログインをどう扱うか
- 保存先で障害が起きたときに、コードを使用済みにする処理を成功扱いしていないか
- 退会した利用者の更新権限を、どこで止めるか
- 秘密を露出させずに、ログから障害を調査できるか

これらの判断は、ライブラリの採用だけでは決まりません

#### 障害と拒否の区別 {#comparison-障害と拒否の区別}

ログインできないという利用者の報告に対しては、どこで成立条件を満たせなくなったかを切り分けます  
以下は運用設計を考えるための仮定で、実際の障害記録ではありません

| 観測したこと | 最初に調べること | してはいけない対処 |
| --- | --- | --- |
| OP のログイン画面へ到達しない | 名前解決、通信経路、サービスの稼働 | 別の未確認 issuer への自動的な切替え |
| コード交換の結果が分からない | 保存の確定と HTTP 応答の到達 | 同じコードを未使用へ戻すこと |
| ID Token の検証で未知の鍵が見つかる | 信頼する取得先の JWKS と鍵の更新 | 署名検証そのものの省略 |
| API で閲覧が拒否される | scope と対象のリソースのアクセス権 | ログイン済みという理由だけでの許可 |

たとえば OP と通信できない障害なら、新しいログインができない一方、既存の RP セッションがどう扱われるかは別の設計です  
すべてのセッションを即座に終えるのか、設定した期限まで使えるのかは、RP が提供する機能と要求される保証に応じて決めます  
障害が発生してから場当たり的に検証を緩めると、通常時とは異なる認証経路を作ることになります

#### ログの記録項目と秘密情報 {#comparison-ログの記録項目と秘密情報}

原因をたどれる記録には、時刻、処理の段階、成功・拒否・内部処理のエラー、使用した設定の版などが役立ちます  
教材なら、コード交換が失敗した理由と、その後にトークンの発行記録が残ったかを、処理単位の内部 ID で対応付ける案が考えられます  
その ID はログを関連付けるためのものであり、認証を通す資格情報にはしません

調査を容易にするために要求を丸ごと記録すると、ログが新しい資格情報の保管場所になってしまいます  
OWASP は、Access Token、認証用パスワード、暗号鍵などをそのまま記録しないことを挙げています [OWASP Logging Cheat Sheet：Data to exclude](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html#data-to-exclude)  
教材でも Cookie、client secret、コードやトークンの値を記録しなくても追える構成を考え、記録の閲覧権限と保持期間を決めます

利用者に返す文言と、運用担当者が読む詳細も役割が異なります  
利用者にはやり直すべきか時間を置くべきかを伝え、内部の検証値や秘密を表示しません  
運用記録にはどの条件で止まったかを残し、同じ「失敗」の一語で通信障害と権限の不足による拒否をまとめないようにします

### 設計レビュー {#comparison-設計レビュー}

OP・AS・API を作る側として、チャットサービスのログインから API 呼出しまでを、次の観点で確認します

1. 受け取った要求の state を応答へ返し、PKCE challenge と nonce を発行するコードと ID Token へどう結び付けるか
2. OP が認証した利用者と、許可した client・scope をどこで結ぶか
3. コードを誰が一度だけ消費できるか
4. RP が照合する `iss`・`aud`・`nonce`・`auth_time` などを、何を根拠に ID Token へ載せるか
5. API が token の権限とチャンネルへのアクセス権をどう確認するか
6. 更新・再利用・失効によって、どの状態が変わるか

RP 側で同じ流れを確認する観点は、コラムの[RP のログイン判定](../columns/rp-implementation.md#rp-login-decision)で扱います

**確認問題:** 別の実装の RP とのログインが一度成功し、suite の一部が成功しました  
「この認証基盤は本番向けに安全」と言ってよいでしょうか
