# パスキーによる E2EE の設計

::: tip このページの目標

E2EE が誰から何を隠す仕組みかを説明し、パスキーの PRF 拡張から得た鍵で、サーバーに読めないデータを設計できるようになる

:::

::: info このページの要点

- **目的と範囲**：TLS は通信路を守るが、E2EE は受け取ったサーバー自身にも内容を読ませない。メタデータや端末は守らない
- **鍵の入手**：WebAuthn の `prf` 拡張で、パスキーごとに決まる 32 バイトの値を得て、そこから暗号化の鍵を導く
- **ログインとの違い**：ログインの署名はサーバーが検証するが、PRF の出力はブラウザの中だけで使い、サーバーへ送らない
- **鍵の階層と回復**：データ鍵をパスキーごとに包んで保存する。すべてのパスキーを失うと、運営者でも復号できない
- **Web アプリの限界**：鍵を扱うコード自体をサーバーが配信するため、配信されるコードの信頼が前提として残る

:::

[おまけ編①](../chapter-ex1/passkeys-background.md)では、パスキーをログインの手段として扱いました  
このページでは同じパスキーを、データを暗号化する鍵の入手先として使います  
パスワードから鍵を導く方式もありますが、この教材ではパスキーを使う方式だけを扱います  
後半の[実習](../practice/e2ee.md)で、鍵の導出から復号までを手元で確かめます

## E2EE の目的と範囲 {#e2ee}

### TLS との違い {#e2ee-tls-との違い}

Web サービスにメモを保存する場面を考えます  
ブラウザとサーバーの間は HTTPS で接続されるので、通信路の途中で内容を読まれることはありません  
しかしサーバーは受け取ったメモを復号して処理し、データベースへ保存します  
運営者、データベースのバックアップ、侵入した攻撃者は、保存された内容を読める可能性があります

[E2EE（End-to-End Encryption、エンドツーエンド暗号化）](../reference/glossary.md#e2ee)は、この「受け取ったサーバー」にも内容を読ませない設計です  
暗号化と復号を両端の利用者の端末だけで行い、サーバーは暗号文を中継・保存するだけにします  
TLS が守るのは端末とサーバーの間の区間であり、E2EE が守るのはサーバーを含めた経路全体です

どこを「端（end）」とするかは設計ごとに決めます  
メッセージアプリなら送信者と受信者の端末、パスキーの同期なら同じ利用者の複数の端末が端です  
E2EE の定義を標準化する提案も IETF に出されましたが、RFC にはならずに失効しています [draft-knodel-e2ee-definition-11](https://datatracker.ietf.org/doc/draft-knodel-e2ee-definition/)  
そのため「E2EE です」という説明を読んだときは、端がどこで、誰が読めないのかを具体的に確認します

### 守れるものと守れないもの {#e2ee-守れる範囲}

E2EE で隠せるのは、暗号化したデータの内容です  
次のものは、内容を暗号化しても、それだけでは守れません

| 対象 | E2EE だけでは守れない理由 |
| --- | --- |
| メタデータ | 誰が、いつ、どれくらいの大きさのデータを保存・送信したかは、サーバーが処理のために見る |
| 利用者の端末 | 復号した内容は端末に表示されるので、端末を乗っ取られれば読まれる |
| 配信されるコード | Web アプリでは、暗号化するコードもサーバーが配信する（[後述](#e2ee-web-limitations)） |
| 暗号文の改変・入替え | 暗号化の方式によっては、読めなくても書き換えや差し替えはできる |

最後の行は、改変を検知できる暗号化方式を選ぶことで対策します  
この教材では、暗号化と同時に改変を検知する AES-GCM を使い、暗号文と「どのメモの暗号文か」という情報を結び付けます  
実習では、暗号文の1ビットを変えたときと、別のメモの暗号文を差し替えたときに、復号が失敗することを確かめます

## パスキーから鍵を得る {#e2ee-prf}

### 鍵をどこから得るか {#e2ee-鍵の入手先}

E2EE では、サーバーが知らない鍵を利用者の端末で用意する必要があります  
しかし端末の中で乱数から鍵を作るだけでは、別の端末やブラウザの再インストール後に同じ鍵を使えません  
そこで、利用者が持ち歩ける何かから、毎回同じ鍵を導き出す方法が必要になります

パスワードから鍵を導く方式は、その代表例です  
ただしこの方式では、推測されやすいパスワードを選ぶと鍵も推測されやすくなり、おまけ編①で扱ったパスワードの課題がそのまま残ります  
この教材では、既にログインに使っているパスキーから鍵を得る方式を扱います

### PRF 拡張 {#e2ee-prf-拡張}

WebAuthn の `prf` 拡張は、資格情報に結び付いた擬似乱数関数（PRF）の出力を RP が得るための拡張です [WebAuthn Level 3 §10.1.4](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#prf-extension)  
RP が入力の値を渡すと、認証器はその資格情報に固有の関数で 32 バイトの出力を返します  
同じ資格情報に同じ入力を渡せば同じ出力が得られ、別の資格情報では別の出力になります  
仕様自身も、利用者のデータを暗号化する鍵に使う例を、この拡張の動機として挙げています

仕様上の要点は次のとおりです

- ブラウザは、RP が渡した入力をそのまま認証器へ渡さず、`"WebAuthn PRF"` という文字列と合わせてハッシュ化してから渡す  
  そのため、同じ認証器の別の用途向けの出力を、Web ページから直接求めることはできない
- CTAP の `hmac-secret` 拡張の上に実装される場合、ユーザー検証（UV）を行ったときの関数が使われる
- 登録時に出力が返るとは限らない。返らなければ、認証の手続きをもう一度行って出力を得る

ブラウザ側の呼び出しは、おまけ編①の `navigator.credentials.get()` に拡張の入力を加える形になります  
以下は説明用の抜粋で、実機では試験していません

```ts
const credential = await navigator.credentials.get({
  publicKey: {
    challenge,             // サーバーから受け取ったログイン用の challenge
    rpId: 'example.org',
    allowCredentials,      // 登録済みの資格情報
    userVerification: 'required',
    extensions: {
      prf: {
        // 資格情報ごとの入力。サーバーに保存した値を使う
        evalByCredential: { [credentialIdBase64url]: { first: prfInput } },
      },
    },
  },
}) as PublicKeyCredential

const prfOutput = credential.getClientExtensionResults().prf?.results?.first
// prfOutput はサーバーへ送らず、このページの中で鍵の導出だけに使う
```

`prf` 拡張への対応は、ブラウザ・OS・認証器・パスキーの保存先の組み合わせで異なります  
採用する場合は、登録時の `enabled` と認証時の `results` を確かめ、対応していない環境での扱いを決めておきます

### ログインと復号は別の処理 {#e2ee-ログインと復号}

PRF の出力は、ログインと同じ手続きの中で得られますが、ログインとは役割が異なります

| 処理 | 使う値 | 値を扱う場所 |
| --- | --- | --- |
| ログイン | 認証器の署名 | サーバーが公開鍵で検証する |
| 復号 | PRF の出力から導いた鍵 | ブラウザの中だけで使い、サーバーへ送らない |

ログインでは、サーバーは公開鍵だけで署名を検証でき、秘密を受け取る必要がありません  
復号の鍵も、同じようにサーバーが知らなくてよい値です  
もしブラウザのコードが PRF の出力をサーバーへ送れば、サーバーは鍵を導けるので、E2EE ではなくなります

逆に、ログインに成功したからといって、そのセッションで復号できるとは限りません  
パスワードなど別の経路でログインした場合や、PRF に対応しない環境では、ログイン状態があっても鍵はありません  
「ログイン済み」と「復号できる」を別の状態として画面とサーバーの両方で扱います

## 鍵の設計 {#e2ee-鍵の設計}

### データ鍵と鍵の包み直し {#e2ee-鍵の階層}

PRF の出力で直接すべてのデータを暗号化すると、問題が起きます  
おまけ編①で見たように、一人の利用者が複数のパスキーを登録することは推奨されています [WebAuthn Level 3 §13.4.6](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-credential-loss-key-mobility)  
しかし PRF の出力は資格情報ごとに異なるので、パスキーの数だけデータを暗号化し直すことになります

そこで鍵を二段に分けます

1. **データ鍵**：メモを暗号化する鍵。利用者ごとに一つを乱数で作る
2. **鍵暗号化鍵**：パスキーの PRF 出力から導いた鍵。データ鍵を暗号化する（包む）ためだけに使う

サーバーには、パスキーごとに包んだデータ鍵（この教材では **鍵スロット** と呼びます）と、暗号化したメモを保存します  
パスキー A でも B でも、自分の鍵スロットを開ければ同じデータ鍵が得られ、同じメモを復号できます

```text
パスキー A ──PRF──▶ 鍵暗号化鍵 A ──開く──▶ 鍵スロット A ─┐
                                                          ├─▶ データ鍵 ──▶ メモの暗号文
パスキー B ──PRF──▶ 鍵暗号化鍵 B ──開く──▶ 鍵スロット B ─┘
```

この構成から、次のことが分かります

- **パスキーの追加**：新しい鍵スロットを作るには、既存のパスキーでデータ鍵を開いてから、新しいパスキーの鍵で包み直す  
  サーバーはデータ鍵を知らないので、サーバーだけではパスキーを追加できない
- **パスキーの削除**：鍵スロットを削除すれば、そのパスキーでは開けなくなる  
  ただし、そのパスキーで既にデータ鍵を取り出した端末があれば、データ鍵自体は知られている。これも防ぐには、新しいデータ鍵を作ってすべてのデータを暗号化し直す
- **スロットの差し替え**：鍵スロットを暗号化するときに資格情報の ID を結び付けておくと、別のパスキーのスロットとして流用されたときに検知できる

### 同期と回復 {#e2ee-同期と回復}

同期型のパスキーでは、同じ資格情報が複数の端末で使えます  
仕様は PRF を資格情報の寿命の間ずっと結び付けるものとしているので、同期した資格情報でも同じ入力から同じ出力が得られることが前提になります [WebAuthn Level 3 §10.1.4](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#prf-extension)  
ただし、同期先が `prf` に対応しているかは製品ごとに確認が必要です

回復は、おまけ編①のログインの回復より厳しい条件になります  
ログインの回復では、運営者が本人を確認して新しいパスキーの登録を許せました  
しかしデータ鍵を包んでいるのはパスキーだけなので、すべてのパスキーを失うと、運営者にもデータ鍵を取り出す方法がありません  
これは E2EE の欠点ではなく、「運営者にも読めない」ことの裏返しです

備えとしては、予備のセキュリティキーを登録して鍵スロットを増やす方法や、印刷した回復用の鍵で別の鍵スロットを作る方法が考えられます  
どちらを採るにしても、「ログインは回復できたが、データは戻らない」状態がありえることを、利用者へ事前に説明します  
Apple の iCloud キーチェーンの説明も、同期に新しい端末を加える条件を E2EE の設計の一部として扱っています [Apple Platform Security：Secure keychain syncing](https://support.apple.com/guide/security/secure-keychain-syncing-sec0a319b35f/web)

## Web アプリの限界 {#e2ee-web-limitations}

ここまでの設計は、ブラウザで動くコードが正しいことを前提にしていました  
しかし Web アプリでは、PRF の出力を受け取り、鍵を導き、暗号化するコード自体を、読ませたくない相手であるサーバーが配信します  
サーバーが悪意を持つか乗っ取られれば、PRF の出力を送信するコードに差し替えられ、利用者はそれに気付けません

WebAuthn の仕様も、RP の origin で悪意のあるコードが動けば、WebAuthn のあらゆる保証が失われうると注意しています [WebAuthn Level 3 §13.4.8](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-code-injection)  
第三者のスクリプトを減らし、Content Security Policy で実行できるコードを制限することが推奨されています  
WhatsApp Web では、配信されたコードが公開された版と一致するかを確かめるブラウザ拡張 Code Verify が提供されています [Meta：Code Verify](https://engineering.fb.com/2022/03/10/security/code-verify/)

つまり Web アプリの E2EE は、「サーバーを信頼しなくてよい」仕組みではありません  
保存されたデータを後から読まれる危険は減らせますが、配信されるコードの信頼は前提として残ります  
設計を説明するときは、何を守れて、何が守れないかを分けて書きます

## 発展：他の人との共有 {#e2ee-共有}

このページでは、端をすべて同じ利用者の端末としました  
他の人とデータを共有する、つまりメッセージアプリのような E2EE では、相手の公開鍵で暗号化します  
ここで新しい問題が生じます  
サーバーが渡した公開鍵が、本当にその相手のものかをどう確かめるかです

これは、おまけ編①の「どのアカウントにその鍵を登録したか」と同じ構造の問題です  
サーバーが攻撃者の公開鍵を相手のものとして渡せば、暗号化は正しく行われても、攻撃者が読めてしまいます  
対策として、利用者同士で鍵の指紋を見比べる方法や、サーバーが配った公開鍵を後から監査できるように記録する Key Transparency があります [Meta：Deploying key transparency at WhatsApp](https://engineering.fb.com/2023/04/13/security/whatsapp-key-transparency/)、[Apple：iMessage Contact Key Verification](https://security.apple.com/blog/imessage-contact-key-verification/)

また、メッセージアプリでは、鍵が後から漏れても過去のメッセージを読まれないように、メッセージごとに鍵を更新します  
代表的な仕様として、Signal の [Double Ratchet](https://signal.org/docs/specifications/doubleratchet/) や、グループ向けの [MLS（RFC 9420）](https://www.rfc-editor.org/rfc/rfc9420.html)があります  
この教材ではこれらを扱いませんが、E2EE を自作したくなったときは、まずこうした既存の仕様と実装を調べてください

## 確認問題 {#e2ee-確認問題}

**問い：HTTPS で通信し、データベースも暗号化しているサービスは E2EE と言えるでしょうか**

::: details 解説
言えません  
HTTPS は通信路を、データベースの暗号化は保存媒体を守りますが、どちらもサーバーが復号できる鍵を持っています  
E2EE と呼ぶには、サーバーが鍵を持たず、内容を読めない設計である必要があります
:::

**問い：ブラウザで PRF の出力を得たあと、「サーバーで鍵を導出したほうが実装が楽」なので、出力をサーバーへ送る設計は E2EE でしょうか**

::: details 解説
E2EE ではありません  
PRF の出力を受け取ったサーバーは、同じ手順でデータ鍵を取り出せます  
通信が HTTPS でも、受け取った相手がサーバーである以上、サーバーに読ませない性質は失われます
:::

**問い：利用者がパスキー B を紛失したので、B の鍵スロットを削除しました。これで B を拾った人はメモを読めなくなったと言えるでしょうか**

::: details 解説
これから B でログインしてスロットを開く経路は止まります  
しかし B で既にデータ鍵を取り出した端末が攻撃者の手元にあれば、データ鍵は知られています  
その可能性を消すには、新しいデータ鍵を作ってメモを暗号化し直し、残ったパスキーで鍵スロットを作り直します
:::
