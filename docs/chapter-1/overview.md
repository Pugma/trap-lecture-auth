# 認証・認可とは

::: tip このページの目標

認証と認可がそれぞれ何を判断するかを説明し、認証の成功と操作の許可を区別できるようになる

:::

::: info このページの要点

- **認証**：提示された証拠を確かめ、どの主体として扱えるかを確認する
- **認可**：その主体に、対象へのどの操作を許可するかを決める
- **両者の関係**：認証に成功しても、すべての操作が許可されるわけではない

:::

認証と認可は、システムへのアクセスを扱う異なる機能です

この教材で扱う OAuth と OIDC の通信は HTTP(S) を前提にします  
OAuth 2.0 は HTTP で使うために設計された仕様で、HTTP 以外のプロトコル上での利用は仕様の対象外です [RFC 6749 §1](https://www.rfc-editor.org/rfc/rfc6749.html#section-1)  
ブラウザのリダイレクトや HTTP の endpoint を使う流れを扱い、gRPC を含む RPC の設計は扱いません

<span id="definitions"></span>

## 認証 {#definitions-認証}

[認証](../reference/glossary.md#authentication)は、主体が主張する識別情報を、提示された証拠に基づいて検証することです  
ここでいう主体は、操作を行う利用者やアプリケーションを指します  
ユーザー認証なら、「どのアカウントの利用者として扱えるか」を確認します

身近な例では、受付で「あなたは誰ですか」と尋ね、提示された会員証の写真と本人を照合する場面に似ています  
名前を聞くだけでなく、その人を名乗った会員として扱ってよいかを確かめています  
Web サービスでは、この問いが「あなたはどのアカウントの利用者ですか」に対応します

ユーザー名を入力するだけでは、そのアカウントを指定したことしか分かりません  
例えばパスワード認証では、登録された秘密を知っていることを検証し、アカウントとの対応を確認します  
名前を指定することと、その名前で扱ってよい証拠を示すことは別です [NIST SP 800-63B-4 §1](https://pages.nist.gov/800-63-4/sp800-63b.html#sec1)

認証に成功しても、実名や現実の所属まで確認されたとは限りません  
何を確認できたかは、そのアカウントの登録方法と、採用した認証方法によります

### 認証要素

認証に使う証拠の性質を、[認証要素](../reference/glossary.md#authentication-factor)と呼びます  
代表的な区分は次の三つです

| 要素 | 意味 | 例 |
| --- | --- | --- |
| 知識（something you know） | 本人が知っている秘密 | パスワード、PIN |
| 所持（something you have） | 本人が持ち、使用を制御できるもの | セキュリティキー、認証に使う端末 |
| 生体（something you are） | 本人の身体的な特徴など | 指紋、顔の特徴 |

ここでの「所持」は、物の所有権ではなく、認証に必要なものを使用できることを指します  
パスワードやパスキーという具体的な認証方式と、知識・所持・生体という要素の分類は別です  
一つの方式が複数の要素を組み合わせることもあり、詳しくはパスキーの説明で扱います [NIST SP 800-63B-4：認証要素の定義](https://pages.nist.gov/800-63-4/sp800-63b.html#def-authentication-factor)

## 認可 {#definitions-認可}

[認可](../reference/glossary.md#authorization)は、アクセス制御の方針に従い、主体に対するリソースへのアクセスや操作の許可を決めることです  
リソースとは、文書やデータなど、アクセスの対象になるものを指します  
「誰が、何に対して、どの操作をできるか」が判断の対象です

乗車券の確認は、認可に近いたとえです  
例えば、名前の記載がない切符を提示し、係員が有効な区間や日付を確かめて乗車を認める場面を考えます  
ここで確認しているのは「あなたは誰ですか」ではなく、「この切符で、この列車に乗れますか」です  
切符を持っていても、区間や日付が条件に合わなければ乗車は認められません

例えば、ある文書を読める利用者でも、その文書を編集できるとは限りません  
同じ利用者でも、対象や操作が変われば、許可されるかどうかは変わります  
認可は利用者を確認するだけで終わらず、実行しようとする操作に適用します [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request)

## 認証と認可の関係 {#definitions-認証結果とアクセス権限の関係}

| 観点 | 認証 | 認可 |
| --- | --- | --- |
| 確認すること | どの主体として扱えるか | 対象への操作を許可できるか |
| たとえ | 会員証と本人を照合する | 切符の条件を確かめて乗車を認める |
| 判断の材料 | アカウントと、提示された証拠の対応 | 主体・対象・操作と、アクセス制御の方針 |
| 成功・許可から分かること | その認証方法の条件を満たした | その条件で対象への操作が許された |

認証結果は、認可に使う判断材料の一つです  
ログインできたことだけを理由に、すべてのデータの閲覧や変更を許可することはできません

一方、公開文書を誰でも読めるという方針なら、個々の利用者を認証せずに閲覧を許可できます  
先ほどの切符の例でも、持ち主の名前を確かめずに乗車を認めています  
認証と認可は関係しますが、常に同じ処理でも、必ず同時に行う処理でもありません

## 確認問題

ある利用者がログインに成功しましたが、文書の編集を拒否されました  
認証に失敗したのでしょうか

::: details 解説
認証は成功していますが、その文書を編集する認可が与えられていません  
どの利用者として扱えるかを確かめることと、その利用者に何を許すかを決めることは別です
:::
