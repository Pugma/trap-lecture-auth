# JWT の署名検証

::: tip このページの目標

教材用の公開データの検証を実行し、デコード・署名検証・ログインに使えるかどうかの判断の違いを結果に基づいて説明できるようになる

:::

::: info このページの要点

- **最初の課題**：手元でコマンドを実行し、ID Token の署名が元のデータでは正しく、改変後には正しくないことを確認する
- **検証の範囲**：署名の検証と、ログインで必要な発行元・宛先・期限などの確認は別の処理である
- **題材**：教材用の固定データを使うため、認証サーバーや外部アカウントは不要である

:::

座学で学んだ署名と ID Token の仕組みを、実際の値と検証結果で確かめます  
OP を作る側にとって、発行した ID Token は受け取る RP が検証できて初めて意味を持ちます  
この課題では、発行された ID Token を受け取る側の立場で検証し、OP が何を正しく発行しなければならないかを確かめます

## ID Token の署名検証 {#段階1署名と-jwt-の検証}

前提は、座学の ID Token・JWS・JWK の説明です  
題材には、このリポジトリの `examples/jose/` にある教材用の公開データを使います  
認証サーバーや外部アカウントは不要です

### 準備

リポジトリのルートで実行します

```sh
mise install
mise exec -- node examples/jose/verify.mjs
```

Node.js の標準機能だけを使うため、この実習のための npm パッケージのインストールは不要です  
先頭に、実際の署名検証の結果が表示されます

```text
Original token signature: true
Changed payload signature: false
Changed signature bytes: false
```

順に、元の ID Token、ペイロードの `sub` を変えたもの、署名の一部を変えたものの結果です  
改変した値はスクリプト内で一時的に作るため、教材のファイルを書き換える必要はありません  
最後に `JOSE fixture checks passed` が表示され、続けて OIDC RP としての検証全体ではないことが表示されます

### 教材データと検証結果の対応

1. `token-response.http` の `id_token` と、`id-token.txt` の文字列が同じであることを確認する
2. `header.json` と `payload.json` を読み、署名方式、鍵の識別子、発行者、受信者、有効期限を見つける
3. `jwks.json` の `kid` がヘッダーと対応すること、公開パラメータ `n`・`e` があり秘密パラメータ `d` がないことを確認する
4. `verify.mjs` の署名検証を読む  
   元のデータでは成功し、ペイロードの `sub` または署名のバイト列を変えると失敗することを、三行の出力と対応する処理から確認する

正常な署名の検証は `true`、変更後の検証は `false` を期待する assertion です  
スクリプト全体の成功は、変更後のデータも受理したという意味ではありません

### 正常系と改変時の検証結果 {#正常系と改変時の期待結果}

スクリプトを読むときは、まずどの値を変えたら何が失敗するかを予想します  
次の表は、実装済みの確認と、その確認からは言えないことを分けたものです

| 対象 | スクリプトが期待する結果 | その結果が示す範囲 |
| --- | --- | --- |
| 元のトークンと公開鍵 | 署名検証が成功 | この署名対象と公開鍵に対応する署名である |
| `sub` を変え、署名を残したデータ | 署名検証が失敗 | 元の署名を、変更したペイロードへ流用できない |
| 署名の一部を変えたデータ | 署名検証が失敗 | 署名値の改変を受け入れない |
| HTTP 応答内の ID Token | 別ファイルの値と一致 | 掲載した応答例とトークンの実例が対応している |

変更後の署名が `false` になることを期待しているので、すべての確認を通るとスクリプト全体は成功します  
異常系の試験では、処理が拒否されたこと自体が正しい結果です  
単にエラーの数を数えるのでなく、何を受け入れ、何を拒否すべきかを先に決めます

### 署名検証後の確認事項 {#署名検証後の受入条件}

次はファイルを書き換える操作ではなく、座学の検証条件を当てはめる問いです  
「信頼する OP が正しく署名したが、別のアプリ向けの ID Token」を受け取った場合、公開鍵での署名検証は成功し得ます  
それでも現在の RP は、宛先が一致しない結果でログインを成立させてはいけません [OIDC Core §3.1.3.7](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation)

同様に、この教材ファイルの有効期限を過ぎてからスクリプトを実行しても、署名の数学的な正しさは期限によって変わりません  
このスクリプトは実際の時刻と Claims を照合していないので、成功を「今ログインに使える」と読み替えないことが重要です  
自分の説明を「署名の確認」と「用途に応じた判断」の二段階に分けて書いてみてください

実際の認証結果を扱うときに、この短いスクリプトをそのまま RP の完成品として組み込むことはできません  
本演習の目的は、ライブラリに任せる暗号処理と、アプリが設定・要求に照らして判断する処理を見分けることです

### 完了条件

手元でコマンドを実行し、`true`・`false`・`false` の三つの結果と、スクリプト全体の成功を確認してください  
そのうえで、次の三点を、確認したファイルや処理を指して説明できれば、この課題は完了です

- JWT の内容を読めることと、署名が正しいことの違い
- ペイロードを書き換えた場合に、元の署名を使えなくなる理由
- 署名が正しくても、RP がログインを許可する前に確認すべき条件

::: details 最後の問いの解説
このスクリプトが確かめるのは教材データの署名と整合性です  
信頼する issuer、RP に対応する audience、有効期限、開始した要求の nonce などを確認する OIDC RP の検証全体ではありません  
RP セッションを作る処理もありません  
したがって、スクリプトが成功したことから実際にログインできると判断することはできません
:::
