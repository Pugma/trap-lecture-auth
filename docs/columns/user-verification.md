# コラム：UV の意味と検証範囲

::: tip このページの目標

WebAuthn の UV から分かることと分からないことを区別し、認証要素や保証レベルを過剰に推定しないようになる

:::

::: info このページの要点

- **UV と UP**：UV はユーザー検証の結果を、UP は利用者の関与を示し、通常の UV だけでは PIN と生体を識別できない
- **保証レベル**：UV が真であることだけでは、認証や回復を含む保証レベル全体への適合を判断できない
- **サーバー側の検証**：UV を要求するだけでなく、署名を検証した応答でその条件が満たされたことを確認する

:::

通常の [UV](../reference/glossary.md#uv) フラグから分かるのは、認証器でユーザー検証を実施した結果です  
PIN と生体を識別するためのフラグではありません  
[UP](../reference/glossary.md#up) はユーザーの関与を示し、UV と別の意味を持ちます [WebAuthn Level 3 §6.1](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-authenticator-data)

この区別は、表示とサーバー側ポリシーの両方に影響します  
利用者の端末で顔認証の画面が出たとしても、サーバーの記録には、検証した証拠以上のことを書かないようにします  
教材では「ユーザー検証を要求し、応答でその条件を確認した」という記録にします  
「生体であることを確認した」と記録するには、その判定を支える別の根拠が必要です  
通常の UV と拡張機能による情報は混同しません

例えば、利用者がセキュリティキーに触れて応答を返した場合、その操作から分かるのは利用者の関与です  
そのキーを持っている人が登録時の本人かを、PIN などで確かめたとは限りません  
UP を「本人確認済み」の表示へ変換すると、証拠より強い説明になります  
反対に PIN 入力の画面が見えなくても、認証器が別の方法でユーザー検証している場合があります  
見えた操作の数や画面の種類から、応答のフラグを推測しないことが大切です

同じ理由で、「UV が真だから、このサービスはあらゆる AAL2 要件を満たす」とは言えません  
NIST の保証レベルには、認証器の特性だけでなく、認証やライフサイクルなどの条件があります  
ローカルな検証を伴う鍵の利用は多要素の構造を持ち得ますが、一つのフラグは保証レベル全体の認定ではありません [NIST SP 800-63B-4 §2・Appendix B](https://pages.nist.gov/800-63-4/sp800-63b.html)

本教材の採用案は、登録とログインで UV を要求し、その要求と応答の対応をサーバー側でも検証することです  
ボタンに「安全なログイン」と書いたことや、ブラウザへ要求オプションを渡したことだけで完了とはしません  
署名が正しい一方で要求した UV が満たされない応答を、成功へ進めない確認を計画します

検証の順序も、表示のための JSON を先に信用する設計にしません  
ブラウザから送られた「検証済み」という独自の値ではなく、署名で保護された authenticator data の UV を確認します  
WebAuthn の認証手順では、要求した検証条件と応答を照合すること、署名を検証することの両方が必要です [WebAuthn Level 3 §7.2](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-verifying-assertion)

教材で記録するなら、要求した UV の条件、検証した UV の値、成否を分けます  
失敗時に「生体認証に失敗」と断定せず、サーバーが分かる範囲で「要求したユーザー検証を確認できない」と扱います  
これにより、利用者への説明と、開発者が調べる検証条件を対応付けられます

**確認の問い：PIN を使ったログインを、生体より弱いから常に拒否する条件を UV だけで実装できますか**

解説：できません  
UV はその二つを識別する値ではありません  
要件として本当に方式の識別が必要なのか、その根拠と利用可能な情報を先に確認します  
端末の見た目からサーバーの検証能力を推測しないことが大切です
