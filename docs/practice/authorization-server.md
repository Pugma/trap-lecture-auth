# 認可サーバーの実装

::: tip このページの目標

OAuth 2.0 / OIDC の提供側を実装するときに、ライブラリとアプリケーションへ残る責任を対応付けられるようになる

:::

::: info このページの要点

- **プロトコル処理**：Client、callback、PKCE、認可コードの交換を仕様に従って検証する
- **アプリケーションの責任**：利用者の認証、同意、scope、認証時刻を根拠とともに扱う
- **保存処理**：コードの一回限りの消費、更新、失効を並行要求でも正しく扱う
- **現在の状態**：Go の参照サーバー、Fosite の固定版、起動手順、実行結果は未提供である

:::

Go と Fosite の具体的な構成は、このページで扱います  
座学で学んだ検証条件を、ライブラリの設定、アプリケーションの判断、保存処理へ対応付けます

## ライブラリとアプリケーションの境界

[Fosite](../reference/glossary.md#fosite) は Go 向けの OAuth 2.0 / OIDC のためのフレームワークです  
公式 README は、ユーザー認証、セッション管理、`prompt`、`max_age` など、提供側固有の知識が必要な処理がアプリケーションに残ると説明しています  
ライブラリを依存に追加することと、仕様に適合する AS / OP が完成することは別です  
[Fosite README：A word on security](https://github.com/ory/fosite#a-word-on-security)

教材では、HTTP ハンドラー、アプリケーションの認証・許可処理、プロトコル処理、保存層を分けて考えます  
これはファイルやインターフェースの名前を指定するものではありません  
責務が重なった箇所でも、何を根拠に受け入れるかを追えることが目的です

| 条件 | 担当する責務 | 実装での確認方法 |
| --- | --- | --- |
| Client・callback・PKCE の検証 | Fosite の設定とプロトコル処理へ接続 | 固定版ソースと不正な要求を拒否する試験 |
| ユーザーの認証と認証時刻 | アプリのログイン・セッション処理 | ユーザー切替と期限切れの試験 |
| 許可された scope の決定 | アプリのポリシーと同意処理 | 要求より狭い許可と拒否の試験 |
| コードの一回限りの消費 | プロトコル処理と保存層の協調 | 同時に交換しても両方は成功しないことを確かめる試験 |
| 更新・失効の範囲 | トークン処理と許可の保存記録 | scope 拡大の拒否、再利用時に関連するトークンを失効させる試験 |
| API での操作と対象へのアクセスの許可 | トークン検証と API | 許可されない対象を返さない試験 |

表の「Fosite へ接続」は、すべてが設定なしで実現されるという保証ではありません  
採用版におけるハンドラー構成、保存インターフェース、失敗時の挙動を確認して初めて具体的な実装に置き換えます

## OP の認証処理

`prompt`・`max_age` への対応では、アプリケーションが管理する認証セッションと実際の認証時刻を、ライブラリの処理へ結び付けます  
ライブラリを採用しただけで完成した OP にはならないため、固定版のソースと拒否試験で分担を確かめます  
仕様上の条件は座学の [OP の設計](../chapter-3/oidc-provider.md)で扱います

traQ の公開ソースを読む課題と、Fosite で参照サーバーを組み立てる課題は区別します  
traQ のハンドラーを Fosite の API 利用例として扱うものではありません

## 続く課題

参照サーバーを用意した後は、認可コードと PKCE、API の認可、Refresh Token の更新、OIDC の接続を順に実装・検証します  
OIDC の適合試験は、提供側の実装を用意した後に [OIDC 適合試験](../reference/conformance-testing.md) と対応付けます

本文の順序に合わせ、確認対象を次のように積み上げます  
以下は課題の設計であり、AS / OP の実行環境と試験結果は未提供です

| 段階 | 正常系と拒否条件 | この段階だけでは確認できないこと |
| --- | --- | --- |
| Code + PKCE → API | 正当なコード交換と許可された操作、誤った戻り先・verifier・コード再利用・scope / 対象への権限不足の拒否 | RT の継続利用、OIDC の認証結果、保存層の並行消費 |
| RT の追加 | 権限を増やさない更新、旧 RT の再利用拒否、関連する RT の失効、並行更新で二つとも成功しないこと | OP の Claims と鍵公開、仕様全体への適合 |
| OP の追加 | 第3章の ID Token 発行と主要検証条件、続いて Discovery・UserInfo・prompt / max_age と拒否条件 | 独立 RP の相互接続、Conformance / Certification |
| 保存層・相互接続・適合試験 | コード消費と更新の競合、別実装の RP、選んだ suite 対象の結果 | 未実行の仕様・実機・アプリ固有の条件、正式認定 |

各段階で、確認した入力・期待する受理または拒否・実際の結果を対応付けます  
基本経路でもコードの一回限りの消費は必要であり、並行処理の試験を後段に置くことはその条件を省略する理由にはなりません
