# コラム：テンプレートと運用の境界

::: tip このページの目標

テンプレートやライブラリの採用後も残る検証すべき事項を挙げ、役割の分割と実際にアクセス権を分離することを区別できるようになる

:::

::: info このページの要点

- **テンプレートの責任**：画面や保存層を提供しても、認証状態とユーザー・Client・権限の対応は検証する必要がある
- **役割と隔離**：AS/OP と API を別の処理に分けるだけでは、秘密や DB 権限を隔離したことにならない
- **標準 API**：内部の照会・失効処理があるだけでは、Introspection や Revocation の HTTP の要求・応答についての仕様への対応を意味しない
- **本番運用**：教材の動作確認に加えて、状態の共有、鍵の更新、監視や事故対応を設計する必要がある

:::

講習会でユーザー管理やログイン画面をテンプレートとして配るのは、学ぶ範囲を絞るためです  
その部分の安全性を考えなくてよい、という意味ではありません  
認証セッションを別の利用者へ取り違えるテンプレートなら、その先で正しい ID Token を発行しても、間違った人物の認証結果を正確に伝えてしまいます

本教材では、見た目や一般的な DB 接続は説明を短くし、認証状態を何と結び付けたかは本文に残します  
同意の画面が整っていても、許可したユーザー、client、scope の対応がサーバー側に残らなければ、許可の証拠として使えません  
テンプレートの境界は、責任を消す線ではなく、どこを詳しく説明し、どこを前提として検証するかを決める線です

## 役割の分離と権限の隔離

主例では AS/OP とメッセージ API を別のハンドラーとして扱い、最初は同じ参照アプリへ置く案を採ります  
これは、発行と利用の責任を読み分けやすくする配置です  
同じプロセスの関数へ分けただけでは、メモリーや DB 権限を分離したことにはなりません

たとえば API の処理に不具合があり、同じプロセスが保持する秘密へアクセスできる状態なら、フォルダー名を `op` と `api` に分けても保護にはなりません  
逆に、別プロセスにしただけでも、同じ強い DB 資格情報を共有していれば影響範囲は広がり得ます  
教材の論理的な配置から、本番環境で攻撃を受けた場合の安全性まで判断しないようにします

例えば API が必要とするのは、トークンから主体と許可範囲を確認する能力です  
それに対して OP の署名鍵を使う能力まで与えると、API が侵害された際に認証結果の発行側へ影響が広がります  
分離案を検討するときは、プロセス名ではなく、各処理が読める情報と実行できる操作を書き出します  
参照専用の資格情報と更新用の資格情報を分ける案も、実際のアクセス権で制約できて初めて意味を持ちます

ユーザー管理と IdP の分離でも、プロセスの配置とデータの所有者を区別します  
共有 DB から別サービスへ移す際の通信と状態の扱いは、[IdP とユーザー管理の分離](identity-architecture.md)で具体化します

## 内部処理と標準の HTTP API

opaque な Access Token を API が調べる場合、同じアプリ内の保存層を参照する設計が考えられます  
別の Resource Server へ分ける際の標準的な連携には、RFC 7662 の [Introspection](../reference/glossary.md#introspection) があります  
これはトークンの状態を調べる HTTP の契約であり、内部の検索関数があるだけで対応済みになるわけではありません  
問い合わせる側の認証と情報の開示範囲も含めて扱います [RFC 7662 §2](https://www.rfc-editor.org/rfc/rfc7662.html#section-2)

同様に、保存された Refresh Token を失効させる内部処理と、RFC 7009 の [Revocation](../reference/glossary.md#revocation) エンドポイントは区別します  
後者を名乗るには、要求・応答やクライアント認証を含む契約への対応が必要です  
教材の更新処理で失効が必要だからといって、標準 API の全実装を済ませたことにはなりません [RFC 7009 §2](https://www.rfc-editor.org/rfc/rfc7009.html#section-2)

Introspection の応答が有効を示しても、メッセージを削除できるという結論までは得られません  
API は応答の scope などを要求された操作へ対応付け、対象メッセージについても認可します  
また、問い合わせ自体にも認証が必要です  
誰でもトークンの情報を取り出せる照会窓口にしない条件は、内部関数を HTTP 化する際に新しく現れる境界です [RFC 7662 §2.1–2.2](https://www.rfc-editor.org/rfc/rfc7662.html#section-2.1)

失効についても、保存層から削除した時点と、別の API が拒否を始める時点を分けて考えます  
照会結果をキャッシュする構成なら、その間は古い判断が残り得ます  
キャッシュを使う場合は、負荷の軽減と情報の新しさの両方を考慮します [RFC 7662 §4](https://www.rfc-editor.org/rfc/rfc7662.html#section-4)

## 本番運用の設計事項

教材では、認可コードの一回限りの消費と、ローテーション時の Refresh Token の更新を学びます  
Access Token まで一回使うと無効になる、という意味ではありません  
実サービスへ進むと、次の事項も判断対象になります

- 複数インスタンス間の状態保存
- 鍵の更新と失効情報の反映
- 監視と事故対応

これらを第一稿で実装しないことと、不要と結論付けることは別です

制作側の確認では、正常系の手順だけでなく、依存する保存先や照会先が使えない場合も設計の対象にします  
教材で「検証できない要求を許可しない」と決めるなら、障害時に正常系へ進む分岐がないことを確かめます  
そのうえで、利用者へ再試行を促す表示と、運営者が障害を知る通知を分けます  
認証情報を丸ごとログへ残さず、どの検証段階で処理を止めたかを追える記録を用意することも、運用へ持ち出す際の設計事項です

署名鍵についても、秘密鍵をサーバーが持ち、公開鍵を JWKS で配れば運用の全体が終わるわけではありません  
どのアルゴリズムと鍵を信頼するかを設定し、受信したトークンの指定だけで決めないことが必要です [RFC 8725 §3.1](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.1)

**確認の問い：AS と API を別ファイルへ分ければ、署名鍵を API から隔離できたと言えるでしょうか**

解説：言えません  
ファイルの分割はコード上の構造です  
隔離について判断するには、実行プロセス、資格情報、アクセス権、保存先などの境界を確認します  
教材で得た役割の理解を、運用の具体的な権限へ対応付ける必要があります
