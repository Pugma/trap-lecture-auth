# コラム：LDAP・SAML・OIDC の使われ方

::: tip このページの目標

LDAP 認証・SAML・OIDC がどのような場面で使われ、アプリが何を受け取り何を検証するのかを比べて説明できるようになる

:::

::: info このページの要点

- **層の違い**：LDAP はディレクトリへのアクセス、SAML と OIDC はアプリへの認証結果の連携であり、同じ層の選択肢とは限らない
- **パスワードの経路**：LDAP 認証ではアプリがパスワードを受け取り、SAML・OIDC ではアプリが IdP の発行した結果を受け取る
- **使われる場面**：社内基盤や大学・SaaS の連携では、これらの方式が組み合わさって使われることが多い
- **推奨ではなく整理**：どれを選ぶかは、接続先が対応する方式と運用の条件で決まる

:::

本編では OIDC を中心に扱い、[認証方式の比較](../chapter-3/federation.md#comparison)で SAML Web Browser SSO と対応付けました  
実際の組織では、OIDC 以外に LDAP や SAML を使ったログインにも出会います  
ここでは、どれが優れているかではなく、それぞれがどこで使われ、どのような性質を持つかを整理します

## 三つの方式の比較

| 観点 | LDAP 認証 | SAML（Web Browser SSO） | OIDC |
| --- | --- | --- | --- |
| 本来の役割 | ディレクトリ（ユーザー・グループ等の情報）の検索と更新 | 認証結果などの主張を IdP から SP へ伝える | OAuth 2.0 の上で、認証結果を OP から RP へ伝える |
| よく見る場面 | 社内の Active Directory や OpenLDAP、Linux へのログイン、VPN・無線 LAN、社内ツールのログイン設定 | 企業向け SaaS の SSO、大学・研究機関の学術認証フェデレーション | 一般向けの「〜でログイン」、モバイルアプリ、API の認可と組み合わせたログイン |
| アプリが受け取るもの | 利用者が入力したパスワード（アプリがディレクトリサーバーへ bind して確かめる） | ブラウザ経由で届く XML の SAML Response・Assertion | ブラウザ経由の認可コードと、コード交換で得る ID Token（JWT） |
| アプリがパスワードを扱うか | 扱う | 扱わない（IdP の画面で入力する） | 扱わない（OP の画面で入力する） |
| 信頼の設定 | ディレクトリサーバーの接続先・TLS・検索用の DN | IdP と SP の Metadata（エンティティ ID、受信先、証明書）の交換 | issuer、Discovery、JWKS、Client の登録 |
| SSO | 同じパスワードで各アプリへ入れるが、ログインは各アプリで行う | IdP のセッションを使って複数 SP へログインできる | OP のセッションを使って複数 RP へログインできる |
| ネイティブアプリ・API | 内部ネットワークの機器やサーバーと相性がよい。インターネット越しに公開する用途は想定しにくい | ブラウザを前提とする Profile が中心 | ネイティブアプリ向けの手順が整理され、API の認可は OAuth と組み合わせる |
| 主な注意点 | 通信の暗号化、空パスワードの扱い、検索フィルタへの入力の埋め込み | XML 署名の検証範囲、宛先・時間条件・要求との対応の確認 | issuer・audience・nonce などの検証、コード交換の保護 |

表の「よく見る場面」は傾向であり、各方式の仕様が用途を限定しているわけではありません  
例えば SAML を使う社内システムもあれば、OIDC に対応した企業向け SaaS もあります

## LDAP 認証

LDAP（Lightweight Directory Access Protocol）は、ユーザーやグループなどの情報を木構造で管理するディレクトリへアクセスするためのプロトコルです  
「LDAP 認証」と呼ばれるものの多くは、アプリが利用者から受け取った名前とパスワードで LDAP の Bind 操作を行い、その成否でログインを判断する使い方です [RFC 4511 §4.2](https://www.rfc-editor.org/rfc/rfc4511.html#section-4.2)

アプリがパスワードをそのまま受け取ってディレクトリへ渡すため、アプリが侵害されるとパスワードも漏れます  
SAML や OIDC のように、アプリがパスワードを見ずに認証結果だけを受け取る構成とは、ここが大きく異なります  
RFC 4513 も、名前とパスワードによる Bind はパスワードをサーバーへ開示するものであり、通信の秘匿がない環境には適さないとしています [RFC 4513 §5.1.3・§6.3.2](https://www.rfc-editor.org/rfc/rfc4513.html#section-5.1.3)

LDAP 特有の落とし穴に、空のパスワードによる Bind があります  
名前があってパスワードが空の Bind は「認証なし」の扱いで、サーバーによっては成功を返しますが、その名前の利用者を認証したわけではありません  
Bind の成功だけでログインを許可するアプリは、空パスワードを入力前に拒否する必要があります [RFC 4513 §5.1.2・§6.3.1](https://www.rfc-editor.org/rfc/rfc4513.html#section-6.3.1)  
また、入力したユーザー名を検索フィルタへ埋め込むときは、SQL と同様にエスケープしないと意図しない検索条件になり得ます [RFC 4515 §3](https://www.rfc-editor.org/rfc/rfc4515.html#section-3)

LDAP はディレクトリでもあるため、ログインの可否だけでなく、所属グループや表示名を引く用途にも使われます  
Active Directory のように、LDAP によるディレクトリと Kerberos による認証などを組み合わせた製品もあります

## SAML

SAML（Security Assertion Markup Language）は、IdP が利用者の認証などについての主張を XML の Assertion として SP へ伝える仕様群です  
流れと OIDC との対応は[本編の比較](../chapter-3/federation.md#comparison-saml-web-browser-sso-との比較)で扱いました

SAML は OIDC より前から普及しており、企業向け SaaS の SSO や、大学・研究機関が参加する学術認証フェデレーションで広く使われています  
フェデレーションでは、参加する IdP と SP の Metadata をまとめて配布し、組織をまたいだ信頼関係を一括で管理する運用が見られます  
一方で、XML 署名の検証は、署名された範囲と実際に読み取る要素がずれないように実装する必要があり、自作よりも実績のあるライブラリを使うのが一般的です [OASIS SAML Technical Overview](https://docs.oasis-open.org/security/saml/Post2.0/sstc-saml-tech-overview-2.0.html)

## 組み合わせて使われる構成

三つの方式は、一つを選ぶと他が不要になる関係ではありません  
よくある構成では、ユーザーの正本を LDAP / Active Directory に置き、IdP がそれを参照して利用者を認証し、各アプリへは SAML や OIDC で結果を伝えます

```text
アプリ A ──SAML──┐
アプリ B ──OIDC──┼── IdP ──LDAP──> ディレクトリ（ユーザー・グループの正本）
アプリ C ──OIDC──┘
```

この構成では、アプリはパスワードを扱わず、ディレクトリへ接続するのは IdP だけになります  
アプリごとに LDAP へ直接接続する構成と比べ、パスワードが通る場所とディレクトリの接続設定を一か所へ集められます  
IdP とユーザー情報の正本を分ける考え方は、[IdP とユーザー管理の分離](../columns/identity-architecture.md)のコラムで扱いました

既存のアプリが LDAP にしか対応していない、接続先の SaaS が SAML にしか対応していない、といった制約もよくあります  
方式は理想だけで決まらず、接続先が対応する方式、組織の既存基盤、運用する人の慣れによって選ばれます

**確認問題：** 社内ツールに LDAP 認証を設定したところ、存在するユーザー名とパスワード空欄でログインできてしまいました  
ディレクトリサーバーのパスワードが漏れたのでしょうか

::: details 解説
パスワードが漏れたとは限りません  
空のパスワードによる Bind は認証なしの扱いであり、サーバーが成功を返しても、その名前の利用者を認証したことにはなりません  
ツールが Bind の成否だけでログインを判断しているなら、空パスワードを拒否する設定や実装を確認し、サーバー側でも認証なしの Bind を拒否する設定を確認します
:::
