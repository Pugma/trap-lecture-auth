# OAuth による権限の委譲

::: tip このページの目標

外部アプリに権限を委譲する目的と登場人物の役割を理解し、利用者の権限とアプリに許可する範囲を区別できるようになる

:::

::: info このページの要点

- **委譲**：利用者のパスワードを渡さず、外部アプリへ必要なアクセスを許可する
- **登場人物**：利用者、外部アプリ、許可を確認するサーバー、メッセージを提供するサーバーの役割を区別する
- **権限の範囲**：scope による操作の制限と、利用者が対象にアクセスできるかの判断を分ける
- **トークン**：Access Token は所持者が使える資格情報なので、AS は発行先と範囲を、API は受け入れる範囲を限定する

:::

この章では、A さんが外部アプリ「チャットビューアー」で、[traQ](https://github.com/traPtitech/traQ) のメッセージを読む場面を例にします  
まず、誰がどのサービスを使い、各サーバーが何を担当するかを整理します

<span id="specifications-教材の構成"></span>

traQ の公開ソースを参考にしますが、チャットビューアーと以後の通信例は説明用の設計です  
実際の traQ の挙動を紹介する箇所には、参照したソースを示します

## OAuth の登場人物と役割 {#oauth-oauth-の登場主体}

チャットビューアーは traQ とは別の Web アプリです  
A さんが閲覧できるメッセージを traQ から取得して表示します  
この例の利用者・アプリ・サーバーを、OAuth の用語と対応付けると次のようになります

| 用語 | 例での登場人物 | 担当すること |
| --- | --- | --- |
| リソースオーナー（[Resource Owner](../reference/glossary.md#resource-owner)） | A さん | 自分がアクセスできるメッセージを、外部アプリが読むことを許可する |
| クライアント（[Client](../reference/glossary.md#client)） | チャットビューアー | 利用者の許可を得て、traQ の API にメッセージを要求する |
| 認可サーバー（[Authorization Server](../reference/glossary.md#authorization-server)、AS） | traQ 側でログイン・許可を確認するサーバー | 利用者と許可の範囲を確認し、API へのアクセスに使うトークンを発行する |
| リソースサーバー（[Resource Server](../reference/glossary.md#resource-server)、RS） | traQ のメッセージ API を提供するサーバー | トークンとアクセス権を確認し、許可されたメッセージを返す |

ここでの**リソース**は、アクセスの対象になるメッセージです  
**Access Token** は、外部アプリが API に提示する資格情報です  
認可サーバーが発行し、リソースサーバーが受け取って検証します  
以下では表の英語名や AS・RS の略称も使います [RFC 6749 §1.1・§1.4](https://www.rfc-editor.org/rfc/rfc6749.html#section-1.1)

### ブラウザとサーバーの配置

ブラウザは、A さんがチャットビューアーや traQ 側の画面を開くために使います  
OAuth の Client はこの例ではチャットビューアーを指し、ブラウザそのものを指すわけではありません  
ビューアーはバックエンドを持ち、そこでトークンを保持して traQ の API を呼びます

認可サーバーとリソースサーバーは役割の区別であり、別々のマシンやプロセスを必須とする分類ではありません  
教材の設計例では、この二つを一つの参照アプリ内の別ハンドラーとして置き、Client は別の Web アプリにします  
同じプロセス内で処理を分けること自体は、セキュリティ上の隔離にはなりません [RFC 6749 §1.1](https://www.rfc-editor.org/rfc/rfc6749.html#section-1.1)

## OAuth と権限の委譲 {#oauth}

OAuth 2.0 は、クライアントに保護されたリソースへの限定的なアクセスを与えるための枠組みです  
チャットビューアーに A さんのパスワードを渡す構成では、操作の限定やアプリ単位の権限取消しが難しくなります  
OAuth では、認可サーバーが許可を確認してトークンを発行し、ビューアーはそのトークンで API を利用します [RFC 6749 §1](https://www.rfc-editor.org/rfc/rfc6749.html#section-1)

### 題材の全体像

A さんが、外部アプリ「チャットビューアー」で traQ のメッセージを読む場面を考えます  
A さんのパスワードをビューアーへ渡さずに、必要なアクセスだけを許可するのが最初の課題です

1. A さんがビューアーから traQ 側の認証・許可の画面へ移る
2. traQ 側が A さんを確認し、ビューアーへ許可する範囲を確かめる
3. ビューアーがその許可に基づく Access Token を取得する
4. ビューアーがトークンを API に提示し、A さんが閲覧できるメッセージを受け取る

ここまでが認可の章で追う流れです  
認証の章ではさらに、traQ 側の認証結果をビューアーのログインへ利用するため、OIDC が何を追加するかを確認します  
通信で使う個々の値を覚える前に、「利用者を確かめる」「外部アプリへの許可を得る」「対象へのアクセスを判断する」という目的を分けておきます


### 利用者の関与と承認 {#oauth-利用者の関与と承認}

本編で扱うのは、人間の利用者が外部アプリへ権限を委譲する流れです  
A さんが認可サーバーで認証を受け、チャットビューアーに何を許可するかを確認する、という操作を基本例にします  
認証は「誰か」の確認、承認は「その Client に何を許すか」の判断であり、ログインできたことだけから委譲への同意を導いてはいけません

ただし、認可要求のたびに承認ボタンを押すことが必須ではありません  
認可サーバーは利用者への確認や既存の許可を通じて、要求を許可できるか判断します  
画面の表示を省ける場合にも、許可の確認そのものが不要になるわけではありません [RFC 6749 §4.1.1](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1.1)

OAuth 全体は、人間だけを対象とする仕様ではありません  
RFC 6749 は Resource Owner が人間である場合を End-User と呼び、Client 自身の権限でアクセスする Client Credentials も定義しています  
人間の利用者に代わるアクセスと、プログラム自身としてのアクセスの違いは、[マシンアカウントのコラム](../columns/machine-authentication.md)で扱います [RFC 6749 §1.1・§4.4](https://www.rfc-editor.org/rfc/rfc6749.html#section-1.1)

### Client の識別と認証 {#oauth-client-の識別と認証}

教材では Client を事前登録し、識別子、callback の URL、許可する scope、利用する認証方式を保存します  
[`client_id`](../reference/glossary.md#client-id) は Client を区別する公開の識別子で、それだけで Client の真正性は証明しません

OAuth は、資格情報を機密に保てる Client を [confidential](../reference/glossary.md#client-types)、そうした保持能力がない Client を public と区別します  
公開されているサービスだから public、社内サービスだから confidential という分類ではありません  
配布したブラウザの JavaScript に埋めた秘密は、利用者が取得できるため、サーバー側の秘密と同じ扱いにはできません [RFC 6749 §2.1–§2.3](https://www.rfc-editor.org/rfc/rfc6749.html#section-2.1)

本教材では confidential な Web Client を主例にし、トークンエンドポイントで `client_secret_basic` を使う採用案です  
これは実装の前提をそろえる選択であり、唯一のクライアント認証方式という意味ではありません  
秘密はブラウザへ配らず、HTTPS のサーバー間通信で使用します

#### Client の種類と秘密の保持 {#oauth-client-の種類と秘密の保持}

同じチャットビューアーでも、サーバーのバックエンドがトークンを管理する構成と、ブラウザへ配ったプログラムだけで API を呼ぶ構成では、秘密を保護できる場所が異なります  
利用者へ配布するプログラムに全員共通の secret を埋め込んでも、利用者自身が読み出せるなら、特定の正規 Client だけが知る秘密としては使えません  
設定ファイルを圧縮する、変数名を分かりにくくする、といった処理ではこの性質は変わりません

confidential という分類も、そのアプリがあらゆる攻撃に耐えることを意味しません  
バックエンドに秘密を置けるという前提と、そのサーバーが侵害されたりログへ秘密を出したりしないよう管理する責任は別です  
Client の種類は、どの認証の前提を置けるかを決める分類です

| 構成の例 | 秘密についての前提 | 認証で言える範囲 |
| --- | --- | --- |
| 運営者が管理するバックエンド | Client の秘密を利用者へ配布せず保持できる | その秘密を持つ Client からの要求として検証できる |
| ブラウザへ配布するアプリ | 配布物の中の共通秘密は利用者が取得できる | 共通秘密だけでは正規アプリを識別できない |
| 同じ製品の複数の構成要素 | 構成要素ごとに保持能力が異なり得る | 製品名だけで一種類と決めず、役割を確認する |

この整理は RFC 6749 の Client の種類と構成例に対応します [RFC 6749 §2.1](https://www.rfc-editor.org/rfc/rfc6749.html#section-2.1)  
本書がバックエンドを持つ構成に絞るのは、秘密の保存場所とサーバー間通信を明確にするためです  
ブラウザだけの Client が OAuth を利用できない、という意味ではありません

#### Client 認証と利用者の許可 {#oauth-client-認証と利用者の許可}

正しい client secret を使っているチャットビューアーでも、A さんが許可していない操作はできません  
Client 認証が答えるのは要求元の確認であり、「この Client にすべての利用者のデータを返してよいか」ではないからです  
利用者が拒否した要求を、Client 認証の成功で上書きしてはいけません

逆に、A さんがチャットビューアーへの読み取りを許可したとしても、別の Client がその許可を自由に引き継げるわけではありません  
後のコード交換では、どの Client へ発行したコードかを確認します  
AS が知っている Client であることと、そのコードの発行先であることは別の条件です [RFC 6749 §4.1.3](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1.3)

さらに、Client を登録した時点で、その開発者の意図や実装全体が安全だと証明されたわけではありません  
登録情報は、識別子や戻り先など、通信を検証するための基準になります  
外部アプリを誰が運営するか、取得した情報をどう保存するかは、利用者へ説明すべき別の判断材料です  
OAuth の通信に適合するアプリでも、許可範囲内で大量のデータを取得する可能性は残ります

### scope と操作権限 {#oauth-scope-と操作権限}

チャットビューアーが `read write` を要求したとします  
`read` と `write` は traQ が定義する scope であり、OAuth の RFC が固定の名前や権限範囲を定めたものではありません  
AS は要求をそのまま許可にせず、Client に認めた範囲や利用者の判断を踏まえて、実際の許可を決めます [RFC 6749 §3.3](https://www.rfc-editor.org/rfc/rfc6749.html#section-3.3)、[traQ の scope 定義](https://github.com/traPtitech/traQ/blob/b08db60b239677913380af450541c1c1952b5898/model/oauth2.go#L32-L35)

例えば、読み取りだけを許可したなら、トークンに対応する権限も `read` だけです  
利用者がログインに成功したことは、書き込みへの同意ではありません  
同意画面で拒否された場合は、コードを発行せず、検証済みの戻り先へ拒否を伝える経路を持ちます

scope は操作の種類を制限し、対象へのアクセスはアプリケーションの認可ルールで判断します  
例えば `read` があることは、すべてのチャンネルや DM を読めることを意味しません  
本教材の API は次の条件を別々に確かめます

- トークンが有効であること
- 読み取り scope があること
- 対象メッセージのチャンネルや DM を、トークンに対応するユーザーが閲覧できること

公開ソースでは、`GET /api/v3/messages/{messageID}` がメッセージ取得に対応し、`read` に取得、`write` に編集などの操作が割り当てられています  
`read` はメッセージ一件だけに限定された scope ではなく、traQ が定める他の読み取り操作も含みます  
本書はその一部を例として扱います  
[traQ のルーティング](https://github.com/traPtitech/traQ/blob/b08db60b239677913380af450541c1c1952b5898/router/v3/router.go#L219-L224)、[read の権限](https://github.com/traPtitech/traQ/blob/b08db60b239677913380af450541c1c1952b5898/service/rbac/role/read.go#L8-L12)、[write の権限](https://github.com/traPtitech/traQ/blob/b08db60b239677913380af450541c1c1952b5898/service/rbac/role/write.go#L8-L15)

チャンネルで他人の投稿を読めることと、その投稿を編集できることも別です  
traQ の編集処理は、要求元ユーザーが投稿者でなければ拒否します  
教材でも、`write` があるだけで A さんによる B さんの投稿の編集を許可しません  
[traQ の投稿者確認](https://github.com/traPtitech/traQ/blob/b08db60b239677913380af450541c1c1952b5898/router/v3/messages.go#L117-L120)

同意画面が適切でも、API が対象へのアクセス権を調べなければ、閲覧できない DM の内容が漏れる可能性があります  
逆に API が対象を調べていても、Client が要求していない権限まで発行すれば、委譲の範囲が不明になります  
許可する側と、実行する側の両方に責任があります  
ロールや属性による権限管理と、scope の切り方の設計例は[コラム：権限管理と scope](../columns/permissions.md)で扱います

#### scope とリソースへのアクセス権 {#oauth-scope-と資源へのアクセス権}

`read` を持つ A さんのトークンと B さんのトークンは、同じメッセージを常に取得できるわけではありません  
例えば A さんは参加しているが B さんは参加していない DM では、操作の種類は両者とも読み取りですが、対象へのアクセス権が異なります  
scope の照合だけで判定を終える実装では、この違いが失われます

反対に、A さん自身がある投稿を編集できても、チャットビューアーに渡したトークンが `read` だけなら、そのトークンでの編集は拒否します  
利用者が持つ権限のすべてを、外部アプリへ預けたわけではないからです  
この権限委譲の例では、操作が許可される範囲を「トークンに認めた操作」と「利用者がその対象に行える操作」の両方で制限します

| 要求 | scope の条件 | 対象の条件 | 教材での判断 |
| --- | --- | --- | --- |
| 閲覧できるチャンネルの他人の投稿を取得 | `read` あり | 閲覧可能 | 許可 |
| 参加していない DM の投稿を取得 | `read` あり | 閲覧不可 | 拒否 |
| 自分の投稿を編集 | `read` のみ | 投稿者本人 | 拒否 |
| 他人の投稿を編集 | `write` あり | 投稿者ではない | 拒否 |

この表は OAuth が定めたリソースのモデルではなく、traQ の題材に沿った認可判断の整理です  
別の API では組織の役割、文書の共有設定、操作時刻なども条件になります  
scope の名前を細かく分けても、リソースごとの判断が自動的に不要になるわけではありません

#### 権限の縮小と委譲の取消し {#oauth-権限の縮小と委譲の取消し}

Client が `read write` を要求して `read` だけを許可した場合、AS は応答の `scope` で実際の範囲を伝えます [RFC 6749 §3.3](https://www.rfc-editor.org/rfc/rfc6749.html#section-3.3)  
API は発行された範囲に従い、そのトークンによる編集の要求を拒否します  
Client 側での発行結果の扱いは[コラム：OAuth Client の実装](../columns/client-implementation.md#client-errors-token)で扱います

発行後に「このアプリとの連携を解除する」操作では、今後その委譲に基づくアクセスを止める必要があります  
Client の画面からログアウトするだけでは、バックエンドに残ったトークンの利用を止めたことにはなりません  
教材では、どの Client への許可を取り消し、関連する Refresh Token と発行済み Access Tokenをどう扱うかを、提供側の操作として区別します  
標準の失効要求と関連トークンへの影響は [RFC 7009 §2.1](https://www.rfc-editor.org/rfc/rfc7009.html#section-2.1)、反映までの経路は[トークンの寿命](token-lifecycle.md#lifecycle)で扱います

委譲の取消しは、すでに Client が取得して保存したメッセージのコピーを回収する操作ではありません  
取得後の保存期間や削除方針まで OAuth のトークンだけで強制できると考えると、許可画面の説明と実際に制御できる範囲が食い違います

### Access Token の性質 {#oauth-access-token-の性質}

本教材は Bearer Token を使います  
[Bearer](../reference/glossary.md#bearer-token) とは、そのトークンを持つ者が利用できる性質を指します  
Client を最初に認証したとしても、盗まれた Access Token を API へ提示する者が同じ Client であると、それだけで保証されるわけではありません [RFC 6750 §1.2](https://www.rfc-editor.org/rfc/rfc6750.html#section-1.2)

教材の API は、`Authorization` ヘッダーで提示されたトークンを受け付ける設計にします  
URL へ埋め込むと履歴やログに残る経路が増えるため、教材の通常経路にはしません  
トークンの形式は Client から見て [opaque](../reference/glossary.md#opaque-token)、つまり中身を解釈しない文字列を採用案とします  
JWT でなければ OAuth ではない、ということはありません [RFC 6750 §2.1・§5.3](https://www.rfc-editor.org/rfc/rfc6750.html#section-2.1)

API は、無効・期限切れなどのトークンと、トークンは有効だが必要な scope がない状況を区別します  
Bearer のエラー仕様では、それぞれ `invalid_token` と `insufficient_scope` が整理されています  
対象へのアクセス権がない場合に何を利用者へ返すかは、存在の開示も含めたアプリ側の方針として決めます [RFC 6750 §3.1](https://www.rfc-editor.org/rfc/rfc6750.html#section-3.1)

#### Bearer Token の受渡し {#oauth-bearer-token-の受渡し}

チャットビューアーが受け取った Access Token を、別のサービスへそのまま渡したとします  
API が通常の Bearer Token として受け付ける構成なら、渡された側もその値を提示できるようになります  
トークンを渡すことは、トークンに認められた操作を実行する能力を別のサービスへ渡すことです [RFC 6750 §5.1・§5.3](https://www.rfc-editor.org/rfc/rfc6750.html#section-5.1)  
Client がトークンをログや別サービスへ渡さないための扱いは、[コラム：OAuth Client の実装](../columns/client-implementation.md#client-token-handling)で扱います

提供側は、Bearer Token の提示だけでは、提示した者が発行先の Client であるかを区別できないことを前提にします  
どの Resource Server を対象に発行し、どのサーバーが受け入れるかという制限は、scope の操作範囲とは別の観点です  
RFC 9700 は Access Token を特定の Resource Server や操作に制限する方針を整理しています [RFC 9700 §2.3](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.3)

本教材は一つのメッセージ API を主例にするため、複数 API 向けのトークン取得手順までは増やしません  
ただし、実装を拡張するときには「同じ AS が発行したからどの API でも受け入れる」と一般化しないようにします  
発行元が信頼できること、対象 API に使えること、要求した操作とリソースへアクセスできることは、それぞれ確認する条件です

#### 利用者からの権限委譲と Client 自身の権限 {#oauth-ユーザー委譲と-client-自身の権限}

夜間に定期処理を行うプログラムでは、人がその場で同意画面を操作しない場合があります  
ただし「人の操作がない」というだけでは、利用者からの権限委譲を使っているかどうかは決まりません  
以前 A さんが許可した範囲で処理を続ける構成と、プログラム自身に与えられた権限で処理する構成は異なります

前者では A さんの許可が処理の根拠として残り、A さんの連携解除や対象への権限変更を考える必要があります  
後者ではプログラムの権限が根拠になるため、無関係な利用者を「ログイン中のユーザー」として作る必要はありません  
Client Credentials Grant は confidential Client が自身の管理下のリソースなどへアクセスするための方式であり、ユーザーの認可コード交換を省略しただけの手順ではありません [RFC 6749 §4.4](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.4)

この違いは、API が誰による操作として記録するかにも影響します  
教材で扱う権限委譲では「A さんの権限を使うチャットビューアー」として、利用者と Client の両方を追えます  
利用者と Client を区別せずに記録すると、誰の許可を取り消せばよいか、どのアプリから要求されたかを区別しにくくなります  
認可方式を選ぶ前に、操作の根拠が利用者からの権限委譲なのか、プログラム自身の権限なのかを定めます

### 認可の責任分担 {#oauth-認可の責任分担}

AS はユーザーの認証とは別に、Client に認める scope と利用者の許可を確認し、実際に許可した範囲を発行結果へ反映します  
メッセージ API は、そのトークンの有効性、操作に必要な scope、対象の閲覧・編集権限を確認します  
要求された権限、トークンに認められた権限、個々の操作の許可は、それぞれ異なる段階の判断です

人がその場で許可の操作を行わないアクセスには、Client Credentials Grant などの方式もあります  
[マシンアカウントと mTLS のコラム](../columns/machine-authentication.md)で、プログラム自身の認証と、そのプログラムへのアクセスの許可を補足します
