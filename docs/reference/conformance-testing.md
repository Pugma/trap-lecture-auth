# OIDC 適合試験

::: tip このページの目標

OP の適合試験の対象と前提を整理し、接続の成功・試験結果・正式認定を区別して記録できるようになる

:::

::: info このページの要点

- **現在の状態**：OIDF Conformance Suite を使う制作側の検証計画であり、起動・接続・試験は未実施である
- **試験対象**：OP の Basic OP / Config OP を参照する案から、教材の対応範囲と不足を確認する
- **実施方法**：通信経路と設定を整理し、ブラウザの手動操作を併用して対象試験を段階的に実行する
- **結果の扱い**：相互接続、一部試験の成功、正式認定を区別し、未実施や失敗も記録する

:::

## 検証計画と実施状況

このページは、制作側が OIDF Conformance Suite で教材の OP を調べるための検証計画です  
suite の起動、OP との接続、module の実行は未実施です  
コピーして起動できるコマンド集や、成功した実験の記録ではありません

suite は、仕様の要求を自分たち以外が定義した試験で確かめる助けになります  
検証結果を読む際は、次を区別します  
[OIDF: About the Conformance Suite](https://openid.net/certification/about-conformance-suite/)

- 別の実装の RP との接続：選んだ実装・構成で相互運用できるかどうかの確認
- suite の一部の成功：実行した試験で確認できた結果
- 正式な OpenID Certification：定められた要件と手続きに基づく認定

これらを一つの「対応済み」にまとめません

## 試験対象と対応範囲

教材では OP を試験する側を利用し、Basic OP / Config OP を参照対象の採用案とします  
正式認定の取得や、全受講者が同じ環境を構築することは、第一稿の範囲に含めません  
現在の公式 OP 試験手順と、採用時に固定する suite の plan・variant・module を照合して対象を決めます  
[OIDF: Conformance Testing for OpenID Connect OPs](https://openid.net/certification/connect_op_testing/)

profile の説明には [Conformance Profiles v3.0](https://openid.net/wordpress-content/uploads/2018/06/OpenID-Connect-Conformance-Profiles.pdf) を参照します  
この文書は 2018 年の版です  
そこにある旧 test ID を、現在の suite でそのまま実行できる識別子とは見なしません  
Basic が「Code Flow の正常系だけ」を意味するとも考えません

最初に確認する差分は次の通りです  
これは完了済みの機能表ではなく、対象を決めるためのレビュー項目です

| 観点 | 教材の採用案 | 適合試験へ進む前の確認 |
|---|---|---|
| client 登録 | 事前登録 | suite 用の client と redirect URI の登録手順 |
| client 認証 | client_secret_basic | profile の client_secret_post 等の要件との差分 |
| フロー | Code + PKCE S256 | 選んだ variant の要求と教材の PKCE 方針 |
| 認証 UI | 通常のログイン・同意 | prompt=none/login/consent と手動操作 |
| 認証時刻 | 実際の認証時刻を保存 | max_age、auth_time の発行と検証 |
| nonce | 教材 RP は毎回送る | Code Flow で nonce を省略する他の RP まで一律に拒否していないか |
| 公開情報 | Discovery / JWKS / UserInfo | 宣言した値と実際の動作、issuer の一致 |
| 必須パラメータの処理 | 固定版で担当を確認 | Core §15.1 等と教材の対応不足 |

差分があれば、教材で対象外とした理由と、profile への適合に不足する事実を両方残します  
試験を通すために PKCE を通常構成で無効にしたり、認証を迂回する特別な URL を追加したりしません  
別設定で実験した場合には、その結果を教材の通常構成の結果と混ぜません

## suite・OP・ブラウザの通信経路

suite、OP、ブラウザは異なる場所で動くことがあります  
ブラウザで OP のログイン画面を開けても、suite から token endpoint や Discovery へ接続できるとは限りません  
ローカル構成では、コンテナ内の `localhost` とホスト上の OP を同じ接続先として扱わないようにします

実行前に、次の項目を一つの設定の記録にまとめます

- issuer、suite の base URL、redirect URI
- client の認証方式
- ブラウザ・suite・OP それぞれからの名前解決と到達性
- TLS の証明書と信頼関係

到達性と証明書の問題を区別し、失敗を隠すために TLS 検証を一律無効化しません

公式にはホスト型環境とローカルでの実行が案内されています  
ローカルで進める場合は採用版の [公式 Build & Run](https://gitlab.com/openid/conformance-suite/-/wikis/Developers/Build-%26-Run) を確認してから環境を作ります  
この初稿では同ページの起動手順を実証しておらず、依存関係やコマンドを動作確認済みとして提示しません  
ホスト型への接続に外部公開やトンネルが必要な場合は、利用者の明示的な承認を得る別タスクとします

試験にはダミーユーザーと専用 client を用意します  
ログやスクリーンショットには client secret、token、ユーザー情報が含まれ得るため、生ログを VitePress の公開ディレクトリへ置きません  
公開用の抜粋を作る場合は、元の証拠を保護した上で秘密を除きます

## 手動操作を含む試験手順

1. 固定した suite の OP 用 plan と variant を選び、必要な登録・設定を行う
2. 各ケースが示す指示を読み、通常の UI でログイン、同意、再認証を行う
3. 必要に応じてエラー画面やブラウザの動作を確認し、指定された証拠を保管する
4. suite の結果と通信内容を読み、仕様の節、設定、ライブラリ、アプリの担当へ原因をたどる
5. 修正後は対象ケースを再実行し、実装の版と結果を結び付ける

手動なのは最初のログイン一回だけとは限りません  
ケースごとの操作や確認が必要です  
Playwright や仮想認証器 E2E は、この手順の前提ではありません  
公式 OP 試験手順を、その時点の UI と一緒に読みます

### 観測結果に基づく原因調査

ここでは「`max_age` を付けた要求への ID Token に `auth_time` がない」という仮の観測を扱います  
実在する module の実行結果やエラーメッセージを再現したものではありません  
要求に `max_age` がある場合、ID Token に `auth_time` が必要であることを、まず仕様で確認します [OIDC Core §3.1.2.1](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest)

その上で、発行側のどこで必要な事実が失われたかを調べます

1. suite が送った要求と、OP が受信した要求に `max_age` があるか確認する
2. OP が保持した認証時刻と、再認証が必要だと判断した結果を確認する
3. 再認証に成功した場合、その時刻が発行処理へ渡っているか確認する
4. 発行された ID Token に、期待する値の `auth_time` が含まれるか確認する

値を一つ追加すれば試験が通る、と考えて発行時の現在時刻を代入してはいけません  
主張すべきなのは認証した時刻であり、トークンを作った時刻ではないからです  
仕様の要求を満たすためには、Claims の形だけでなく、その根拠となる事実まで処理を戻って確認する必要があります

このような調査では、最初からライブラリの不具合と決めません  
要求を受け取るアプリ、認証処理、保存層、トークン発行の設定のどこが担当する条件かを対応表へ戻って確認します  
修正後は当該試験に加え、関連する通常のログインや再認証を要求しない場合を確認し、別の経路を壊していないかを調べます

### 接続障害と仕様違反の切り分け

Discovery へ到達できなければ、まだその後の ID Token 検証は観測できていません  
それを「ID Token の試験が失敗した」と記録すると、調べる対象が曖昧になります

| 観測 | 調査の出発点 | この時点では言えないこと |
| --- | --- | --- |
| 接続がタイムアウトする | 名前解決・到達性・待受け | OP が Claims の要件を満たすか |
| TLS 検証で止まる | 証明書と接続名、信頼する証明書 | プロトコルの応答が正しいか |
| 応答は返るが必須の値がない | 要求条件と発行処理 | 環境設定だけを直せば解消するか |
| 手動操作の完了待ちで止まる | ケースが要求する操作 | 実装が拒否されたか、まだ未観測なのか |

この分類は調査の順序であり、suite がそのまま同じ名前の状態を出すという意味ではありません  
公式の結果表示を保存したうえで、自分たちの調査段階を付記します

### 再実行の条件

一度目の試験で同意やセッションが保存されると、二度目は画面や応答が変わることがあります  
そのため、実装のバージョンだけでなく、試験開始時に利用者がログインしていたか、client への許可があったかも記録します  
前の状態を消して再実行した結果と、状態を引き継いだ結果は、異なる条件での観測です

試験の指示に従った準備と、試験を成功させるためだけの認証を省略する特別な処理も区別します  
同じ実装と設定から再現できる手順を残すことが、結果を後から検証するための前提になります

## 試験結果と解釈の記録

次の記録様式は未実施から始めます  
実際の UI に表示された識別子と結果を記録し、教材が付けた評価を別欄にします

| 項目 | 現在値 / 実施時に記入する内容 |
|---|---|
| OP 実装 | 未実装<br>実施時は commit、依存関係と設定のバージョン |
| suite | 未選定<br>release/commit、ホスト型かローカルか |
| 対象 | 未選定<br>profile、plan ID、variant、module ID |
| 実行条件 | 未実施<br>日時、ブラウザ、OS、事前の認証状態 |
| 生の結果 | 未実施<br>suite に表示された値をそのまま記録 |
| 教材側の解釈 | 確認した性質、仕様の該当節、原因、修正先 |
| 証拠 | 未取得<br>保護されたログの場所と公開可能な抜粋 |
| 残る項目 | 未対応の要件、環境の制約、実行しなかった理由 |

例えば `REVIEW` や `WARNING` が表示されたら、その意味と必要な判断を確認します  
都合よく `PASSED` に読み替えません  
自分たちが実行しなかったものと、suite が `SKIPPED` と報告したものも区別します  
一部の試験が成功しただけで Basic OP 全体に適合したとは書かず、後から検証範囲を確認できる記録を残します

**確認問題:** OP テストが成功したら、メッセージ API の「閲覧できないチャンネルのメッセージを拒否する」試験を削ってよいでしょうか

**解説:** 削れません  
OP のプロトコル動作と、API での個々のリソースへのアクセス制御は対象が違います  
教材 RP の ID Token 検証、保存層の並行処理、WebAuthn の検証も、この OP 試験だけでは検証済みになりません  
Go のローカル試験と手動ブラウザ確認をそれぞれ残します
