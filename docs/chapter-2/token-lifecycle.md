# トークンの寿命と提供側の設計

::: tip このページの目標

トークンの更新・失効で変わる状態を説明し、コードや更新処理を一回だけ成立させるための条件を挙げられるようになる

:::

::: info このページの要点

- **寿命**：Access Token・Refresh Token・セッションの用途と終了条件を分ける
- **更新と失効**：更新で資格情報が切り替わり、失効が反映されるまでには検証方法やキャッシュの影響がある
- **提供側**：プロトコルの検証とアプリケーション固有の判断を分け、コード消費や発行の整合性を考える

:::

API を呼び出すまでの通信を踏まえ、継続利用・利用の終了・データの保存を考えます  
Client・AS・RS は、認可の説明にある[登場人物と役割の対応表](oauth.md#oauth-oauth-の登場主体)と同じ役割を指します

## トークンとセッションの寿命 {#lifecycle}


Access Token の寿命を短くすると漏えい後の利用可能期間を限定できますが、継続利用には更新や再認可の経路が必要です  
発行後に権限を維持・終了する仕組みを、トークンとセッションに分けて扱います

### Access Token と Refresh Token の用途 {#lifecycle-access-token-と-refresh-token-の用途}

[Access Token](../reference/glossary.md#access-token) は API に提示し、許可されたリソースへアクセスするために使います  
[Refresh Token](../reference/glossary.md#refresh-token) は AS のトークンエンドポイントへ送り、新しい Access Token を取得するために使います  
Refresh Token をメッセージ API に渡したり、Client の画面へ表示したりする必要はありません [RFC 6749 §1.4–§1.5](https://www.rfc-editor.org/rfc/rfc6749.html#section-1.4)

| 状態・値 | 主な保持先 | 用途 | 終わらせると何が止まるか |
| --- | --- | --- | --- |
| AS の認証セッション | AS とブラウザ | ユーザーの認証状態を再利用 | AS での認証状態の再利用 |
| Client のセッション | Client とブラウザ | Client 自身の画面利用 | Client のそのセッションでの利用 |
| Access Token | Client のバックエンド | API 呼び出し | そのトークンを使う API アクセス |
| Refresh Token | Client のバックエンド | 新しいトークンの取得 | その Refresh Token による更新 |
| 許可の保存記録 | AS の保存層 | 発行範囲・更新・失効を追う | 設計した範囲の発行や更新 |

この表の状態を一つの「ログイン中」という bool にまとめると、終了の意味が曖昧になります  
Client からログアウトしても、AS の Cookie や発行済みトークンが自動的に消えるわけではありません  
どの状態を無効にする操作なのかを決めて初めて、ログアウトの効果を説明できます

### トークンの寿命と更新条件 {#lifecycle-トークンの寿命と更新条件}

教材では、Access Token を比較的短命にし、必要と判断した Client に Refresh Token を発行する採用案です  
有効期間の具体的な値は、対象データ、漏えい時の影響、更新の頻度などを踏まえて選ぶ設定であり、RFC が一律に何分と定めたものではありません

この構成では、更新時に次の条件を確認します [RFC 6749 §6](https://www.rfc-editor.org/rfc/rfc6749.html#section-6)

- Refresh Token が有効であること
- 要求元が Refresh Token の発行先の Client と一致すること
- Client 自身の認証が成功すること
- 要求 scope を指定する場合、元の許可を超えていないこと

読み取りだけを許可した Client が、更新要求に書き込み scope を追加して権限を増やすことは拒否します

Refresh Token を発行するか自体も設計判断です  
長期のバックグラウンド利用を必要としないアプリには、更新用の秘密を増やさず、必要時に認可要求をやり直す選択もあります  
RFC 9700 はリスク評価に基づいて発行を判断するよう求めています [RFC 9700 §4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14.2)

### Refresh Token のローテーション {#lifecycle-refresh-token-のローテーション}

本教材では、更新ごとに新しい Refresh Token を発行し、古いものを無効にする[ローテーション](../reference/glossary.md#rotation)を設計例にします  
説明のため、同じ許可のもとで Refresh Token が更新される順序を `R0 → R1 → R2` と表します  
これは実トークンではなく状態のラベルです

`R0` での更新に成功したら `R1` が有効になり、`R0` は使用済みになります  
その後に `R0` が使われた場合、単に「知らない値」と捨ててしまうと、再利用という出来事が分かりません  
古いトークンと新しいトークンの関連を保存することで、不正利用の可能性を検知し、現行の更新用トークンを失効させる設計につなげられます  
正規 Client と攻撃者のどちらが先に使ったかは、この出来事だけでは判定できません [RFC 9700 §4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14)

教材では同じ許可から発行された Refresh Token を無効にし、再認可を要求する方針を採用案とします  
関連する Access Token を即時に止めるかは、API の検証方法とデータの保存方法も含めて決めます  
Refresh Token の失効は、発行済み Access Token の無効化を自動的に意味するものではありません

同時更新も試験対象です  
二つのタブやバックグラウンド処理が同じ Refresh Token を使うと、正規の操作でも再利用が発生します  
AS 側では、二つの更新が両方成功しないことを確認します  
重複要求への猶予期間を設ける場合は、漏えいしたトークンの再利用も許容する可能性を評価する必要があります  
更新でも、一回限りの消費を保存層で保証する設計が必要です

RFC 9700 は public Client の Refresh Token に送信者制約またはローテーションを要求します  
本教材は confidential Client でもローテーションを採る選択ですが、すべての Client にローテーションだけが必須という説明にはしません [RFC 9700 §2.2.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.2.2)

#### 並行更新と再利用 {#lifecycle-並行更新と再利用}

チャットビューアーが一覧の更新と検索を同時に実行し、どちらも Access Token の期限切れを検知したとします  
二つの処理がそれぞれ保存済みの `R0` を読み出すと、次の順序が成立します  
以下は競合を説明する例であり、traQ の実行結果ではありません

| 順序 | 一覧を更新する処理 | 検索する処理 | AS の状態 |
| --- | --- | --- | --- |
| 1 | `R0` を取得 | `R0` を取得 | `R0` が有効 |
| 2 | `R0` で更新に成功 | `R0` を保持 | `R0` は使用済み、`R1` が有効 |
| 3 | `R1` を保存 | `R0` で更新を要求 | 旧トークンの再利用を検知 |

本教材の方針では、AS は最後の要求を拒否するだけでなく `R1` による更新も止めます  
攻撃者が存在しなくても、Client が更新を調整しなければ利用者に再認可を求めることになります  
逆に、二つとも正常に受け入れてそれぞれ新しい Refresh Token を発行すると、一回の許可から更新に使える Refresh Token が複数残り、教材で想定した再利用検知が成立しません

通信の失敗も同じ状態遷移につながります  
AS が `R1` を確定した後に応答だけが失われると、Client には `R0` しか残りません  
その後に届く `R0` による更新要求は、AS から見ると旧トークンの再利用です  
AS は応答の失敗を理由に `R0` を有効へ戻さず、ローテーションの方針どおりに扱います

Client 側での更新の調整と、結果が不明な場合の対応は[コラム：OAuth Client の実装](../columns/client-implementation.md#client-refresh-coordination)で扱います

### 失効の反映 {#lifecycle-失効の反映}

opaque token を毎回保存層で調べる構成なら、API はトークンが無効になっていることを確認し、利用を拒否できます  
キャッシュを入れれば、その期限までは古い結果を受け入れる可能性があります  
自己完結した JWT を署名と期限だけで検証する構成でも、発行元の失効操作が自動的に伝わるわけではありません  
形式だけで即時失効の可否を断定せず、検証時に何を参照するかを見ます

[Introspection](../reference/glossary.md#introspection) は、保護されたリソース側が AS にトークンの状態を HTTP で問い合わせる仕組みです  
`active` の応答などを定めます  
[Revocation](../reference/glossary.md#revocation) は、Client が AS にトークンの失効を要求する仕組みです  
両者は要求元と操作の目的が異なります  
サーバー内で保存状態を読む関数や、独自の削除画面だけで標準エンドポイントを実装したことにはなりません [RFC 7662 §2](https://www.rfc-editor.org/rfc/rfc7662.html#section-2)、[RFC 7009 §2](https://www.rfc-editor.org/rfc/rfc7009.html#section-2)

失効を要求する手段と、失効を保存・反映する処理は区別されます  
標準エンドポイントを実装する場合も、その背後で Refresh Token の無効化と再利用時の状態遷移を保証する必要があります

#### 失効の遅延とキャッシュ {#lifecycle-失効の遅延とキャッシュ}

例えば API が検証結果を 60 秒間キャッシュする設計を考えます  
60 秒は説明用の値であり、推奨設定ではありません  
12:00:00 に有効性を確認し、12:00:10 に AS で失効させても、キャッシュだけを見る API は 12:00:50 の要求を受け入れる可能性があります  
AS の保存記録が正しく更新されていても、利用者が期待する「今から使えない」とは一致しません

Introspection を導入しても、応答を保存して再利用するなら同じ問題が残ります  
RFC 7662 はキャッシュによる性能上の利点と、失効後も古い結果を使うリスクを区別しています [RFC 7662 §4](https://www.rfc-editor.org/rfc/rfc7662.html#section-4)  
失効の要求側と実行側の間に伝播の遅れがあり得ることは、Revocation の仕様でも扱われています [RFC 7009 §2.1](https://www.rfc-editor.org/rfc/rfc7009.html#section-2.1)

毎回問い合わせる方式では反映を早められますが、AS や保存層の障害が API の利用にも影響します  
問い合わせに失敗したとき、以前の有効という結果だけで無期限にアクセスを認めると、失効を反映できない期間も無期限になります  
教材では、有効性を確認できない保護対象への操作を成功させない方針とし、可用性への影響も設計の結果として扱います  
「無効だと確認した」と「確認できなかった」は異なるため、内部の記録や運用上の調査でも区別します

また、トークンを失効させることと、利用者のリソースへの権限を変更することは別の入力です  
有効なトークンが残っていても、利用者が対象の閲覧権限を失ったなら、API は変更後の権限に基づいてアクセスを判断する必要があります  
トークンの検証結果だけをキャッシュしているのか、対象へのアクセス判断まで保存しているのかによって、古い権限が残る経路は変わります

### 有効期間と終了条件 {#lifecycle-有効期間と終了条件}

「Access Token は短く、Refresh Token は長く」という比較だけでは、利用者から見た動作は決まりません  
例えばチャットビューアーを一日中開いている人と、週に一度だけ開く人では、同じ更新期限でも再認可が必要になる頻度が異なります  
一方、ビューアーを閉じた後にもバックエンドが定期取得するなら、画面を開いていない期間にも権限が使われます

設計では、少なくとも次の三つの時間を分けて考えます

- **Access Token の有効期間**：そのトークンで API にアクセスできる期間
- **更新を続けられる期間**：利用者が再び認可操作をしなくても、新しいトークンを取得できる期間
- **失効を反映するまでの期間**：許可を取り消してから、各 API が利用を拒否するまでの期間

二番目をどう区切るかも、単一の数字ではありません  
最後に更新してから一定期間使われなければ終了する方式と、利用を続けていても最初の許可から一定期間で終了する方式では、放置された権限と継続中の権限への効果が違います  
RFC 9700 は Refresh Token の不使用期間に基づく失効を扱いますが、教材に一律の日数を与えるものではありません [RFC 9700 §4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14.2)

例えば説明用に「7日間更新がなければ終了」と決めても、毎日自動更新するバックエンドはこの条件に達しません  
それを望まないなら、許可全体の期限や、利用者が連携を取り消す経路も必要になります  
有効期間を決める議論では、人が操作した時刻なのか、プログラムが更新した時刻なのかも明示します

#### ログアウトや連携解除と失効範囲 {#lifecycle-終了操作と失効範囲}

次の表は、ログアウトや連携解除の設計を比較するための例です  
すべてを本教材で実装するという意味ではありません

| 利用者の操作・出来事 | 主に終わらせたいもの | 追加で決める点 |
| --- | --- | --- |
| この端末でビューアーからログアウト | その Client のセッション | バックエンドに Refresh Token を残すか |
| ビューアーとの連携を解除 | その client に与えた許可 | 派生した Access Token がいつ使えなくなるか |
| Refresh Token の漏えいを検知 | 同じ許可から発行された Refresh Token | 同じ利用者の別端末・別 client まで止めるか |
| 利用者のアカウントを停止 | その利用者としての利用 | 新規発行、更新、既発行トークン、API での対象ごとの権限確認へどう反映するか |

「すべて無効にする」は短く説明できますが、どの関連を保存していれば全部を列挙できるかが問題になります  
ユーザー ID だけで全件を消す設計では、別 client の連携まで止めることになります  
逆に、Refresh Token 一件だけを消す設計では、すでに発行された Access Token や別の Refresh Token が残る可能性があります

保存する単位を決めるときは、発行時だけでなく、失効時に必要なデータも検索できるかを考えます  
client ごとの許可、端末ごとのセッション、新旧の Refresh Token の関連をどこまで区別するかは、利用者へ提供するログアウトや連携解除と対応します  
RFC 7009 も、失効したトークンに関連するトークンや grant の扱いを、失効ポリシーと結び付けています [RFC 7009 §2.1](https://www.rfc-editor.org/rfc/rfc7009.html#section-2.1)

### 更新とエラー応答 {#lifecycle-更新とエラー処理}

API と AS は、拒否の理由を Client が区別できる応答を返します  
Bearer Token のエラーでは、API は無効なトークンに `invalid_token`、scope 不足に `insufficient_scope` を返します [RFC 6750 §3.1](https://www.rfc-editor.org/rfc/rfc6750.html#section-3.1)

例えば読み取りだけが許可されている Client の更新要求に対し、AS は同じ許可を超える書き込みの scope を発行しません  
何回更新しても書き込み権限は増えず、対象チャンネルへの権限がない場合も、トークンの更新によって参加権限が生まれるわけではありません

更新要求が成立しない場合、AS のトークンエンドポイントは `invalid_grant` を返します  
これは期限切れ、失効、別 client への発行など、仕様上複数の条件を表すエラーです [RFC 6749 §5.2](https://www.rfc-editor.org/rfc/rfc6749.html#section-5.2)  
提供側の記録には秘密の値を残さず、どの処理がどの分類で拒否したかを残します

Client がこれらの応答を受けて、更新・再認可・機能の停止のどれへ進むかは[コラム：OAuth Client の実装](../columns/client-implementation.md#client-errors-refresh)で扱います  
ここで示した寿命・失効範囲・エラー応答は設計例であり、参照実装による動作確認は未実施です

### トークン漏えい時のリスク {#lifecycle-トークン漏えい時のリスク}

短い期限やローテーションは、漏えいそのものを防ぐものではありません  
Bearer Access Token は有効な間、所持者に使われる可能性があります  
TLS、秘密を残さないログ、保存先の保護に加え、送信者の鍵と結び付ける方式もありますが、本教材は送信者制約の全実装を行いません  
この残るリスクを把握したうえで寿命と失効経路を選びます [RFC 6750 §5](https://www.rfc-editor.org/rfc/rfc6750.html#section-5)、[RFC 9700 §2.2.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.2.1)

### 検証対象 {#lifecycle-検証対象}

更新の正常系に加え、scope の拡大、別 Client の利用、旧トークンの再利用、同時更新を拒否し、関連する状態が方針どおり変化することを確認します  
失効については、AS 内の記録だけでなく、その後の API 呼び出しが拒否される時点まで観測します  
Client のログアウトを試す場合も、終了したセッションと有効なまま残るトークンを区別して記録します

## 提供側の責任分担 {#provider}


仕様の条件を、認可要求の受付、トークンの発行、状態の保存へ割り当てます  
ライブラリの成功応答だけでは、アプリケーション固有の認可や保存の整合性まで保証されません

::: info この節で扱う実装の範囲
本文は設計と検証条件の説明です  
参照サーバーによる実行検証は未実施です  
ここでは実装言語やライブラリを選ぶ前に、保証すべき条件を確認します
:::

<span id="provider-ライブラリとアプリケーションの境界"></span>

HTTP 要求の受付、利用者の認証と許可、プロトコルの検証、状態の保存を分けて考えます  
どのライブラリを選んでも、これらの条件を満たすことが提供側の責任です

### 提供側のデータモデル {#provider-提供側のデータモデル}

提供側で扱う情報は、次のように区別します

- **Client**：事前登録されたアプリの設定
- **User**：チャットを利用する内部ユーザー
- **[認証セッション](../reference/glossary.md#session)**：ブラウザと認証済みユーザー、実際に認証した時刻を結び付ける情報
- **認可の記録**：誰がどの Client にどの範囲を許可したかの記録
- **[認可コード](../reference/glossary.md#authorization-code)**：その許可をトークンと交換する一回限りの値

教材で扱う [grant](../reference/glossary.md#grant) の保存モデルは、Client、ユーザー、許可された scope、失効状態をまとめて追跡する設計上の記録です  
OAuth の authorization grant という仕様用語の定義と、DB テーブルが一対一に定められているわけではありません  
保存モデルの名前より、発行と更新が同じ許可の範囲を守ることが重要です [RFC 6749 §1.3・§1.5](https://www.rfc-editor.org/rfc/rfc6749.html#section-1.3)

例えばユーザーが同意画面を開いた後、別タブで別アカウントへ切り替えた場合を考えます  
古い画面の許可を、新しいセッションのユーザーに機械的に結び直すと、誰の判断だったかが曖昧になります  
教材では、保存した認可要求と認証済みユーザーの対応を確かめ、変化していたら再確認へ戻す設計にします

### 認可エンドポイントの処理 {#provider-認可エンドポイントの処理}

最初に、Client、callback、要求された処理、scope を確かめます  
本教材の構成では、章末の[PKCE とコード交換の保護](pkce.md)で扱う PKCE の条件もここで確かめます  
戻り先が検証できる前にそこへ転送しない点は[Authorization Code Flow](oauth-flows.md#code-flow)と同じです  
認証が必要なら、処理中の要求をサーバー側に保存し、ログイン後に元の処理へ戻します  
ログイン画面の hidden input だけを信頼して、scope や Client を復元する設計にはしません

ログイン後は、内部ユーザー ID と認証時刻を得ます  
`authenticated=true` だけでは、チャンネルへのアクセス権や後の OIDC の `auth_time` に対応できません  
既存の認証セッションを再利用したときは、現在の処理時刻を新しい認証時刻として記録しないようにします

同意画面の表示はテンプレート化できますが、許可・拒否の処理は教材でも正しく実装する必要があります  
セッション、CSRF 防御、保存した要求、実際の許可された scope を確認してから発行へ進みます  
AS のパスワード画面でユーザーを認証することと、Client にユーザーのパスワードを渡す Password Grant は別です  
本教材は Password Grant を実装しません [RFC 9700 §2.4](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.4)

### トークン発行と保存の整合性 {#provider-トークン発行と保存の整合性}

トークンエンドポイントでは、Client 認証と交換条件の検証を経て、コードの消費と発行結果の保存を行います  
一回限りの条件を守るには、保存層がどう競合を扱うかまで確認しなければなりません  
プロセス内のロックだけなら、将来複数プロセスにした際に同じ保証が成立するとは限りません

保存方式を評価するときは、同じコードに対して二つの交換要求を送った場合と、保存の途中で失敗した場合を調べます  
コードを使用済みにする処理とトークンを記録する処理が分離していれば、片方だけが成立する可能性があります  
どの更新を一体として確定するかが設計上の論点です  
Refresh Token のローテーションでも、旧トークンの消費と新トークンの記録に同じ観点が必要です

API 側は opaque token を検証する内部の連携から始める採用案です  
AS と RS が同じ参照アプリにあるため、保存したトークンに対応する許可を取得できます  
この内部処理を、標準の Introspection HTTP エンドポイントを実装したこととは呼びません

#### コード消費の原子性 {#provider-コード消費の原子性}

コードの状態を読んでから別の操作で使用済みに変えるだけでは、一回限りの条件を保証できません  
二つの要求 X と Y が同じコードを交換すると、次の実行順序が可能だからです

| 順序 | 要求 X | 要求 Y |
| --- | --- | --- |
| 1 | コードが未使用だと確認 | — |
| 2 | — | 同じコードが未使用だと確認 |
| 3 | 使用済みに変更して発行 | — |
| 4 | — | 使用済みに変更して発行 |

各要求が単独で動く試験では成功しても、この順序では二つの発行が成立します  
必要なのは、未使用という条件を満たす場合だけ消費を確定し、競合した他方にはその確定を認めないことです  
条件付き更新、保存層のロック、トランザクションの競合検出などが実現手段になりますが、特定の仕組みを使ったという名前だけでは保証になりません  
実際の分離レベルと更新条件で、二つの要求がともに成功しないことを確かめます

RFC は使用済みコードによる要求の拒否を MUST、可能な場合にそのコードから発行したトークンを失効させることを SHOULD としています  
一方で、特定の DB 製品や SQL 文を指定してはいません [RFC 6749 §4.1.2](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1.2)  
プロトコル上の結果を保存層の操作へ対応付ける部分が、アプリケーションの設計責任になります

#### 保存や通信の失敗 {#provider-保存失敗と通信失敗}

競合だけでなく、処理が途中で止まる位置によっても結果は変わります  
次は、コードの消費とトークンの保存を行う教材構成についての障害例です

| 失敗した位置 | 起こり得る不整合 | 設計で確認すること |
| --- | --- | --- |
| コードの消費後、トークン保存前 | コードだけが使用済みになり、交換結果が存在しない | 一体で確定する更新範囲と、失敗時に戻る範囲 |
| トークン保存後、コード消費前 | トークンが存在するのに、コードをもう一度使える | 発行結果だけを先に有効にしないこと |
| 保存の確定後、HTTP 応答の到着前 | サーバーでは成功し、Client からは結果が不明 | 応答の失敗を理由にコードを未使用へ戻さないこと |

保存層のトランザクションは、同じ境界に含めた更新をまとめるための手段です  
HTTP 応答が Client に届いたことまで、DB の確定と一体にするものではありません  
そのため、保存を確定した後の通信失敗を、保存前の失敗と同じように扱うことはできません

AS は応答を書き込めなかったことを理由にコードを再利用可能にしないため、交換結果が不明になった Client は新しい認可要求からやり直すことになります  
コードを再利用可能にすると、すでに発行した結果との対応が崩れます  
更新処理や複数の保存先を使う場合も、何が確定済みで何が未確定かを区別してから、再試行できる操作を決めます

ライブラリの呼び出しがエラーを返した場合も、その時点までに保存層へ何が書かれたかを確認します  
教材の検証では、失敗を返した事実に加えて、有効なトークンが残っていないか、コードが再利用できないかを観測します  
これらはプロトコル処理と保存処理を接続して確認すべき条件であり、ここで動作確認済みとするものではありません

### 拒否条件の検証 {#provider-拒否条件の検証}

本教材の構成（Code Flow に[章末の PKCE](pkce.md)を加えたもの）の正常系は、A さんが読み取りを許可し、Client がコードを交換して A さんが閲覧できるチャンネルのメッセージを取得する経路です  
設計を評価する際は、次の要求をどの処理が拒否するか、その判断に何の情報が必要かを説明します

- 誤った verifier によるコード交換
- 使用済みコードの再利用
- 別 Client に発行されたコードの交換
- 書き込み scope がない状態での書き込み
- A さんのトークンによる、A さんが参加していない DM へのアクセス

任意の実習では、例えばコードの再利用を拒否する処理や、閲覧できないチャンネルのメッセージを返さない API を対象にできます  
試験では HTTP 応答だけでなく、コードの使用状態や許可の記録も観測します  
通常の画面操作の成功は、競合や不正要求の拒否を確認したことにはなりません

対象チャンネルへのアクセス権の確認は API 側の契約であり、トークン発行の成功応答からその成立を判断することはできません  
ライブラリの検証とアプリ固有の認可を別々に試験し、組み合わせた経路も確認します

委譲する権限の範囲、コード交換、更新と失効が適切に実装されても、エンドユーザーの認証結果を Client が受け取り、検証するための標準的な契約は OAuth 単体では定まりません  
外部アプリへのログインには、認可とは別に認証連携の契約が必要です

### 処理間の責任分担 {#provider-処理間の責任分担}

責任分担表を実際に使うには、同じ要求について、各処理へ入る前と出た後に何が確定したかを追います  
「ライブラリに渡したので検証済み」という説明では、渡した値がどの入力から来たか、呼出しがどこまで成功したかが隠れてしまいます

A さんがビューアー C に読み取りを許可する要求を考えます  
認可画面には C の名前と要求 scope が表示され、A さんが許可ボタンを押します  
ここで信頼すべきなのは画面に見えた文字列ではなく、検証した登録情報、サーバーに保持した要求、現在の認証状態の対応です

| 境界 | 入力として扱うもの | 次の処理へ渡せる根拠 |
| --- | --- | --- |
| HTTP 要求からプロトコル処理へ | client ID、callback、scope、PKCE の値 | 登録情報や仕様の条件との照合 |
| 認証画面から許可判断へ | 認証処理の結果と保存した要求 | 利用者の内部 ID と要求の対応 |
| 同意画面から発行処理へ | 許可・拒否の選択 | CSRF 防御、保存した要求との対応、実際に許可した範囲 |
| コードからトークンへ | client 認証、コード、verifier | 発行先 client、一回限りの状態、交換条件 |
| トークンから API の操作へ | 有効性、利用者、許可された scope、対象 | 操作と対象のリソースの認可 |

例えば同意画面のフォームに `user_id` があっても、その値を発行対象のユーザーとして採用しません  
攻撃者がフォームを書き換えられることは、通常の HTTP 入力と同じ前提だからです  
フォーム値は操作の要求であり、認証済みユーザーという事実の代わりにはなりません

同様に、画面へ表示した scope と、許可の記録に保存した scope が異なる設計では、利用者が何を認めたかを説明できません  
プロトコル上の scope の意味は AS が定め、要求と発行結果が異なる場合の応答も契約に従います  
画面の説明、アプリのポリシー、発行された値の三つを対応させてレビューします [RFC 6749 §3.3・§5.1](https://www.rfc-editor.org/rfc/rfc6749.html#section-3.3)

#### 検証と応答の順序 {#provider-検証と応答の順序}

処理の順序にも意味があります  
例えば callback の登録との一致を調べる前に、ログイン失敗をその callback へ返す設計は、正常系のコード発行を防いでいても、不正な戻り先へ情報を送る経路を残します  
要求の拒否を実装したという事実と、安全な経路で拒否を返したことは別です [RFC 6749 §4.1.2.1](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1.2.1)

また、API で対象のメッセージ本文を読み、応答を書き始めた後にアクセス権を確認しても、すでに送った内容は取り消せません  
ライブラリがトークンを検証する時点、アプリがリソースを認可する時点、HTTP 応答を書き始める時点を分け、許可がそろう前に情報を出さない構成にします

この順序はファイルの配置だけからは判断できません  
認証済みでない利用者でも呼べる関数に何を渡せるか、失敗時に後続処理が実行されないかを、実際の呼出し経路で確認する必要があります

### 利用者ごとの保存状態 {#provider-利用者ごとの保存状態}

ユーザーが一人だけの試験では、別のユーザーを誤って選んでも結果が変わらない場合があります  
教材で二人を用意する目的は、単に画面の名前を変えるためではなく、許可が正しいユーザーに結び付いているかを確かめるためです

例えば A さんと B さんが同じ C に読み取りを許可し、同じ時刻にトークンを取得したとします  
保存層を client ID だけで引くと、後から書かれた B さんの許可が A さんの要求にも使われる可能性があります  
scope まで一致していても、対象の利用者が異なるため交換可能な情報ではありません

この設計をレビューする問いは、次のようになります

- A さんのコードを交換した結果が、A さんの許可を参照しているか
- B さんの更新が、A さんの更新状態を上書きしないか
- A さんが C との連携を解除したとき、B さんの連携まで消さないか
- 失効した A さんのトークンを、現在の C の別の許可で救済しないか

ここで必要なのは、必ず特定の複合キーを使うという結論ではありません  
同じ client、同じ scope、同じ利用者でも複数の許可を区別する必要があるかを含め、保存モデルと操作の意味が一致していることです  
テーブル設計は仕様に一意に定められていない一方、トークンが表す許可を別の許可へすり替えてよいわけではありません

#### モックと保存層の試験範囲 {#provider-モックと保存層の試験範囲}

試験用の保存層がすべての書き込みで成功を返すなら、DB の制約違反や同じコードを同時に使用した場合の競合は観測できません  
その試験は呼出しの組み合わせを確認する役には立ちますが、実際に保存したデータの整合性まで実証したことにはなりません

拒否を確かめる試験でも、最初の入力検証で落ちた要求だけを使うと、その先の保存条件が壊れていても気付けません  
例えばコード消費の競合を調べるなら、二つとも client 認証と verifier が正しく、消費の時点まで到達する要求である必要があります  
そのうえで、何件の成功結果と有効な発行記録が残ったかを調べます

仕様を読む作業、ライブラリの設定を確認する作業、アプリの方針を決める作業、保存層で実証する作業は、それぞれ異なる証拠を生みます  
具体的な呼出し順や保存 API は、実習で使うライブラリの固定版と接続して確認する必要があります

::: details コラム：OAuth 1.0 と OAuth 2.0

OAuth 2.0 は OAuth 1.0 と後方互換ではありません

バージョン番号や接続先の変更だけで移行できるものではなく、別のプロトコルです [RFC 6749 §1](https://www.rfc-editor.org/rfc/rfc6749.html#section-1)

本書は OAuth 2.0 に PKCE と OAuth Security BCP を合わせた構成を対象とし、OAuth 1.0 の署名計算は扱いません  
既存システムの資料に「OAuth」と記載されている場合は、版と採用仕様の確認が必要です  
本書の章順は、この構成を理解するための説明順であり、各仕様が成立した歴史的な順序を表すものではありません
