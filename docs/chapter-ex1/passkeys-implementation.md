::: tip このページの目標

:::

- **登録**：認証済みユーザーへ資格情報を結び付ける
- **認証**：challenge・origin・RP ID・署名・UV の条件を検証する
- **ブラウザの実装**：TypeScript で `navigator.credentials.create()` と `navigator.credentials.get()` を直接呼び出す

:::

## WebAuthn の登録と認証 {#webauthn}


この章では、既存ユーザーへの登録からパスキーでのログイン、サービスのログイン状態の確立までを設計します  
読み物で説明した公開鍵の仕組みを、要求をまたぐ状態へ対応付けます

登録と認証では、ブラウザが同じ WebAuthn API を使っているように見えても、サービスが保存し検証する情報が異なります  
先に全体の往復を図で確認してから、各段階を説明します

登録後にログインを許す根拠となるため、開始時の認証済みセッションと、完了時の登録先を対応付けます

認証は、登録済みの鍵が今回発行した challenge に対応する応答を作れたかを確認する操作です  
認証器から応答を得た時点ではまだ成功ではなく、サービス側の検証と開始状態の消費が完了してからログインを成立させます

### origin・RP ID・issuer の設定 {#webauthn-origin・rp-id・issuer-の設定}

まず、OP を表示する origin、WebAuthn の RP ID、OP の issuer を別々の設定として管理します  
[origin](../reference/glossary.md#origin) はスキーム・ホスト・ポートを含むブラウザ側の出所であり、RP ID を issuer の URL と同じ文字列にすればよいわけではありません  
RP ID と origin の適合条件は WebAuthn の定義に従います [WebAuthn Level 3 §5.4.2](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#dictdef-publickeycredentialrpentity)

教材の設定表には、各値、その値を使う処理、ブラウザからの到達方法を記録します  
リバースプロキシの内側で動かす場合も、サーバーから見える内部アドレスだけを写して終わりにはしません  
想定する外部 origin を明示し、受け取った Host ヘッダーなどを根拠なく信頼して許可先を増やさない設計にします

例えば教材用 OP を `https://auth.example` で表示するなら、origin はその URL の出所、RP ID は `auth.example` のようなドメインの値として検討します  
OIDC の issuer は、さらに OIDC の契約で一致を確認する識別子です  
三つが似た文字列でも、どの仕様がどの値を比較するかは別です  
開発環境から公開環境へ移す際も、一つの URL の設定を変えれば全条件が自動で揃うとは考えません

特に、以前登録した資格情報と RP ID の関係は、画面の移転先だけを変更して解消できる問題ではありません  
設定変更を設計するときは、新しい場所で登録する資格情報と、既存の資格情報を使う要求の両方を確認します  
この教材では複数ドメインを跨ぐ移行を実装せず、単一の RP ID を固定する前提を残します [WebAuthn Level 3 §5.4.2](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#dictdef-publickeycredentialrpentity)

ライブラリには公開鍵を使った応答の検証を任せますが、誰に登録を許すか、処理を開始するときにどこへ情報を保存するか、いつ無効にするかはアプリケーションの責任です  
公式パッケージ文書には、登録・ログインの開始と完了、`SessionData` などの型が示されています  
実装時はこの動的なページだけに依存せず、採用するバージョンに固定して責任の境界を確認します  
[go-webauthn 公式パッケージ文書](https://pkg.go.dev/github.com/go-webauthn/webauthn/webauthn)

### ブラウザの実装 {#browser-api}

パスキー実習では、ブラウザ側を TypeScript で書きます  
最終段階では登録に使う `navigator.credentials.create()` と、認証に使う `navigator.credentials.get()` を直接呼び出し、Go / `go-webauthn/webauthn` を使うサーバー側も実装して一往復を完成させます  

| 担当 | 実装する処理 |
| --- | --- |
| ブラウザの TypeScript | 開始要求、受信したデータの変換、WebAuthn API の呼び出し、応答の送信、結果の表示 |
| ブラウザと認証器 | 利用者の操作を受け付け、資格情報を作成する、または秘密鍵を使って認証応答を生成する |
| Go のサーバー | challenge と開始時の状態を保存し、応答を検証して登録やログインを確定する |

認証では、サーバーが毎回生成した challenge をブラウザへ渡します  
TypeScript で challenge や署名を自作する課題ではありません  
また、TypeScript が秘密鍵や PIN、生体情報を受け取ることもありません

#### 認証の呼び出し

以下は教材で用意する通信処理を含む**疑似コード**です  
`開始要求` と `完了要求` は標準 API ではなく、今後提供するサーバーへ通信する処理を表しています  
開始応答は `{ publicKey: ... }` という形を教材側で用意し、変換 API へはその内側の値を渡す想定です

```js
// 疑似コード：通信関数とサーバーは未提供
const options = await 開始要求()
const publicKey = PublicKeyCredential.parseRequestOptionsFromJSON(
  options.publicKey,
)
const credential = await navigator.credentials.get({ publicKey })
if (credential === null) throw new Error('認証応答がありません')
const result = await 完了要求(credential.toJSON())
// 成功表示は、サーバーの検証結果を確認してから行う
```

JSON では challenge などのバイナリ値を base64url で表現します  
`parseRequestOptionsFromJSON()` はこれを API が受け取るバイナリ値へ変換し、`toJSON()` は認証応答を送信可能な形に戻します  
登録では `parseCreationOptionsFromJSON()` で変換し、`navigator.credentials.create({ publicKey })` を呼び出します [WebAuthn Level 3 §5.1](https://www.w3.org/TR/webauthn-3/#iface-pkcredential)

`get()` が応答を返しても、サーバーでのログインはまだ完了していません  
応答には `clientDataJSON`、`authenticatorData`、`signature`、`userHandle` などが含まれ、サーバーは開始時の状態や保存済みの資格情報と照合します  
この検証については、後の「認証の開始と完了」で確認します

#### 実習の完成条件

明示的な登録ボタンとログインボタンを用意し、次の処理を実装します

- サーバーから開始用のデータを取得し、登録と認証に対応する API を呼び分ける
- 得られた応答を JSON に変換し、開始時と同じブラウザセッションでサーバーへ送る
- サーバーが検証を完了した場合だけ、登録完了またはログイン成功を表示する
- 利用者の中断、API の失敗、通信やサーバー検証の失敗を扱い、再試行では新しい開始要求を送る

`NotAllowedError` には中断以外の原因もあるため、必ず「利用者がキャンセルした」とは表示しません  
通信中の二重操作を防ぎ、失敗した場合もボタンを再び操作できるようにします

実習環境では secure context を用意し、WebAuthn API と上記の JSON 変換 API が利用できることを確認します  
開始・完了の通信、CSRF 対策、開始時の状態との結び付けは提供側のテンプレートにも必要です  
課題の完了確認では、通常の登録とログインに加え、中断時に成功表示されないこと、使用済みの応答を再送してもサーバーが拒否することを確かめます  
ブラウザ側だけで成功を判定していないか、ここで確認します

### 登録の開始 {#webauthn-登録の開始}

利用者が「パスキーを追加する」を押した時点で、OP の認証済みセッションから内部ユーザー ID を取り出します  
フォームの `user_id` をそのユーザーへの登録を許可する根拠にはしません  
教材では登録操作の CSRF 保護と、登録を許すだけの認証状態が維持されていることも確認します

登録を開始するときは、次の情報をひとまとめにして保存します

- 処理の種類：登録であること
- 登録先：対象ユーザーと、開始したブラウザセッション
- 要求との対応：challenge と有効期限
- 検証方針：UV を要求するかなど、開始時に決めた条件

この章の採用案は UV を要求することです  
登録の応答を受け取った際に、現在のフォーム値から検証方針を作り直してはいけません  
要求時に求めた条件と照合するためです

具体例として、利用者 A が登録を開始した後、同じブラウザでログアウトして B に切り替える場合を考えます  
残った画面で登録を完了できたとしても、A が開始したときの情報を B のセッションへつないだり、B の鍵として保存したりしてはいけません  
この教材では、開始時のユーザーとセッションの対応が失われた処理を終了し、登録をやり直す方針を採ります

二つのタブから同時に登録を始める場合も、開始時に保存した情報を「そのユーザーの最新 challenge」一個だけで管理すると、片方の応答が他方の要求と混ざります  
教材では各処理を区別し、完了時の要求がどの登録開始に対応するかを追う設計にします  
複数の登録を同時に開始できるようにするか、一つに制限して前の処理を終了するかは実装上の選択ですが、どちらの場合も古い応答を新しい開始として受け入れません

登録を取り消した場合や画面を閉じた場合にも、サーバーに保存した開始時の情報は自動で消えたとは限りません  
期限切れと消費済みを判定し、再試行では新しい処理を始めるようにします  
認証器側に資格情報ができた後でアプリ側の登録が失敗する場合もあるため、画面上の完了と保存側の完了を対応付ける必要があります

### 登録応答の検証と保存 {#webauthn-登録応答の検証と保存}

サーバーは開始時に保存した情報を取得し、ライブラリへ応答と検証すべき条件を渡します  
仕様の登録手順には、challenge、origin、RP ID に対応する値、要求した UV、アルゴリズムなどの確認が含まれます  
受け取った JSON に公開鍵らしい値があるだけでは、登録成功にはなりません [WebAuthn Level 3 §7.1](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-registering-a-new-credential)

検証を通過した資格情報は、credential ID、公開鍵、内部ユーザー ID、および採用版が要求する検証用データとして保存します  
秘密鍵や利用者の PIN をアプリケーション DB に保存する設計にはしません  
既存の credential ID を別ユーザーへ付け替える要求も拒否する方針にします

教材で重視するのは、検証と永続化の間の失敗です  
検証成功の直後に DB 書き込みが失敗したなら、利用者に「登録完了」と返すことはできません  
同じ応答が並行して届いた場合も、登録処理が二つ成立しないよう、開始時に保存した情報を使用済みにする処理と、資格情報の保存に整合性を持たせます  
採用する保存層で具体的な原子性を検証するまでは、単に「一度だけ使う」とコメントしただけで完成としません

登録完了の順序は、次の失敗を区別すると見通しがよくなります

| 失敗する場所 | 教材で成立させない結果 |
| --- | --- |
| 応答の検証 | 未検証の公開鍵をユーザーへ登録する |
| 開始時の情報を使用済みにする処理 | 同じ開始から複数の登録を成立させる |
| 資格情報の保存 | 保存していないのに登録成功と通知する |

この表は DB 操作の実装手順を指定するものではありません  
どの更新を一緒に確定させ、失敗したら何をやり直すかを、保存層とライブラリの挙動に合わせて決めるための条件です  
実装時には登録成功のレスポンスを返す直前だけでなく、永続化の失敗を意図的に起こした場合の結果も確認します

### 認証の開始と完了 {#webauthn-認証の開始と完了}

ログアウト後は、明示的な「パスキーでログイン」ボタンから認証を始めます  
Conditional UI は必須にしません  
開始時には新しい challenge と期限を発行し、認証を開始したブラウザのセッションと結び付けて保存します  
登録を開始したときの情報を流用しないことで、処理の種類も判定できます

アカウントを先に選ぶ方式では、そのユーザーに属する資格情報を照合します  
資格情報側からアカウントを特定する方式では、返された credential ID と user handle を保存済みの対応へ結び付けます  
画面の表示名や送信されたメールアドレスだけからログイン先を決めません  
どちらの方式も「署名を検証した鍵が、誰に登録された鍵なのか」が必要です

credential ID は資格情報を探す手掛かりであって、それを知っている人にログインを許す秘密ではありません  
攻撃者が A の credential ID を送ってきても、そのレコードの公開鍵に対応する正しい署名がなければ受け入れません  
逆に B の鍵で正しい署名が作れても、A のユーザー ID と組み合わせて A として認証してはいけません  
鍵の検証と、鍵が属するアカウントの照合が揃って初めて、ログイン先を確定できます [WebAuthn Level 3 §7.2](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-verifying-assertion)

認証応答では、署名に加えて次の条件を確認します [WebAuthn Level 3 §7.2](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-verifying-assertion)

- challenge が開始時の要求に対応していること
- origin が許可したものと一致すること
- `rpIdHash` が期待する RP ID に対応すること
- 要求した UV が満たされていること

署名が正しくても、これらの条件を満たさない応答や有効期限が過ぎた開始時の情報を受け入れない方針にします

署名カウンターの扱いも、単純な増加だけを普遍的な成功条件にしないよう注意します  
採用するライブラリと認証器の挙動を調べ、異常をどう評価するかを固定版で確認します  
同期型を含む対象の違いを隠して「数字が増えなければすべて攻撃」と書くことは避けます

### ログイン状態の確立 {#webauthn-op-セッションへの接続}

公開鍵を使った応答の検証に成功し、開始時の情報を使用済みにできたら、内部ユーザー ID と実際の認証時刻を使ってサービスの認証済みセッションを確立します  
教材ではセッション ID を更新し、未認証の状態から認証済みの状態へ移る時点を明確にする設計にします  
失敗した要求を成功用の画面へ進めたり、ブラウザに残った古い情報からユーザー ID を補ったりしません

このサービスが OIDC の OP でもある場合は、その後の認可要求で認証状態を材料として `prompt`、`max_age`、同意などを判断します  
ログイン方式が変わっても、OIDC を提供する場合の認可要求の検証や RP の ID Token 検証は残ります  
`auth_time` はトークンを発行した現在時刻で代用せず、認証の時刻に対応させます  
方式を Claims に載せる場合も、独自の値を標準の `amr` や `acr` だと説明しません [OIDC Core §2](https://openid.net/specs/openid-connect-core-1_0.html#IDToken)

ここで、パスキーの登録成功を認証成功と同じ通知へまとめないようにします  
登録は将来その鍵を使って入れるようにする操作であり、既に持つ認証状態を前提に実行する場面です  
今回の教材で既存セッションの認証時刻を更新するのは、パスキーによる認証を実際に完了したときとします  
設定画面で資格情報を追加しただけで、利用者がたった今ログインし直したことにすると、後続の `max_age` の判断に誤った時刻を渡すことになります

### 正常系と拒否条件の検証 {#webauthn-正常系と拒否条件の検証}

実装時には、まず一組の OS・ブラウザ・認証器について、通常のログイン、資格情報の登録、ログアウト、パスキーでのログインを手動で確認します  
ここで確認できるのは、その組合せで利用者が一連の操作を完了できたことです

サーバー側では、正常な fixture を基準に一条件ずつ変える試験を設計します  
別ユーザーへの登録、challenge の不一致と再利用、別のセッションで開始したときの情報、想定外の origin、登録されていない credential、要求した UV を満たさない応答を拒否できるかを確かめます  
並行して同じ応答を処理する試験は、保存層の原子性に対応させます  
UI を手動で操作して成功しただけで、これらの拒否条件が確認できたとは扱いません

要求した UV を満たさない場合の試験では、署名は正しく UV が false の応答を用意します  
応答の UV ビットを後から書き換えるだけでは署名も壊れるため、署名検証で拒否したのか UV を調べたのか区別できません  
適切な fixture を用意できない間は、その応答を拒否する試験を未実施として残します

手動確認でも、成功した利用者と処理を区別して記録します  
例えば「A で登録し、ログアウトし、同じ資格情報で A へ戻れた」と書けば、保存した鍵とアカウントの対応まで追えます  
さらに B の画面から A が開始したときの情報を使った場合を別に記録すれば、正常に動いた確認と、取り違えた要求を拒否した確認を区別できます  
ただしブラウザで作れなかった不正な応答まで確認済みにせず、サーバー側 fixture による確認が必要な項目として分けます

試験記録には次の情報を残します

- ライブラリ版と実装 commit
- 設定とブラウザ環境
- 各試験の成功・失敗・未実施

OIDC Conformance Suite の成功は、この内部認証の試験の代用にはなりません  
同期や回復システム、網羅的な attestation と拡張の対応は、今回の最小実装の範囲外です

### 確認問題 {#webauthn-確認問題}

**問い：登録応答の検証が成功した後、送信されたユーザー ID に資格情報を保存してよいでしょうか**

::: details 解説
登録開始時に認証済みセッションへ結び付けたユーザーと照合します  
鍵の登録手順を検証したことと、そのアカウントへ登録する権限があることは別です
:::

**問い：同時に届いた二つの要求が、開始時に保存した同じ情報を読めた場合、片方を後で削除すれば十分でしょうか**

::: details 解説
両方が削除前に成功処理へ進む可能性があります  
消費済みへの遷移を一度だけ成立させ、資格情報の保存やセッションの確立との整合性を検証します  
どの DB 操作で保証するかは、参照実装を作る段階で実証します
:::
