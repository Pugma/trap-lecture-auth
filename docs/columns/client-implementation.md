# コラム：OAuth Client の実装

::: tip このページの目標

OAuth Client が自身で保持・照合する状態と、AS・API の応答を受けた後の判断を、提供側が満たす契約と区別して説明できるようになる

:::

::: info このページの要点

- **責任の範囲**：state の照合、トークンの保管、エラー後の判断は Client の実装が担い、AS や API の検証では代わりにならない
- **認可要求の状態**：state は開始した処理ごとに、ブラウザセッションへ結び付けて保持し、一度だけ照合する
- **トークンの扱い**：Bearer Token は所持者が使える資格情報なので、ログや別サービスへ渡さない
- **エラーと更新**：拒否の種類ごとに次の操作を分け、Refresh Token の更新は一つの処理にまとめる

:::

本編の第2章は、AS とメッセージ API を作る提供側の視点で、Client が確かめる内容を提供側の契約として扱いました  
このページはその Client 側の対になる補足で、チャットビューアーのような Client が自身で保持し、判断する内容を扱います  
[OAuth による権限の委譲](../chapter-2/oauth.md)、[OAuth のフロー](../chapter-2/oauth-flows.md)、[トークンの寿命](../chapter-2/token-lifecycle.md)を読んだ後に参照するコラムです

## Client が担う確認 {#client-responsibility}

Authorization Code Flow では、AS と API がそれぞれの条件を検証しますが、それだけでは Client 側の条件は満たされません  
例えば AS がコードを受け付けても、そのコードが Client で開始したブラウザ処理の結果であることまでは、AS は確認していません  
反対に Client で state が一致しても、AS がコードの交換を受け入れる保証にはなりません

Client の実装が担う主な内容は次のとおりです

- **認可要求の状態**：開始した処理と、callback に戻った結果を対応付ける
- **トークンの保管**：取得した Access Token と Refresh Token を、必要な処理だけが使える場所に置く
- **応答への対応**：AS や API の拒否を受けたときに、更新・再認可・機能の停止のどれへ進むかを決める

以下では、この順に具体例を扱います

## 認可要求ごとの状態の保持 {#client-state}

`state` を送って戻った値を読むだけでは検証になりません  
別のセッション、期限切れの処理、すでに完了した処理に属する値を受け入れない保存方法が必要です  
教材では処理ごとに保持し、一度成功した処理の記録を再利用しません [RFC 9700 §4.7](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.7)

[OAuth のフローの通信例](../chapter-2/oauth-flows.md#code-flow-http-の通信例)では、callback に届いた要求について、Client はこのブラウザセッションに保存した要求の情報を取り出し、state と期限などを照合します  
戻ってきた値と、同じ要求内の別の値を比較するだけではありません  
PKCE を使う場合の `code_verifier` も、同じ認可要求の情報として Client のバックエンドに保持します

失敗した callback で Client が新しい state を作り、その値と到着した値を比較しても、元の要求との対応は取り戻せません  
教材では開始時の記録が存在しない要求を受け入れず、必要なら新しい認可要求として最初から開始します  
不一致を補正して成功へ進める処理は、検証が守ろうとした条件を失わせます

### 並行する認可要求 {#client-state-concurrent}

チャットビューアーで二つのタブから認可を開始すると、Client の識別子は同じでも、開始した処理は二つあります  
それぞれを処理 A、処理 B と呼ぶと、保持する `state` も別々になります  
これは値の対応を示すラベルであり、実際に使う値ではありません

処理 A の callback から結果 A を受け取ったなら、Client は開始時の状態から state A を取得して照合します  
セッションに一つだけ state を保存し、処理 B の開始で上書きすると、正常な処理 A の応答も照合できなくなります

教材では、開始した処理ごとに状態を分け、その状態が当該ブラウザセッションに属することも確かめる構成にします  
state の値を知っているだけで、別のブラウザの処理へ接続できる設計にはしません  
ここで必要なのは乱数の生成だけでなく、保存した組を正しいセッションから引くこと、期限を設けること、完了後の対応を再利用しないことです

### callback 後の画面の移動 {#client-post-callback-redirect}

検証済み callback からさらにアプリ内の元の画面へ戻したい場合、その移動先は OAuth の `redirect_uri` とは別のアプリケーション上の情報です  
教材では開始時の処理へ安全に結び付け、callback に到着した任意の URL をそのまま次の転送先にしません  
AS の検証が正しくても、Client 側に無制限の転送が残れば別の漏えい経路になるためです [RFC 9700 §4.11.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.11.1)

## トークンの受渡し {#client-token-handling}

チャットビューアーが受け取った Access Token を、別の分析サービスへそのまま渡す場面を考えます  
API が通常の Bearer Token として受け付ける構成なら、分析サービスもその値を提示できるようになります  
トークンを渡す行為は、単に利用者の識別子を教える行為と同じではありません  
トークンに認められた操作を実行する能力を、別のサービスへ渡すことになります

Client は、中身を知らない opaque な文字列だから無害だと扱ってはいけません  
API の資格情報として機能することが分かっている以上、ログや解析用イベントへ含めるだけでも、新たな取得経路が生まれます  
形式を隠すことと、所持者による利用を防ぐことは違います [RFC 6750 §5.1・§5.3](https://www.rfc-editor.org/rfc/rfc6750.html#section-5.1)

また、ある API で使えるトークンを、関係のない API へ試しに送る設計は避けます  
受信したサービスはその値を知るため、誤った送信先も漏えい先になり得ます  
提供側がトークンの受け入れ先を制限する考え方は、[Bearer Token の受渡し](../chapter-2/access-token.md#oauth-bearer-token-の受渡し)で扱います

## 発行結果とエラーへの対応 {#client-errors}

### トークン要求の失敗と許可範囲 {#client-errors-token}

トークンエンドポイントが `invalid_grant` などのエラーを返した場合、Client はこの応答を、Access Token が空だった成功応答として処理しません  
有効なトークンを取得できていないため、後続のメッセージ API の要求へ進む根拠がありません  
応答の形は[OAuth のフロー](../chapter-2/oauth-flows.md#code-flow-不正な要求とエラー応答)で扱います

Client が `read write` を要求しても `read` だけが許可されたなら、Client は実際の発行結果に従う必要があります  
AS は要求と異なる scope を発行する場合、応答の `scope` で実際の範囲を伝えます [RFC 6749 §3.3](https://www.rfc-editor.org/rfc/rfc6749.html#section-3.3)  
チャットビューアーは編集機能を利用できない状態として扱い、利用者が操作した段階で同じ書き込みを繰り返し試す設計にはしません

### API エラーへの対応 {#client-errors-api}

期限切れのトークンと権限不足は、同じ「メッセージを取得できなかった」でも原因が違います  
前者では有効なトークンの取得が必要ですが、後者では同じ許可のままトークンを取り直しても操作範囲は増えません  
例えば `read` だけで投稿の編集を試したとき、更新を繰り返して書き込みが可能になると考えるのは誤りです

また、対象の DM を利用者が閲覧できない場合、Client が追加の scope を要求すれば解消するとも限りません  
scope は Client への委譲範囲であり、利用者自身のリソースへの権限を作り出すものではありません  
再認可、トークン更新、対象のリソースの選び直しは、それぞれ異なる原因へ対応する操作です

Bearer のエラーでは、無効なトークンに `invalid_token`、scope 不足に `insufficient_scope` が定められています [RFC 6750 §3.1](https://www.rfc-editor.org/rfc/rfc6750.html#section-3.1)  
教材の Client は、すべての失敗から無限に認可画面へ戻すのではなく、どの段階の条件が不足したかを区別して処理を止めます  
詳細を利用者へ表示する場合も、API が開示していない DM の存在や内部の秘密を、Client が推測して補うことはしません

### 更新後の判断 {#client-errors-refresh}

API 呼出しが拒否されたとき、すべてを「トークンが古い」と扱って更新すると、権限不足でも同じ処理を繰り返してしまいます  
読み取りだけが許可されているビューアーが投稿を試みた場合、アプリは機能を利用不可とするか、必要な追加許可を別の認可要求で求める必要があります

| 拒否された場所 | 分かったこと | 教材での次の判断 |
| --- | --- | --- |
| API が Access Token を無効と判定 | 現在の値ではアクセスできない | 有効な Refresh Token があれば更新を試す |
| API が必要な scope 不足と判定 | 現在の許可範囲では操作できない | 同じ更新を繰り返さず、必要な許可を見直す |
| AS が更新要求を `invalid_grant` と判定 | その Refresh Token による更新が成立しない | 更新を停止し、必要なら再認可へ進む |
| AS への通信が失敗 | 更新の処理結果が分からない | [更新結果が不明な場合](#client-refresh-coordination)の方針へ進む |

`invalid_grant` だけから「盗まれた」「利用者が連携解除した」と原因を一つに断定することもできません  
期限切れ、失効、別 client への発行など、仕様上複数の条件を表すエラーだからです [RFC 6749 §5.2](https://www.rfc-editor.org/rfc/rfc6749.html#section-5.2)

利用者向けには再接続が必要なことを伝え、調査用には秘密の値を残さず、どの処理がどの分類で失敗したかを記録します  
教材の設計レビューでは、成功するまで更新するループではなく、どのエラーで停止するかを確認します  
ここで示したエラー後の判断は設計例であり、参照実装による動作確認は未実施です

## Refresh Token の更新の調整 {#client-refresh-coordination}

[並行更新と再利用](../chapter-2/token-lifecycle.md#lifecycle-並行更新と再利用)では、二つの処理が同じ `R0` で更新すると、AS が再利用として扱い、`R1` による更新も止まる例を扱いました  
Client 側では、同じ許可から発行された Refresh Token について一つの処理だけが更新し、他の処理はその結果を再利用する設計が考えられます  
ただし、アプリが複数のプロセスで動くなら、一つのプロセス内の調整だけでは足りません  
どこで最新のトークンを共有し、どの範囲の処理を直列化するかまでが Client の責任です

通信の失敗も別に考える必要があります  
AS が `R1` を確定した後に応答だけが失われると、Client には `R0` しか残りません  
タイムアウトは「AS が更新しなかった」という証拠ではないため、無条件に同じ値を再送すると再利用になります  
教材では結果が不明なまま更新を繰り返さず、利用者に再認可を求める方針を取ります  
これは障害時の教材の選択であり、RFC がすべての Client に同じ画面遷移を指定しているわけではありません

## 確認問題

**問い：二つのタブで認可を開始し、先に開始したタブの callback が state の不一致で失敗したとき、callback で新しい state を作り直して照合すれば処理を続けてよいでしょうか**

::: details 解説
作り直した state は、元の認可要求との対応を表しません  
不一致の原因は、セッションに一つだけ保存した state を後の処理が上書きしたことにあります  
開始した処理ごとに状態を分けて保持し、失敗した処理は新しい認可要求として最初からやり直します
:::
