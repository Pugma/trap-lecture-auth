# コラム：権限管理と scope

::: tip このページの目標

利用者の権限と Client への委譲範囲を分け、操作・scope・対象のリソースの条件を対応付けて権限の設計を検討できるようになる

:::

::: info このページの要点

- **scope**：概念と操作を対応付け、Client に委譲する範囲を定める
- **RBAC・ABAC**：ロールや属性を使い、個々のリソースに対する操作を判断する
- **Client**：提供元が定義した scope から、機能に必要な範囲を選ぶ

:::

本編では、OAuth による権限の委譲と、API が scope と対象へのアクセス権を確認する仕組みを扱いました  
ここからは、その仕組みをアプリケーションへ適用するための設計例です  
ロールや属性による権限管理、scope の切り方、認可処理の共通化を考えます  
本編のフローを理解するための前提ではなく、[OAuth のフロー](../chapter-2/oauth-flows.md)を読んだ後に参照するコラムです

## 操作ごとの認可 {#definitions-操作ごとの認可}

教材用に、A と B が参加するチャンネルと、B と C だけが参加する DM を考えます  
A の認証が成立していることを共通の前提にしても、次の要求の答えは一致しません

| 要求 | 教材での判断 | 判断に必要な情報 |
| --- | --- | --- |
| 参加しているチャンネルの B の投稿を読む | 許可できる | A がそのチャンネルを閲覧できること |
| 同じ投稿を A が編集する | 拒否する | 投稿者が B であること |
| B と C の DM を読む | 拒否する | A が DM の参加者でないこと |

ここで、投稿を読む画面を開けたことを根拠に編集まで許すと、読み取りと書き込みの認可が混ざります  
また、画面上で編集ボタンを隠すだけでは、直接 API に送られた要求を拒否できません  
認可は、サーバーが受け取った操作と対象に対して適用します  
すべての要求で権限を検証し、許可条件が成立しない場合に拒否する設計は、OWASP の推奨にも対応します [OWASP Authorization Cheat Sheet：Validate the Permissions on Every Request](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request)

判断の材料には、要求から読んだ値と、サーバー側で確かめた事実があります  
要求の「投稿者は A です」という値だけを信用すれば、利用者が値を書き換えて編集権限を作れてしまいます  
教材の設計では、操作する主体は検証済みの認証結果から、投稿者や所属先は保存されたリソースから求め、両者を照合します  
認証はこの判断に使う主体を定めますが、投稿者との関係まで代わりに判断するものではありません

## 認可の適用範囲 {#definitions-認可の適用範囲}

認可条件は、画面の種類ではなく、実行する操作とリソースに対応付けます  
例えば「投稿の詳細を見る」と「検索結果に本文を含める」は別の API でも、どちらも投稿内容を利用者へ返す操作です  
詳細画面だけで DM の参加者を確認し、検索側では確認しなければ、別経路から同じ情報を取得できてしまいます  
一つのボタンを保護することと、リソースへのアクセスを保護することの違いです

操作をまとめて処理する場合も、対象の一件だけを検証して残りを無条件に処理してよいとは限りません  
教材の例で複数の投稿を一度に取得するなら、許可された対象だけを返すか、要求全体を拒否するかを方針として定めます  
どちらを選んでも、閲覧できない投稿が結果に混ざらないことは共通の条件になります

さらに、認可に使う事実は時間とともに変わります  
昨日閲覧できたリソースを今日も閲覧できるかは、現在の権限とアプリケーションの方針によります  
認証が継続していても、権限の変更まで固定されるわけではありません  
認証結果を長く再利用する設計では、どの認可情報を操作時に確認し直すかを区別する必要があります

こうした確認を各 API が個別に思い出して実装するだけでは、経路ごとに抜けが生じます  
共通化できる認可処理と、投稿者や参加者などリソース固有の条件を整理し、両方が適用される構成にします  
OWASP が権限の検証を全要求へ適用するよう勧めるのも、特定の入口だけを守る設計では別経路が残るためです [OWASP Authorization Cheat Sheet：Validate the Permissions on Every Request](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request)

## RBAC と ABAC {#oauth-rbac-と-abac}

scope は外部アプリへ何を委譲するかを表しますが、利用者自身が何をできるかは、アプリケーションの認可モデルで決めます  
[RBAC（Role-Based Access Control）](../reference/glossary.md#rbac) は、権限をロールにまとめ、利用者などの主体をロールへ割り当てて管理する方法です [NIST：RBAC FAQ](https://csrc.nist.gov/Projects/Role-Based-Access-Control/faqs)

例えば教材用のチャット管理アプリで、「閲覧担当」「投稿担当」「メンバー管理担当」を用意するとします  
各利用者へ一つずつ操作権限を配る代わりに、担当する仕事に必要な権限をロールへまとめます  
担当が変わったときにはロールの割当てを変更し、そのロールに認めた操作を使える主体を管理します

| 教材で用意するロール | 許可する操作の例 | 別に確かめる条件 |
| --- | --- | --- |
| 閲覧担当 | 投稿を読む | 対象チャンネルを閲覧できるか |
| 投稿担当 | 投稿を作成・編集する | 投稿先へ参加しているか、編集対象の投稿者か |
| メンバー管理担当 | 管理対象のメンバーを変更する | その組織を管理できるか、自分の権限を越える変更でないか |

このロール名と割当ては説明用で、traQ の実際のロール定義ではありません  
ここで「投稿担当」というロールを持つだけで全組織の投稿を編集できることにすると、仕事の種類と対象範囲を混同します  
ロールの割当てがどの組織・チャンネルに対して有効なのか、リソース固有の条件をどこで検証するのかも決める必要があります

### 属性による認可 {#oauth-属性による認可}

[ABAC（Attribute-Based Access Control）](../reference/glossary.md#abac) は、主体、対象のリソース、要求された操作、必要に応じて環境の属性をポリシーに照らして判断する方法です [NIST SP 800-162：定義](https://csrc.nist.gov/pubs/sp/800/162/upd2/final)  
ロール名だけでは表しにくい、操作対象やその時点の条件を組み合わせられます

教材で「同じ組織に所属し、投稿者本人であり、チャンネルが書込み可能なら編集を許す」という規則を考えます

| 判断材料 | 教材で見る属性の例 | 信頼する取得元の例 |
| --- | --- | --- |
| 主体 | 利用者 ID、所属組織、利用停止の有無 | 検証済みの主体とサーバー側の登録情報 |
| リソース | 投稿者 ID、所属チャンネル、書込み可能な状態 | 保存された投稿・チャンネル |
| 操作 | 閲覧、作成、編集 | API が実行しようとしている処理 |
| 環境 | 操作時刻など、必要な追加条件 | サーバーが確認できる情報 |

これは ABAC の考え方を当てはめた教材上の規則です  
すべての属性を毎回使う必要はなく、その操作に必要な条件を選びます  
リクエスト本文の `owner_id` や `role` をそのまま信じると、攻撃者が認可の材料まで自由に変更できてしまいます

RBAC と ABAC は、製品を二者択一で選ぶための名前ではありません  
「ロールで編集操作を許す」ことと「その投稿の所有者・所属・状態を確認する」ことを組み合わせる設計ができます  
逆に条件を増やすだけでは管理しやすくならず、どの属性を誰が更新できるか、欠けた場合にどう拒否するか、権限変更をいつ反映するかが必要になります

### 利用者の権限と委譲範囲 {#oauth-利用者の権限と委譲範囲}

教材で利用者から権限を委譲された Client が呼ぶ API では、次の条件をすべて満たす操作だけを許可する設計にします

- トークンが有効で、対象 API に対して使える
- 発行された scope がその操作を許す
- 利用者のロールや属性が、そのリソースへの操作を許す

例えば投稿担当の A が `read` だけを委譲したなら、Client に編集を許しません  
逆に `write` を持つ Client でも、A が対象の投稿を編集できなければ拒否します  
scope、ロール、属性を単純な OR で足すと、いずれか一つの許可が他の制限を打ち消してしまいます

認可ポリシー自体には、例外、複数ロール、拒否の優先などの設計があり、すべての方式が同じ規則で許可・拒否を組み合わせるわけではありません  
上の三条件は、この教材がユーザーの権限と委譲範囲の両方を制限として使う設計です  
認可の実装は IdP だけの仕事ではなく、リソースや業務ルールを知る API に残ります

## scope の粒度 {#oauth-scope-の粒度}

API と AS を自分たちで設計する場合は、利用者が別々に許可・取消ししたい操作を基に scope の単位を考えます  
細かいほど必ずよいわけではなく、利用者が意味を理解できること、Client が必要な範囲を選べること、API がその制限を実際に検証できることを揃えます  
RFC 9700 は、用途に必要な最小限へトークンの権限を制限することを推奨しています [RFC 9700 §2.3](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.3)

次は新しい API を設計する場合の比較です  
`messages:read` などは架空の scope 名であり、traQ が受け付ける値ではありません

| 分け方 | 利点 | 検討すること |
| --- | --- | --- |
| `read` / `write` | 要求する値が少なく、機能をまとめやすい | 閲覧だけでも広い種類の情報を取得できないか |
| `messages:read` / `messages:write` | メッセージ操作を他の機能から分けられる | 作成と削除など、影響が違う操作もまとめてよいか |
| `messages:read` / `messages:create` / `messages:delete` | 用途や影響に応じて別々に委譲できる | 同意画面や互換性の管理が複雑になりすぎないか |

コロンや名前の前半に、OAuth 共通の階層関係や包含規則はありません  
`messages:write` を持てば `messages:read` も含むかは、提供元が定める意味によります  
RFC 6749 が定めるのは scope の伝え方などであり、名前の意味は AS 側が定義します [RFC 6749 §3.3](https://www.rfc-editor.org/rfc/rfc6749.html#section-3.3)

教材の設計では、利用者のロール名をそのまま scope にすることも慎重に考えます  
`admin` だけでは、Client がメンバー管理を必要としているのか、投稿削除を必要としているのかが分かりません  
ロールは人や主体の担当をまとめるため、scope は Client に預ける操作を区切るため、と関心を分けると変更の影響を追いやすくなります

scope が細かくても、「どのチャンネルか」「他人の投稿か」は別に確認します  
一方で scope にリソースの制約を表す設計が一切できないという意味でもありません  
大切なのは、採用した提供元の契約を読み、トークンが表現する範囲と API が追加で判断する範囲を明確にすることです

### 概念と操作の対応 {#oauth-概念と操作の対応}

scope を設計する一つの方法は、「何に対する、どの操作か」を組にすることです  
例えばメッセージという概念に `read`・`create`・`update` を対応付け、`messages:read`・`messages:create`・`messages:update` と定義します  
ここでは個々のメッセージ ID を scope に埋め込まず、具体的な対象へのアクセス可否を API 側の条件で確認する設計を採ります  
これらは教材用の名前であり、traQ の既存 scope や OAuth 共通の命名規則ではありません

| 概念と操作 | scope の例 | 個々の対象で確かめる条件の例 |
| --- | --- | --- |
| メッセージの閲覧 | `messages:read` | そのメッセージが属するチャンネルを閲覧できる |
| メッセージの作成 | `messages:create` | 投稿先チャンネルへ投稿でき、書込み可能な状態である |
| メッセージの編集 | `messages:update` | そのメッセージの投稿者で、チャンネルが書込み可能な状態である |
| 添付ファイルの取得 | `files:read` | そのファイルの公開範囲や共有先へのアクセス権を満たす |

この分け方なら、同じ `messages:update` でも、A さん自身の投稿は編集でき、B さんの投稿は拒否するという違いを表せます  
作成時にはまだ対象メッセージが存在しないため、親となる投稿先チャンネルに対して条件を確認します  
「どの種類の操作を委譲したか」と「今回の対象へ操作できるか」を分けることで、scope を対象の数だけ増やさずに済みます

### 認可インターフェース {#oauth-認可インターフェース}

似たリソースへ認可処理を広げるときは、操作と検証条件の対応を共通の契約として整理できます  
例えば「検証済みの主体・操作・対象・実行時の条件を受け取り、許可または拒否を返す」というインターフェースを設けます  
これは教材上のアプリケーション設計であり、OAuth が定める API やライブラリのインターフェースではありません

共通の処理とリソース固有の処理を、次のように分担します

- **共通の入口**：トークンの有効性と提示先を検証し、API が実行する操作に必要な scope を照合する
- **リソースごとの規則**：メッセージなら投稿者やチャンネル、ファイルなら共有設定など、対象に応じた条件を確認する
- **操作を許可する条件**：両方の確認が許可した場合だけ操作を実行し、未定義の操作や必要な条件を確認できない場合は許可しない

例えば、メッセージ取得と添付ファイル取得を同じ認可の入口へ接続し、それぞれに必要な scope と閲覧条件を登録します  
呼出し側は共通の契約に従いつつ、対象を検証する側はリソースの性質に応じた規則を持てます  
共通化するのは検証を呼び出す手順と判定の扱いであり、「閲覧」という同じ名前だけで全リソースに同じ権限を与えるわけではありません

操作の種類はサーバー側の処理から決め、所有者や所属先は保存された対象から取得します  
要求元が送った `action` や `owner_id` をそのまま認可の根拠にせず、一件ずつ取得する処理・一覧を取得する処理・更新処理で同じ規則を適用します  
一覧でも対象ごとの制約を検索条件などへ反映し、権限のないリソースを返してから画面側で隠す実装にはしません

この形なら、リソースの追加時には「対応する操作」「必要な scope」「対象の検証条件」を組として見直せます  
同じ scope で閲覧可能な対象と不可能な対象を試すことで、共通処理だけが成功し、対象の検証が抜け落ちていないかも確認できます

## Client の scope 選択 {#oauth-client-の-scope-選択}

既存の API を利用するだけの場合、Client は提供元が用意した scope から選びます  
提供元が `read` だけを定義しているとき、Client が `messages:read` と書き換えてもメッセージだけの権限にはなりません  
狭い要求を表せない場合は、その提供元で選べる最小の範囲と取得できる情報を確認し、不要な取得・保存を避ける設計にします  
Client 側で利用を控えることと、トークン自体の権限が狭くなることは別です

traQ を利用するチャットビューアーなら、まず機能と外部 API の呼出しを対応付けます

| Client の機能 | 外部への要求 | 権限を求める判断 |
| --- | --- | --- |
| 投稿の閲覧 | メッセージを取得 | 提供元の `read` を確認し、広い読み取り範囲も把握する |
| 投稿の編集 | メッセージを編集 | 機能を提供する場合に `write` を検討し、対象の編集権限も必要とする |
| ビューアー内の表示設定の変更 | Client 自身の設定を保存 | この操作だけを理由に外部 API の `write` を求めない |

最後の行が示すように、Client 自身の権限と外部 API の権限は別です  
外部サービスの管理者だからといって、ビューアー内の課金設定やメンバー管理まで自動的に許可する必要はありません  
外部の属性を使う場合も、どの提供元のどの意味を信頼し、Client 自身のロールやポリシーへどう対応付けるかを決めます

実装では、要求した scope と実際に許可された scope を区別します  
発行結果が要求と異なれば AS はその範囲を通知しますが、Client が毎回の応答に必ず同じ形式で scope が列挙されると決めつけず、提供元と仕様の応答条件に従います [RFC 6749 §3.3・§5.1](https://www.rfc-editor.org/rfc/rfc6749.html#section-3.3)

Client 自身も必要最小限の scope を要求することが推奨されています [RFC 6749 §10.3](https://www.rfc-editor.org/rfc/rfc6749.html#section-10.3)  
必要な権限がなければ、該当機能を利用できないことと理由を示します  
追加機能を使う際に改めて許可を求める構成も考えられますが、以前の許可が自動的に合算されるかは提供元次第です  
再認可後も実際の範囲を確認し、拒否されたら要求を繰り返し続けないようにします

画面の操作可否は利用者向けの案内です  
その判断の後にロールや所属が変わる場合もあるため、API は要求ごとに最終的な認可を行い、Client は拒否にも対応します  
これらは IdP を自作しなくても、外部 API を使うアプリとそのバックエンドに必要な設計です

**確認問題：** 読み取り専用のビューアーを、外部サービスの管理者が使います  
将来の機能追加に備えて `write` も要求し、Client 内でも自動的に管理者として扱ってよいでしょうか

::: details 解説
現在必要な機能は読み取りなので、その提供元で必要な最小の scope を選びます  
利用者が強い権限を持つことと、それを Client へ預ける必要があることは別です  
また、外部サービスの管理者という属性を Client 内の管理権限へ対応付けるには、別のポリシーが必要です  
将来の機能、外部への委譲、Client 自身の権限を一つの「管理者」でまとめないようにします
:::


## 権限変更の反映

ここまで説明した RBAC・ABAC を使う場合は、ポリシーに渡すロールや属性の取得元も確認します  
署名済みトークンにロールを入れる構成でも、その値は発行時点の情報であり、現在の役割変更が自動的に反映されるわけではありません  
保存層を毎回参照するのか、どの期間キャッシュしてよいのかを、権限変更を反映すべき時間と合わせて決めます

教材で要求を拒否できるか試験するときは、同じ scope の A と B で異なるリソースへアクセスする場合に加え、途中でロールを外した場合、対象の所属が変わった場合、必要な属性を取得できない場合を考えます  
API が不明な状態を無条件の許可へ変えないことと、Client に保存した古い表示情報だけで操作を実行しないことを確認します
